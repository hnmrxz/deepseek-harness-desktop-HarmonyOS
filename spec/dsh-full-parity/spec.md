# Feature Specification: dsh 核心升级 0.1.6-alpha.2 —— 设置项核查与工作区工具能力修复（v3 周期）

**Created**: 2026-09-20  
**Status**: Draft  
**Input**: User description: "适配最新的官方web dsh-v0.1.6-alpha.2版本能力。注意检查各设置项是否正常。解决工作区文件夹文件读写等工具能力问题"

## Overview

把端侧捆绑的 dsh 核心从 0.1.5-rc.2/rc.3 升级到 **0.1.6-alpha.2**（官方 Web 前端随核心包同步升级），并在新核心之上：①逐项核查 Web UI 与原生两侧的设置项；②全面诊断并修复工作区文件读写等 agent 工具能力问题。本周期是 `spec/dsh-full-parity/` 的 **v3 覆盖重写**：v2 已交付的 UI 复刻成果（WebShell 直载官方 UI、RemoteShell 手机范式、路由矩阵）作为基线保持不动，本周期不重做 UI；v2 遗留未执行的最终验证并入本周期验证阶段一并回归。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 核心升级到 0.1.6-alpha.2（Priority: P1）

用户打开应用，端侧 host 运行 0.1.6-alpha.2 核心并伺服**新版官方 Web UI**；既有能力（会话创建、消息回合、审批/提问交互）在新核心下不回归。

**Why this priority**: 其余所有故事都依赖新核心跑起来；这是整个周期的前置切片。

**Independent Test**: 重新打包核心并启动 host，确认树内元数据版本为 0.1.6-alpha.2、Web UI 正常打开并显示新版前端、能完成一次完整问答回合。

**Acceptance Scenarios**:

1. **Given** 打包配方指向 0.1.6-alpha.2，**When** 运行核心打包全流程，**Then** 产出可安装的核心包并通过全部形状断言（无静默跳过的补丁）。
2. **Given** 设备/模拟器上安装新包，**When** 应用启动 host，**Then** host 成功绑定 HTTP、写入 host-ready.json、官方 Web UI 可访问。
3. **Given** host 已就绪，**When** 通过 Web UI 或原生界面创建会话并发送一条消息，**Then** 回合正常完成（模型响应或明确、真实的失败原因，而非静默失败）。
4. **Given** 已安装 rc.3 的既有设备，**When** 升级到仅含 alpha.2 的新包，**Then** 版本决策选中 alpha.2；既有已装核心树的回滚路径不被破坏。

---

### User Story 2 - 工作区文件读写等工具能力端到端可用（Priority: P1）

用户让 agent 在工作区里做文件操作：新建文件、读取文件、修改（覆盖）已有文件、列出工作区目录——全部成功；Web UI 的工作区文件面板同样可用。已知的历史问题（沙箱拒绝 `link()` 的写降级、默认工作区不能是 `/`）必须有端到端证据证明已解决。

**Why this priority**: 文件读写是 agent 工具能力的基本盘，也是用户点名的痛点；不解决它，升级后的核心对用户而言仍是"空壳"。

**Independent Test**: 在真机或模拟器上让 agent 执行"创建→读取→修改→列出"四步文件链，再在 Web UI 工作区面板核对文件可见；全程零工具报错。

**Acceptance Scenarios**:

1. **Given** 一个已就绪的会话，**When** 要求 agent 新建一个工作区文件，**Then** 文件真实落盘、内容正确（覆盖 `link()` 被沙箱拒绝的降级路径）。
2. **Given** 工作区已有一个文件，**When** 要求 agent 修改它，**Then** 覆盖写入成功且内容更新（`rename` 发布路径）。
3. **Given** 工作区有若干文件，**When** 要求 agent 读取其中一个并要求列出目录，**Then** 两者都成功返回真实内容。
4. **Given** 会话已建立，**When** 在 Web UI 打开工作区文件面板，**Then** 面板列出工作区真实文件，与沙箱目录内容一致（默认工作区是可写目录而非 `/`）。
5. **Given** 端侧工具集（ondevice preset）配置，**When** 会话运行，**Then** 工具能力与配置声明一致：被禁用的工具不出现在会话中，被启用的工具真实可用。

---

### User Story 3 - Web UI 设置项逐项正常（Priority: P2）

用户在**新版官方 Web UI** 的设置页逐项操作：模型/供应商与密钥、工具开关、插件管理、外观等——每个设置项都能打开、修改、保存，且重启后不丢。

**Why this priority**: 新版本可能改变设置项的形态与存储；用户点名要求核查，这决定升级后的日常可用性。

**Independent Test**: 构造设置项核查清单（升级后按新版设置页实际项生成），逐项走"改→存→重启→读回"四步，全部通过。

**Acceptance Scenarios**:

1. **Given** 新版 Web UI 已打开，**When** 进入设置页，**Then** 设置页正常渲染，无加载失败/空白分组。
2. **Given** 任一设置项，**When** 修改并保存后重启应用，**Then** 设置值保持不变。
3. **Given** 模型/密钥类设置，**When** 配置真实可用的模型端点与密钥，**Then** 会话能基于该配置完成一次真实模型调用。

---

### User Story 4 - 原生设置项在新核心下正常（Priority: P2）

用户在原生侧的设置能力——远程主机连接与重认证、主题切换、核心管理（版本展示、切换/回滚）——在 0.1.6-alpha.2 之上全部正常。

**Why this priority**: 原生设置是双形态体验的另一半；核心升级最容易碰坏的就是核心管理与主机连接链路。

**Independent Test**: 在设备/模拟器上走查原生设置入口：连接一个远程 host、切换主题并重启验证、在核心管理页确认版本显示与回滚动作。

**Acceptance Scenarios**:

1. **Given** 应用已连接本端 host，**When** 打开原生设置/核心管理页，**Then** 显示 0.1.6-alpha.2 版本信息，与树内元数据一致。
2. **Given** 一台已装过旧核心的设备，**When** 在核心管理页执行回滚/切换，**Then** 动作按既有语义执行（正在使用的版本拒绝覆盖等防护不变）。
3. **Given** 远程模式，**When** 输入远程 host 地址连接并触发重认证，**Then** 连接、断连提示、重认证流程与 v2 行为一致。
4. **Given** 主题偏好，**When** 切换主题并重启应用，**Then** 主题保持且应用成功。

---

### User Story 5 - 协议兼容回归（Priority: P3）

ArkTS 客户端与原生模型层使用的协议端点在 0.1.6-alpha.2 上逐一兼容：会话创建/列表/跟随、轨迹流、审批与提问、工作区文件列表等既有端点不回归；上游若新增/变更端点，按新契约重新生成兼容层。

**Why this priority**: 协议漂移是版本升级的隐性断点；显式回归才能保证 v2 成果（原生手机链）在新核心上继续成立。

**Independent Test**: 用既有协议探测工具对 0.1.6-alpha.2 的 host 跑一轮端点探测，与当前契约逐字段核对，漂移即适配后复测通过。

**Acceptance Scenarios**:

1. **Given** 0.1.6-alpha.2 host 已就绪，**When** 运行协议端点探测与契约核对，**Then** 既有端点全部按预期响应（或已适配后响应）。
2. **Given** 原生手机链（RemoteShell 全功能），**When** 连接新核心 host 完成一轮会话操作，**Then** 回合流、工具卡、审批/提问、轨迹面板表现与升级前一致。

---

### Edge Cases

- 打包时上游源码漂移导致补丁形状断言失败：必须**显式适配**（更新断言与补丁），绝不允许静默跳过或放宽到"找不到就过"。
- 新版 dsh-web-app 的启动参数表变化（增删 CLI 选项）：以新版本源码为准重新核对，不允许沿用旧参数表想当然。
- 新版 Web UI 若对宿主环境提出新要求（新信任模型/新必填配置）：host 入口脚本按新要求适配，保持"端侧差异只走运行期组合 + 打包补丁层"的不变式。
- 真机不可用时：模拟器验证覆盖功能性回归，但 `link()`/symlink 类沙箱策略问题在模拟器上无法定论——验证报告必须如实区分"已验证/仅模拟器验证未覆盖"。
- 既有设备上存在旧核心树与新包并存：版本决策、空间清理（逐出策略）不得误删正在使用的版本。
- `koffi` 等原生依赖版本要求随新核心变化（如 dsh 要求 koffi ^3.x）：沿用自建/移植件供给路径重新适配，产出的原生件必须通过必需产物校验。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 核心打包配方的版本 MUST 更新为 0.1.6-alpha.2，且该配方保持唯一事实来源；打包全流程 MUST 成功产出核心包并放入应用内置资源。
- **FR-002**: 应用内置资源 MUST 只保留 0.1.6-alpha.2 一个核心包（移除 rc.2/rc.3 旧包）；已安装旧核心树的设备 MUST 保留既有回滚语义。
- **FR-003**: 全部既有沙箱补丁与垫片（Origin 栅栏列表、link 降级、凭据属主豁免、ESM proxy 分支、sharp 调度器、平台别名、停止通道等）MUST 在 0.1.6-alpha.2 源树上重新生效并通过形状断言；任何上游漂移 MUST 显式适配并留痕。
- **FR-004**: 端侧 host MUST 在 0.1.6-alpha.2 上成功启动：HTTP 绑定、host-ready.json 写出（含 workspace 字段）、官方 Web UI 伺服可用。
- **FR-005**: agent 工作区文件能力 MUST 端到端可用：新建写入（`link()` 被拒后的降级路径）、覆盖写入、读取、列目录四类操作全部成功；Web UI 工作区文件面板 MUST 展示与沙箱一致的真实文件。
- **FR-006**: 端侧工具集配置（ondevice preset）MUST 与新核心的工具机制一致：禁用项不出现在会话、启用项真实可用；若新核心提供更适合端侧的工具配置方式，按新方式适配。
- **FR-007**: Web UI 设置页 MUST 逐项核查（清单以新版设置页实际项为准）：每项可打开、可修改、可保存、重启后保持；发现的故障逐项修复。
- **FR-008**: 原生设置能力（远程主机连接/重认证、主题、核心管理含版本显示与回滚）MUST 在新核心下正常，行为与 v2 基线一致。
- **FR-009**: ArkTS 客户端协议层与 0.1.6-alpha.2 MUST 兼容：既有契约端点逐一探测验证通过；上游契约若有增删变更，兼容层按新契约再生成并复测。
- **FR-010**: 仓库既有质量门禁与构建 MUST 全绿：七项检查脚本全部通过、entry 构建成功，不因升级引入回归。
- **FR-011**: 最终验证 MUST 为 build+ui 范围，且 MUST 一并回归 v2 遗留验收（形态路由矩阵、删除收敛后的页面回归、手机链对照复刻不回归）。

### Key Entities *(include if feature involves data)*

- **核心打包配方**: 版本号、平台、原生依赖别名（overrides）、裁剪规则、必需原生产物清单——升级的唯一入口。
- **核心包**: zip 容器 + 树内元数据（版本、profile、插件清单）——端侧识别与版本决策的依据。
- **host 就绪信息**: host 落盘的机读文件（含 baseUrl、token、workspace 字段）——客户端连接与建会话的凭据来源。
- **设置项核查清单**: 升级后按新版 Web UI 设置页实际项生成的逐项走查记录（项名、四步结果、修复状态）。
- **协议契约端点表**: 客户端与服务端共用的端点契约，由探测工具生成/核对。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 设备/模拟器上 host 以 0.1.6-alpha.2 启动，核心版本在原生核心管理页与树内元数据两处一致可见。
- **SC-002**: agent 在单个会话内完成"新建→读取→覆盖修改→列目录"四步文件链零报错；Web UI 工作区面板与沙箱目录内容一致。
- **SC-003**: 设置项核查清单覆盖 Web UI 与原生全部设置项，100% 完成"改→存→重启→读回"走查，故障项全部修复或如实登记为上游限制。
- **SC-004**: 七项质量门禁 + entry 构建 + 协议探测全部通过。
- **SC-005**: v2 遗留验收（路由矩阵、删除回归、手机链对照）回归全部通过。

## Assumptions

- 0.1.6-alpha.2 为预发布版本，其依赖闭包可在打包机上物化（npm 上已确认存在）；预发布版本的风险由用户明确选择承担。
- 原生件供给路径沿用：koffi 走自建 3.x 路线、node-pty/sharp 用 ohos 移植件；若新核心版本要求变化则按需升级这些供给。
- "不改上游源码"不变式维持：端侧差异只通过运行期组合（入口脚本垫片）与打包期补丁层表达。
- v2 的原生 UI 成果无需重做；除非新 Web UI/新核心迫使宿主行为变化（如新启动参数），否则不触碰 UI 层。
- 真机与模拟器以当时可用者为准；模拟器验证无法定论的沙箱策略项（link/symlink 类）在报告中如实标注。
- 上周期已勾选的实现任务（T001-T033）保持完成态，不在本周期重做；其验证并入本周期验证阶段。

## Open Questions

- 新版 dsh-web-app/官方前端是否引入必须适配的新宿主要求（新 CLI 参数、新信任模型、新必填配置）？——升级物化后实证，以新版本源码为准。
- 0.1.6-alpha.2 的协议变更幅度未知：若出现破坏性变更，客户端适配范围以"既有功能不回归"为界，不做超前适配。
- ondevice preset 仍禁用 tool-bash/tool-pwsh/tool-fs-search：默认维持现状；若新版核心的工作区文件面板依赖 fs-search 类工具，再评估是否按端侧可行性重新启用。
