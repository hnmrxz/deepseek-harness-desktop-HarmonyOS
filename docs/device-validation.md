本文是**真机验收的唯一台账**。它回答一个问题：**哪些事只能在真机上看、怎么做、看什么算通过。**

> **本项目的基本原则（不可协商）**：没有真机时**允许把功能开发完成**，但**不允许宣称设备验收完成**。

> 未验时一律 `PENDING`）。任何"设备上已好"的表述都必须以本文的实测读数为依据，而不是推断。

## 1. 已知待验收项（**今天就已经具体到可执行**的）

### D1. `undici` 解析钩子在端侧**独立线程**里能否注册

- 背景：`web_fetch` 的修复依赖 `main.js` 的 `installUndiciNameHook()`，它用 `module.register()`
  注册解析钩子，而该钩子运行在 Node 的**独立线程**中。
- 本机已证：PC（aarch64，与设备同架构）上可以。
- 真机要看的：Host 日志里出现 `undici 解析钩子已注册（web_fetch 走本仓垫片，绕开 WASM）`；
  若出现的是 `undici 解析钩子注册失败（web_fetch 将不可用）：…`，说明端侧运行时不支持该机制，
  需要改走 `--experimental-loader` 或换实现。
- 失败时的行为：**只降级、不阻断启动**（web_fetch 坏掉不该拖垮整个 Host），所以**必须靠日志主动确认**，
  不能因为"Host 起来了"就认为它生效了。

### D2. 真机抓一次网页（`web_fetch` 端到端）

- 为什么不能只靠 D1：D1 只证明钩子注册了，不证明抓取成功。
- 步骤：真机上让模型调用一次 `web_fetch` 抓一个**公网**页面（上游只允许公开地址，loopback 会被策略拒绝，这是设计）。
- 期望：返回网页正文（`statusCode 200` + 文本内容），而不是 `WEB_PROVIDER_ERROR`。
- 本机对照基线：`node tools/check-web-fetch-jitless.mjs` 在 B 臂 8/8 通过（真实上游 provider + 真实垫片）。
  该门禁**不能**替代本项——它证的是 PC 上的宿主，不是设备上的运行时。
- 关联：矩阵 §3.2、`docs/50-端侧核心运行架构.md` 的 E263/E264。

### D3. 安装与签名（当前**所有**设备验证的前置阻塞）

- 现状：未签名 HAP（约 138 MB）可完整构建（`CompileArkTS` + `PackageHap` 通过），
  `SignHap` 因缺签名材料而失败。
- 缺什么：`.p12` / `.cer` / `.p7b`（在用户的 Windows 机器上），以及对应的 profile。
- 影响：**没有这一步，上面所有真机项都无法开工。** 这是当前唯一的全局阻塞。

### D4. API 24 与 `Circle().fill(...)` 的兼容性（已知悬案）

- 现象：6 处 `Circle().fill(...)` 被编译器标注 `since SDK 26.0.0`，而我们的
  `compatibleSdkVersion` 固定在 `6.1.1(24)`（用户决定：**暂保持 24**，沉浸光感因此不可用，
  升级路径记在 `HarmonyTheme` 的 `HarmonyMaterial`）。
- 要看的：真机上这 6 处渲染是否正常（是真有风险，还是仅告警）。
- 结论未定前**不要**为了消警而升级 SDK——API 24 是有意决策。

### D5. 输入模态事实链（P3）

四件事都**只能**在真机上确认（本机既无设备也无意指）：

1. **`inputDevice.getDeviceList()` 在设备上可用吗**：SDK 声明里没有 `@permission`（已核 d.ts），
   但真机上是否返回完整列表、是否需要额外系统能力声明，必须实测。
   判据：日志里出现有效枚举结果（而非 `输入设备枚举不可用：<code>`）。
2. **根容器的 `.onHover` 能收到悬停吗**：它挂在页面根 `Stack` 上，而悬停事件是否从子组件冒泡到祖先
   是**平台行为**，不能靠推断。判据：接上鼠标后 `hover` 反馈与右键菜单出现（手机形态下也应有）。
3. **根容器的 `.onKeyEvent` 能收到物理按键吗**：按键走焦点链，根节点能否收到取决于焦点在谁身上。
   判据：外接键盘按任意键后，快捷键提示类交互启用（日志里可见"观察到物理按键"）。
4. **热插拔与降级**：运行中插上鼠标 → hover/右键应**立刻**生效；拔掉后重新枚举应回到"没有指针"
   （枚举是可降级的，与"事件证据只增不减"性质不同——两者都在 `model/InputFacts` 里）。
5. 诊断页应能显示 `modalityNote`（合成理由）；报"设备枚举不可用"时按 1 排查。

### D6. 详情栏拖拽把手与宽度记忆（P3）

三件事只能在真机上判断：

1. **细把手点得中吗**：视觉宽度只有 12vp（它在两栏之间，视觉上应只是一条线），命中区域用
   `responseRegion` 按输入模态放宽到 44vp（触控）/ 24vp（指针）。真机上要确认触控能稳定拖到，
   且**不会误触发**（贴着主内容边缘操作时不应把栏宽拖走）。
2. **拖拽与页面滚动/其他手势冲突**：`PanGesture({direction: Horizontal})` 挂在把手这一列上，
   但它与消息列表的纵向滚动、消息长按菜单在同一片区域。判据：横拖只改栏宽，纵滑仍能滚列表，
   长按仍出菜单。
3. **宽度记忆跨重启/跨形态**：拖宽 → 关应用 → 重开，栏宽应保持；换到窄窗口时栏应被让步链
   自动收窄（而不是撑破布局）。记忆**全局一份**（不按形态分记），这一点若在真机上手感不对，
   再改成按形态分记。落盘失败时应出现一句轻提示（"详情栏宽度这次没能记住"）。

### D7. 平板侧边浅层面板的观感与手势（P3 §12）

双栏（平板竖屏 / 手机横屏 / 2in1 拖窄）下详情改为**压在内容右缘的侧边面板**，判断标准只能靠真机：

1. **层级是否看得清**：本仓不手写遮罩（遮罩由原生 Sheet 提供），故侧边面板**没有蒙层**，
   靠"面板覆盖在内容右缘 + 点面板外关闭"表达层级。真机上要确认用户能一眼看出这是浮层、
   而不是布局变成了三栏。
2. **点面板外关闭是否顺手**：实现是一层**透明**点击层承担"点外面关闭"。判据：点空白处关闭、
   点面板内**不**关闭；且透明层不该让用户觉得"内容点不动了"（它会挡住列表交互——若手感不对，
   需改成非阻断式并重新考虑层级表达）。
3. **面板宽度**：沿用用户记住的"想要的宽度"并夹在可用空间内（`clampDetailDesired`）。
   判据：800vp 平板竖屏上列表仍露出足够宽度（不该出现面板吃掉大半屏）。
4. **档位切换的连续性**：窗口从双栏拖到三栏时，浮层应自动关闭并由右栏承担（已有逻辑）；
   从三栏拖回双栏时，详情不应突然消失（当前是保留右栏的开启意图、由浮层接管——需实测确认）。

### D8. 轨迹时间总览的观感与手势（P2 §11）

轨迹视图上方新增「总计 + 每格比例条 + 拖动聚焦 + 统计四项」，判断标准只能靠真机：

1. **比例条在手机上看得清吗**：格子多、耗时分布悬殊时（例如一次 8 秒的助手回合 + 十几个
   几十毫秒的工具格），最窄的格可能只有一两个像素。判据：是否还能看出"大概有这么多格"，
   以及是否需要给最窄格一个最小宽度。**这是本项最可能需要返工的地方。**
2. **拖动聚焦与列表滚动冲突**：比例条上的 `PanGesture({direction: Horizontal})` 与下方列表的
   纵向滚动、以及条本身的点击（`onClick` 用组件相对坐标换算）要能共存。判据：横拖只换聚焦格、
   纵滑仍滚列表、轻点能聚焦。
3. **聚焦详情是否够用**：目前给「种类 · 第 n/共 m 格 · 开始于 hh:mm · 耗时」。
   判据：不看列表能否凭这一行知道"这是哪一步"；若不够，需要加强联动（见下）。
4. **双向联动的手感**（本轮补上，故需实测）：
   · 条 → 列表：拖动松手或点选后，列表滚到那一格对应的条目并高亮。判据：跳转位置对不对
     （用 `ScrollAlign.START` 对齐首行）、动画是否突兀。
   · 列表 → 条：滚动列表时条上的聚焦跟着**首行**走。判据：是否让人误以为"条在自己动"；
     若观感不好，可改成只在**用户主动滚动后**更新，或干脆去掉这一路（保留条→列表即可）。
   · **最需要盯的是抖动**：两路互相触发时不应来回跳。当前靠"拖条期间关掉列表那一路" +
     "滚到条目的行首使两侧一致"来避免，属**推断**，必须实机确认。另：条→列表当前用
     **立即跳转**（不是平滑滚动）——因为平滑滚动会在动画途中反复触发滚动回调、让聚焦扫过
     中间每一格。真机上若"跳得太硬"，再补"程序化滚动期间挂起列表→条"后换回平滑。

### D9. `@Provide/@Consume` 在真机上的运行时行为（P0 机制）

**为什么必须实测**：本仓有过先例——`@BuilderParam` **编译通过、真机运行时 JS 崩溃**（D4）。
编译器只能证明语法与类型，证明不了"祖先提供、后代消费"在设备运行时真的连得上。

本轮已在**最窄的一条轨道（侧栏）**上用起来：`Index` `@Provide('panelRegistry')`，
`SidebarShell` `@Consume('panelRegistry')` 并按注册表可用性过滤入口。

判据：
1. 侧栏**正常显示三个入口**（说明 `@Consume` 拿到了注册表，而不是拿到 `undefined`）。
2. 把某个侧栏面板的 `available()` 改成 `false`（临时验证）⇒ 该入口**从侧栏消失**，
   其余入口与主区不受影响。若 `@Consume` 没连上，这里会抛错或静默显示全部。
3. 四形态切换、以及"切会话 → 进设置 → 回会话"之后仍正常（消费链不因重建而断）。

**在这一条通过之前，不要把主区的 100 个 `@State` 迁到 `@Provide/@Consume`**——那是全量迁移的前提。

### D10. 浮层门户提到页面根之后：三形态下浮层是否都可达（P0 收尾）

**为什么必须实测**：这是本轮**改了结构、无法在本地跑起来验证**的一处行为变更。
原先 `bindSheet` 只挂在 `buildSingle` 的根 `Column` 上 ⇒ 双栏/三栏下四类浮层（模型选择 / 凭据 / 目录 /
文本与整值设置）**点了没反应**（触发点都在主区内容里，主区三形态都可见）。修法是把门户提到页面根
（`Index.build()` 的根 `Stack`）。编译器只能证明语法，证明不了"提到根上之后 `isShow` 仍被正确驱动"。

判据（**三形态各测一遍**）：
1. **单栏**：会话页 → 模型选择浮层正常弹出、能选中、下拉关闭后**还能再打开**（`closeSheet()` 复位的意义）。
2. **双栏（600–839vp，如平板竖屏/手机横屏）**：主区设置页点「凭据」类条目 ⇒ **浮层弹出**（修好之前这里毫无反应）；
   再回会话页点模型选择 ⇒ 同样弹出。**注意**：双栏下详情走的是侧边浅层面板，不该出现 Sheet。
3. **三栏（≥840vp）**：`Ctrl+J` 翻右栏（不是浮层）；再从主区点凭据/目录 ⇒ 浮层**盖在上方**、关闭后三栏布局不变。
4. 浮层打开时按 `Esc` ⇒ 关闭浮层而**不**停轮次（`escapePressed()` 的顺序语义，见 D3 §5.1 那一节）。
5. 观感：浮层出现的位置/遮罩是否正常（挂在根节点而不是某个轨道节点上，理论上更"居中于窗口"）。

**未过此条之前**：不得宣称"浮层在三形态下都可达"。

### D11. 侧栏里的工作区树（窄版行）与三栏主区那句说明（P1）

**为什么必须实测**：本轮把「工作区→会话」树挂进了侧栏 PANEL 轨道（240vp），并为这个宽度做了窄版行
（第 1 行名字、第 2 行三个动作）；三栏下主区的「工作区」页签改成一句说明。**这些全是布局改动，
本地无法渲染**（无模拟器/设备，且签名材料缺失 = D3）。

判据：
1. 三栏档位：侧栏自上而下应是 品牌 → **工作区树** → 面板入口（工作区/核心/设置）→ 底部二级入口；
   树的滚动条不遮挡文字，长工作区名与长会话名**以省略号收尾而不是换行**。
2. 窄版行第 2 行的三个动作（`+ 会话` / `文件` / `删除`）在触屏上**都点得到**（高度 44vp）；
   「删除」仍是两步（先变「确认删除」并染告警色，再按才删）；只有注册过的工作区才出现该入口。
3. 会话行（宽窄共用）在 240vp 下：名字 1 行省略、`运行中` 徽标与「归档」不重叠。
4. 三栏下主区点「工作区」页签：显示那句说明而不是第二份列表；在侧栏点某工作区的「浏览文件」，
   主区应切到文件浏览（下钻）——**这条是本轮唯一的功能性新增，必须走通**。
5. 单栏 / 双栏的观感应**与本轮之前一致**（本轮没有改动它们的行样式：主区仍是宽版行）。
6. **New Session**（品牌行下方的 `＋ 新建会话`）在触屏上点得到，且与 `Ctrl+N` 行为一致（都走 `createSession()`）。
7. **入口清单与沉底**：侧栏看不到「核心」入口（E110：核心内容在设置页的第一个分区里），
   而「设置」**贴在侧栏底部**（不随清单浮动）；点「工作区」与「设置」各切到对应主区页面并正确高亮。
   进会话后（会话没有侧栏席位）应当**没有任何入口高亮**——若仍高亮"工作区"，说明 `selectedPanelId` 没接到位。

**未过此条之前**：不得宣称"侧栏信息架构已对齐官方"。

### D12. 单栏（手机）侧栏抽屉（P1-5）

**为什么必须实测**：抽屉是本轮**新增的一整层导航面**，本地无法渲染（无模拟器/设备，签名材料缺失 = D3）。
它同时改了返回键阶梯的**第一优先级**——一旦"收不起抽屉"，手机就会卡在一个盖住全屏的面后面。

判据（手机档位，单栏）：
1. 根页（列表页）页头左侧有导航入口（`☰`），点开 ⇒ 抽屉从左滑出/出现，宽度约 240vp，右侧露出底层页面。
2. **四条收起路径都要通**：点抽屉右侧的空白区域、按返回键、在抽屉里选一个面板入口、在抽屉里点一个会话
   （第 3、4 条分别验 `navigateToMain` 与 `enterSession` 的自动收起）。
3. **返回键不得穿透**：抽屉打开时按返回**只**收抽屉（不得同时退栈/退页）；抽屉关着时返回仍是原阶梯。
4. 抽屉里的内容与平板/桌面侧栏**同一份**（品牌 / ＋新建会话 / 工作区树 / 面板入口 / 设置沉底），
   且窄版行的三个动作（`+ 会话` / `文件` / `删除`）在抽屉宽度下都点得到。
5. **已知的过渡状态**：底部标签栏**还在**（本轮刻意不夺走入口）⇒ 手机上会同时存在两块导航面。
   若观感上互相打架，记录现象即可——是否撤掉标签栏等这一条通过后再定。

**未过此条之前**：不得宣称"手机侧栏已与官方对齐"。

### D13. 会话正文的 Markdown 渲染与链接打开（P2-1）

**为什么必须实测**：解析规则已由 fixture 断言（本机可跑），但**画出来是什么样**只能在设备上看：
`Text > Span` 的行内强调要跟着文字流换行、代码块底色与等宽字体、引用条、列表缩进，都属渲染层。
另外链接打开走的是 `openLink`（系统能力），本地无法验证。

判据（发一条含各类标记的消息，或在会话里让助手回一段 Markdown）：
1. **行内**：`**粗**`、`*斜*`、`` `码` ``、`~~删~~` 各就各位；**长粗体在窄栏里正常折行**（不是断成一列碎块）。

**未过此条之前**：不得宣称"侧栏的信息架构已对齐官方"。

### D24. 输入区接管（P7-2，对齐官方 approval / user-questions）

**为什么必须实测**：本地能证明的是"焦点规则正确"（14 条 fixture）与"接线在"（功能接线门禁第 20 项）。
**证明不了**：卡片在输入区上方的观感与触控目标、等宽原始请求在窄屏是否溢出、
以及"用户在会话 A 时不会被会话 B 的审批打扰"这个体感。

判据：
1. 当**当前会话**有审批时，输入区上方出现卡片：**状态带（圆点 + 等待审批）→ 标题（工具 X 请求越权执行）
   → 等宽原始请求 → 选项**；
2. **其它会话的待决不再出现**在这张卡里；若别的会话还有待决，只显示一行提示并可去「待决」页处理；
3. 在会话 A 点"允许一次"，**只影响会话 A**；切到会话 B，（若 B 也有待决）卡片换成 B 的那一条；
4. 提问（`ask_user_question`）同样在输入区接管，标题是**问题正文**，且**不显示**等宽原始请求那一行；
5. 回答/放行后卡片消失（输入区恢复原状），且轨迹里出现对应的处理记录；
6. 窄屏（手机竖屏）下等宽那一行**换行而不横向溢出**。

**未过此条之前**：不得宣称"审批/提问的交互位置已对齐官方"。

### D25. 后台任务的"触发器 + 清单"（P7-3，官方 `dsh-client-ui-jobs` 结构）

**为什么必须实测**：本地能证明的是"结构照官方写了、判定仍在模型里（fixture 40 条）"；
**证明不了**：折叠指示的方向感、点开清单在窄屏的高度、以及 live 耗时是否真的每秒走字。

判据：
1. 会话头只有**一行**：有 live 任务时行首出现**状态点**，文案是「N 个后台任务运行中」；全部结束时文案变「N 个后台任务」且**状态点消失**；
2. 行尾是**折叠指示**（收起时向下、展开时向上）；整行**点得中**（≥44vp），点一次展开、再点收起；
3. 展开后的每行 = 状态点 + **任务类别**（`kind`，与「哪一个」（`label`）分列）+ 状态文案或 detail + 耗时；
4. **live 任务的耗时每秒变化**（`jobsTick` 在跑），全部结束后定时器停（不空转）；
5. 一个任务都没有时，**整段不出现**（会话头不为没用到的能力长控件）；
6. 手机竖屏下长 label 省略号截断而**不换行撑高**。

**未过此条之前**：不得宣称"会话头的后台任务呈现已对齐官方"。

### D26. 轨迹条目的事件详情（P7-4）

**为什么必须实测**：本地能证明"该有哪几行、截断口径与工具卡一致"（16 条 fixture）；
**证明不了**：详情卡在两个挂载点的观感、长值在窄屏的行为、以及"点格子→出详情"的手感。

判据：
1. 在轨迹视图**点时间线的一格** ⇒ 会话头时间线下方出现「事件详情」卡，行是**标签 + 值**（来源/状态/工具调用/参数/结果/耗时…）；
2. 点卡上的「关闭」⇒ 卡片消失（且列表里的聚焦高亮同时清掉）；
3. 点**右栏「轨迹」面板**里的同一格 ⇒ 右栏时间线下方出现同一张卡（**没有**「关闭」，因为右栏焦点常驻）；
4. 空字段**不出现**：一个只有状态的工具条目，详情里就不该有"参数/结果"这种空行；
5. 超长工具结果被截断，并**写明总长**（与工具卡上的截断提示口径一致）；
6. `internal` 的条目（系统提示词等）在「来源」里**显示「· 内部事件」**；
7. 手机竖屏下长值不横向溢出（最多 6 行后省略）。

**未过此条之前**：不得宣称"轨迹视图的 inspect 能力已对齐官方"。

### D27. 提问**整组**（P7-5：这一条修的是"一轮对话卡死"）

**为什么必须实测**：本地能证明"整组投影 + 一次回 + 逐题拦阻文案"（16 条 fixture + 编译）；
**证明不了**：多题卡片的观感、切题时草稿是否真的不丢、以及**真 Host 一次带多题时**这条路的实际效果
（本机 Host 没有模型，问不出多题）。

判据：
1. 当 Agent 一次问**多道题**时，卡片显示「第 n / N 题」，**第一题**的正文与选项；
2. 选一项（或多选若干）⇒ 主键是「下一题」⇒ 点击后**进到下一题**，且**回到上一题时选择还在**；
3. 到**最后一题**时主键变成「提交」⇒ 点击后一次提交**整组**答案，卡片消失；
4. **当前题没答就点主键** ⇒ 出现「请先完成这道问题。」（官方 `error.incomplete`）；
5. **别的题没答就提交** ⇒ 出现「请选择一个选项或填写自定义答案。」（官方 `error.unanswered`）；
6. 「跳过本题」⇒ 该题记为**明确不作答**（空选择）并可继续/提交；提交后 Host 那一轮**能继续**（不再卡死）；
7. 只问一道题时**不显示**「第 1 / 1 题」这种噪音。

**这一条与前几轮的关系**：P7-5 之前，一次多题请求只会显示第一题，**整组答案凑不齐、那一轮永远停在等待**。
过此条之前不得宣称"提问路径可用"。

### D28. 权限预设：有能力能切、没能力说「不可用」（P7-6）

**为什么必须实测**：本地能证明"能力判定 / 文案 / 命令形式"（10 条 fixture）与"本机 Host 三个事实都为空"（核心闭环 M2 段）。
**证明不了**：在**带权限预设的真机 Host** 上点下去是否真的切换成功。

判据：
1. 当 Host **没有**权限预设时（本机就是这种）：输入区的权限 chip 显示「权限：不可用」，**点不动**，
   无障碍文案说清原因（"这台 Host 未提供权限预设…"）；
2. 当 Host **有**权限预设时：chip 显示当前值且**可点** ⇒ 弹出单选列表（当前项标记）⇒ 选另一项后
   执行 `/permission <id>`，回执是「已执行…」或把宿主原因原样带出；
3. 切换后该 chip 的显示值**跟着变**（权限投影 `currentValue` 变化）；
4. 设置 → 通用：若 Host 声明了"新会话默认权限"项，它**自然出现**且可写；未声明时不出现假入口。

**这一条的要点**：在本机 Host 上，第 1 条就是"通过"的形态 —— 不得因为"看不到切换"就判失败。


### D29. 消息图片：引用 → 字节 → 画面（P0-3）

**为什么必须实测**：本地能证明"几何判定"（755 条 fixture 里的单图八种情形 + 官方制品逐字对照）、
"端点存在且假 id 回 `session/attachment-invalid`"（核心闭环 M2e）、以及"投影不再产生 `[image]` 字面"。
**证明不了**：ArkTS 的 `Image()` 吃不吃 `data:image/png;base64,…` 这种长串、大图解码的头帧与内存表现、
以及**真机上是否真的出现了图**（本机 Host 无模型 ⇒ 没有带图的回答回流）。

判据：
1. 一条带图片的消息在**对话视图**与**轨迹视图**里都出现图（两个视图共用 `MessageRow`，形状应当一致）；
2. **单图**按官方几何显示（最大边 240；很小的图**不放大**；极端比例的图不变成一条线或 0 宽高）；
   **多图**显示为 64×64 方图 + 10vp 间距，用户消息靠右、助手消息靠左；
3. 首帧是**同一尺寸的"加载中…"框**（不是先小后大）；读到时**不跳动**；
4. 读取失败时出现「图片加载失败 / 点此重试」，**点一下能重试**；失败文案里带 Host 的原因
   （例如 `session/attachment-invalid` ⇒ "这条会话里没有这个图片附件…"）；
5. 会话切换来回后图片**不串会话**（切到别的会话再切回，图仍在；另开一个会话看不到别的会话的图）；
6. 断开连接（或杀掉 Host）后再连：图片缓存已清空，图会重新读取而不是显示成"曾经读到过"；
7. 时间线 / 搜索命中 / 展开收起等既有交互**没有因此错位**（图片让行变高，虚拟列表与"跳到某条"仍要对得上）。

**这一条的要点**：第 2、3 条在真机上最容易翻车（`data:` URL 的尺寸语义与解码时机），
必须真机截图留证；本机自检的结论**不替代**它。


### D30. 文件变更流不许"自激"（E383）

**为什么必须实测**：本机对真 Host 已经量到过一种自激（订阅 → 一帧 → 重列并重订阅 → …），
**同一秒 367 次** `workspaceFiles/list`；修后同一套步骤是 **2 次**，并已钉成核心闭环第 20 步。
**证明不了**：设备那种"约 5 秒必断、每 2 秒重连"的连接条件下，重连驱动的重订阅会不会
又叠出高频重列（本机的 WS 抖动模式与设备不同）。

判据：
1. 打开工作区/文件页，停留 **5 分钟**不做任何操作：旁路日志（`hdc shell hilog | grep HDSH-TRACE`）
   里 `files changes opened` 的次数应保持个位数，**不得**随时间线性增长；
2. 同一时段内 `workspaceFiles/list` 的请求不应形成突发（可与 Host 侧日志对照；
   若端侧 trace 已被冲掉，本身就是 D30 的失败信号——见 E383c 的教训）；
3. Agent 真的改了工作区文件时，目录**仍然会自动刷新**（修法不能把功能一起修掉：
   这正是 E383"结构修法 + 闸门"两条都要验的原因）；
4. 断网/重连一轮后，自动刷新仍然有效（`onError` 清标记、`onEnd` 不清标记这条区别的作用）；
5. 若出现 `workspaceFiles/changes 触发过频（>10 次/秒）——已暂停自动重列` 这行日志，
   如实记录并**当缺陷报**（它意味着闸门拦下了一次自激，而不是"闸门在工作所以没事"）。


### D31. 输入区发图与图片解码器（P0-4 / E384）

**为什么必须实测**：本机能证明的只有"我们这边的判定与拼装"（788 条 fixture，含官方顺序、
四条类型白名单与魔数嗅探）、"随包的 `sharp` 已是真件"（`--check-sharp` 绿 + 解包核对）与
"这条链路在真 Host 上走到哪一步"（核心闭环 M2f：本机是 SKIP）。**证明不了**的是设备上到底能不能出图
——那个 `.node` 对着 **OHOS libc** 链接，在 glibc 开发机上必然 `invalid ELF header`（已实证）。

**先做第 0 步（不做这一步，后面几条的结论都会指错方向）**：
核心页 →「原生件加载」，或**复制诊断报告**里的「原生件」一行，看 `sharp` 是"可用"还是"不可用 + 原因"。
- 第 0 步的探针已改为**走调度器**（E384j）：它会照真件在 require 时建 soname/RPATH 兼容软链、
  设 `LD_LIBRARY_PATH`，因此**真件可用时这里就会报可用**；若报不可用，原因会分成三类且都能对症：
  `真件加载失败：…`（携带原生层的真实报错）/ `调度器拿到的不是真件（没有 versions）`（桩又回来了）/
  `调度器加载失败：…`。**没有第三类解释时不要**去查"图片格式"。

判据（第 0 步通过之后）：
1. 输入区点「图片」→ 图库可选、返回后在附件条里出现**缩略图**（不是文件名）；
2. 选一张普通手机照片（数 MB）→ 发送 → 会话里这条用户消息**显示图片**；
   助手侧能看到图的内容（例如让它描述图里有什么）；
3. 选一张**超过 12 MiB** 的图：附件条**不入列**，并且提示里写清实际大小与上限（可执行）；
4. 选一张非图片（构造一个改名的文件）→ 被拒且原因说"格式不支持"，**不是**含糊的失败；
5. 离线（断网/停 Host）时发带图的消息：提示明确说"图片不会随队列发送"，
   且**不能**出现"图发了但只有文字到"的静默结果；
6. 发送成功后附件条清空，图片 base64 **不再留在内存**（反复发 10 张大图不出现内存持续上涨）。


### D32. 斜杠命令：命令卡与真实结局（P7-13）

**为什么必须实测**：本机对真 Host 已经量到关键事实（闭环 M2g）：执行 `/feedback`（缺参数）
⇒ 回执 `command.rejected` + 宿主原文，轨迹里出现 1 条已兑现命令条目（`kind=error`）。
**证明不了**的是界面：命令卡在四种形态下的观感、以及"命令在对话里的位置"是否符合直觉。

判据：
1. 在输入区敲 `/`：命令面板列出宿主目录（本机 5 条左右），选中一条只读命令（如 `/help`）执行；
2. **对话里出现一条命令卡**：命令原文（`/name args`）+ 状态徽标（进行中 → 已完成）+ 结局文本
   （若宿主给了文本）；**不是**一条"助手说：…"的气泡；
3. 故意执行一条**缺参数**的命令（如 `/feedback`）：卡片显示 **失败** 徽标，
   并且**显示宿主的原话**（例如 `Feedback text is required. Usage: /feedback <text>`）——
   而不是「已执行」（旧版本就是这句假成功）；
4. 故意执行一条**不存在**的命令（如 `/nope`）：输入区提示「宿主不认识这条命令」，且**输入内容仍在**
   （官方语义：保留输入让用户改）；
5. `/permission <id>` 在**有能力**的 Host 上：命令卡显示已完成，且输入区的权限 chip 跟着变；
6. 连打两条命令：两条各自的卡片都出现（按 `commandId` 配对，不串台、不合并成一条）。



### D33. `@` 引用与 `/` 命令的插入（P7-14）

**为什么必须实测**：本机能证明"替换而不是追加"（22 条 fixture 覆盖识别与替换，含目录引用的
未闭合引号不补空格）。**证明不了**的是真机输入法的实际行为：中文输入法候选栏、光标移动后
的 token 识别、以及"插入后 Host 是否真的把 `@path` 解析成了引用"。

判据：
1. 在草稿中间敲 `@src/fo`（前面有正文）→ 候选弹出 → 选一条：
   输入框里**只**出现 `@src/foo.ts `（**不**残留 `@src/fo`），前面的正文原样保留；
2. 选中一个**目录**：插入的是 `@"dir/`（引号开着）且**没有**尾随空格；
   继续敲字符能在这条目录下继续补全（官方"钻取"路径）；
3. 输入 `/co` → 选 `/compact`：草稿只剩 `/compact `（半截 `/co` 不残留）；
4. 敲了 `/compact ` 之后再敲参数：候选面板**收起**（不在写参数时还弹菜单）；
5. 光标移回中间、在已有 `@xxx` 之后继续敲：不误判为正在输引用（不会弹出面板）；
6. 发出去之后，消息里那条引用**在助手的回答里被当成引用处理**（例如让它读该文件）；
   若 Host 报"引用无法解析"，按缺陷记（我们的插入文本必须与 Host 的 mention 语法一致）。



### D34. 发送失败后的草稿恢复（P7-15）

**为什么必须实测**：本机能证明规则本身（6 条 fixture：成功不还 / 离线已排队不还 /
用户敲了新内容不还 / 原文为空不还）。**证明不了**的是真机上"失败横幅 + 草稿回到输入框"
这两件事同时发生的观感，以及中文输入法下"用户是否算动过输入框"的边界。

判据：
1. 断网（或停 Host）后敲一条长消息按发送：消息进待发队列，输入框**保持为空**
   （提示里说明已排队）——**不得**出现"队列里有 + 输入框里也有"（那会发两遍）；
2. 连上 Host 后故意让发送失败（例如把宿主地址改成一个能连但会拒绝的地址）：
   输入框里**原文回来了**，同时状态条给出失败原因——可以改一改直接重发；
3. 失败后**立刻**先敲了几个字（在原文回来之前）：输入框里的新内容**不被覆盖**；
4. 未选择会话时按发送：不发送、不排队、**草稿留在输入框**，并提示先选会话；
5. 附件（图片/文件）在失败后**仍在附件条里**（与草稿同一批语义：失败不该吞掉用户的输入）。



### D35. 排队项竞态不许报"失败"（P7-16）

**为什么必须实测**：本机能证明判定与文案（11 条 fixture：两个码命中、四个反向不命中、文案不含"失败"）。
**证明不了**的是真机上这些竞态出现的**频率**与界面观感——它们本来就只在"手快"或"轮次刚结束"时出现。

判据：
1. 一条消息正在跑、队列里排了两条：**快速连点两下**第一条的「插话」——
   屏幕**不得**出现「修改待发队列失败」之类的红字（第二次点按撞 `queue-item-not-found` 属正常）；
   旁路日志里应能看到一行 `updateQueue race session/queue-item-not-found：…`；
2. 轮次**刚结束**（回答刚落地）时点「插话」：同样不报错；
   日志里是 `steer-unavailable`，且该消息**仍在队列里**（下一轮会正常发出）；
3. 真的失败仍要报：把连接断开后点「移除」⇒ 必须给出「当前离线，无法修改待发队列。」；
4. 「取回编辑」在竞态下不再提示"移除失败"（文本已经回到输入框，事情已经完成）；
5. 上述第 1、2 条重试若干次，界面状态与 Host 的实际队列**始终一致**（不出现幽灵行）。



### D36. 审批卡只有两选、且不许批准"看不见的操作"（P7-17）

**为什么必须实测**：本机能证明的是"卡片只有两个选项、词汇与官方闭集一致、缺 `toolName` 时走交还链条"（编译期 + 源码对照）。
**证明不了**的是真机上一次真实越权请求到来时，卡片的样子与两条路径的实际结果。

判据：
1. 触发一次需要审批的操作（例如让 agent 执行一条会被沙箱拦下的命令）：
   审批卡上**只有两颗按钮**——「拒绝」与「允许一次」；**没有**任何"始终允许/以后别问了"之类的第三项；
2. 点「允许一次」⇒ 该操作继续，**下一次**同类操作**再次弹卡**（上游无持久授权，行为必须与文案一致）；
3. 点「拒绝」⇒ 操作被拦，助手收到拒绝（不是超时/无人应答）；
4. 卡片上能看到**在批准什么**（工具名 + 原始请求可展开）；若出现一张**说不出工具名**的卡，按缺陷记
   （缺 `toolName` 的请求应当被交还 Host 链条，而不是摆一张可批准的"未知操作"卡）；
5. 危险类操作（写文件/删文件/执行命令）：**主选是「拒绝」**（视觉权重反转仍生效）；
6. 在会话 A 里不得看到会话 B 的审批卡（P7-2 已有判据，一并复验）。



### D37. 模型重试：不许是"出错了 + 一片空白"（P7-18）

**为什么必须实测**：本机能证明文案与投影（10 条 fixture：计数行的四种形态、倒计时的三种状态）。
**证明不了**的是设备上真实重试时的观感：倒计时是否每秒在走、切后台再回来是否还对得上。
（重试在设备上最容易出现——WebSocket 长连接每 5 秒一断是已知条件。）

判据：
1. 制造一次模型请求失败（例如把 Host 侧模型凭据改错，或中途断网）：
   对话里出现**重试行**——「正在重试（第 N/M 次）」+ **约 K 秒后重试**（K 每秒减一）+ 失败原因一行；
   **不得**出现"出错了"加一片空白；
2. 等待结束、下一次请求发出后：倒计时消失，只剩「正在重试」（对应上游 `llm/retry-started`）；
3. `mode: 'always'` 的重试（若 Host 配置成不限次）：文案写「不限次数」，**不**显示 `∞`；
   **不得**编一个上限数字；
4. 切后台 30 秒再回来：倒计时**不能**从头开始（起点是事件时间，不是"页面可见时刻"）；
5. 错误行里**没有**假的「重试」标签（点它没反应的那种）；「查看诊断」仍可用；
6. 重试最终成功时，重试行**不**该留在那里装作还在重试（后续正文/回答到达后的观感一并记录）。



### D38. 目标栏：可操作、且"没有目标"不占位（P7-20）

**为什么必须实测**：本机能证明判定（22 条 fixture：可见性 / 相位动词 / 相位未知 / 受阻 / 读不到与没有目标分开）。
**证明不了**的是真机上 `goals/*` 的**实际可用性**（本机 Host 上没有目标，`goals/get` 也不一定实现）与那一行在窄屏上的排版。

判据：
1. 用 `/goal` 建一个目标 ⇒ 输入区上方出现目标栏：**相位标签（进行中）+ 目标正文**；
2. 点「暂停」⇒ 相位变成 **已暂停**，按钮变成「继续」；再点「继续」⇒ 回到 进行中；
   **失败时不得**显示成已暂停/已继续（写动词不做乐观改）；
3. 点「编辑」⇒ 同一行内出现输入框 + 保存/取消；保存后正文**立刻**变；
4. 点「清除」⇒ 整条栏**消失**（不是留一条空栏）；
5. **没有目标时整条栏不占位**（官方语义）；只有"读不到/形状未识别"时才显示一行说明，
   且那一行不提供任何动词；
6. agent 自己把目标标成完成或受阻时：栏**实时**变化（完成 ⇒ 消失；受阻 ⇒ 显示受阻 + 原因），
   不需要切走再切回来（`goal/change` 事件驱动）；
7. 若这台 Host 的 `goals/*` 未实现：如实显示失败原因（文案见 `model/FailureText.ets`），
   不得静默无反应。



### D39. 回合产出文件行：来源、只算成功、点了真能看到（P7-21）

**为什么必须实测**：本机能证明推导规则（12 条 fixture：三种写类工具、只算成功、去重与顺序、正文不算）
与"点击会读内容并切页"的代码路径。**证明不了**的是真机上这一行在四种形态下的排版，以及
"切到工作区页之后预览真的显示出来"（它依赖 `fileTreeFor` 作用域与 `workspaceFiles/read`）。

判据：
1. 让 agent 改两个文件（一个新建、一个编辑）⇒ 该回合尾部出现一行"本回合写入 2 个文件"，
   两枚 chip 的**名字**是文件名；
2. 点一枚 chip ⇒ 切到文件页并**显示该文件内容**（不是空白、不是"未选择文件"）；
   返回会话页再点另一枚，内容跟着变；
3. 让 agent **只读**文件（`read`）或执行命令 ⇒ **不出现**这一行（读不算产出）；
4. 让一次写入**失败**（例如写只读路径）⇒ 那个文件**不在**清单里（只算成功）；
5. 同一回合先写后改同一个文件 ⇒ 只出现**一枚** chip；
6. 文案里提到的文件名**不影响**清单（只有真实工具调用算）；
7. 超过 6 个文件时：横滑能看到前面的，文案交代总数（"本回合写入 9 个文件（显示前 6 个）"）。



### D40. 返回键层级：真机上只有"一次一层"，且每一步都看得见（P8-1）

**为什么必须实测**：本机能证明的是**决策**（2304 种组合态矩阵：任一组合只产生一个 `BackAction`）与
`Index.consumeBack()` 的执行分支。**证明不了**的是"按下返回后屏幕上真的变了一层"——那取决于
真机的层级呈现（Sheet 收起的动画与状态、抽屉、下钻页的分派），也正是本轮三个缺陷的共同形态：
**代码上动作发生过了，屏幕上什么都没变**。

判据（每一步都必须是"看得见的一层"）：

1. 手机单栏：工作区 → 浏览文件（第 1 层）→ 点开一个文件（第 2 层预览）；
   按系统返回 ⇒ **回到文件树**（不是停在这一层、也不是直接回工作区列表）；再按一次 ⇒ 回工作区列表；
2. 同一个预览页，点页头那枚返回箭头 ⇒ 与系统返回键**完全同一步**（两次操作可互换，结果一致）；
3. 预览打开后按返回，**再等 10 秒**（让 Host 推新事件）⇒ 预览**不得自己回来**（假关闭回归判据：
   预览真值在中枢，视图只清镜像就会复现）；
4. 手机单栏：从列表点进一个会话 ⇒ 按一次系统返回 ⇒ **回到列表**（会话仍在列表里、仍是选中态，
   再点进去内容还在）；**不得**出现"第一次按返回没反应、第二次直接退出应用"；
5. 手机：抽屉打开时按返回 ⇒ 只收抽屉（页面不动）；抽屉 + 浮层同时开着 ⇒ 仍是先收抽屉；
6. 任意浮层（凭据/设置草稿/选择/详情半模态）开着 ⇒ 按返回只关浮层；关掉后**重开同一个浮层**，
   不得带上一次的内容、回执或"写入中"状态（归一化判据）；
7. 多栏（平板/2in1）三栏下，把右栏切到「预览」面板并选中一个文件 ⇒ 按返回：
   记录**实际发生的事**（本端按"并排栏不算层"处理 ⇒ 先退出文件浏览/或交给系统）。
   这一条**是待确认项**（`docs/07` 已登记）：若实测观感是"预览明明在屏幕上，返回却不关它"，
   就要把"该面板此刻是否显示"也纳入 `previewIsLayer()` 的判据；
8. 三栏/双栏：窗口从宽拖到窄（越过断点）后按返回 ⇒ 不出现"按了没反应"（层级在窄档下仍成立）。


### D41. 敏感内容隔离：内部事件在任何出口都读不到（P8-5）

**为什么必须实测**：本机能证明**规则**（内部条目在详情里不产生正文行、出口取值给空串、
Host 原文先脱敏——25 条 fixture + 归真验证），**证明不了**的是"真机上是否还有我们没数到的出口"：
通知栏、系统分享、应用切换器预览、辅助功能朗读、长按菜单都可能在界面上"再显示一遍"。
这些出口**代码里没有**，但只有设备能确认它们确实没被系统接走。

判据：
1. 让 agent 跑一轮（有系统提示词参与），打开时间线 → 点**系统消息**那一格 ⇒
   详情里**没有**任何提示词正文；有且只有"内部事件正文不显示（共 N 字符）…"那一行；
2. 同一格：长按 / 复制 / 引用 / 分享 四处都试一遍 ⇒ 都拿不到正文（详情行可复制的只有结构化事实）；
3. 未识别事件（若本机 Host 上触发得到）：点它的格子 ⇒ 详情里看不到原始 JSON 片段；
4. 让一次请求以 Host 错误收场，且错误里含可疑串（可用一个带 `?token=` 的自建 URL）⇒
   会话错误行里那个 token 显示为 `[已隐藏凭据]`，而**错误原因本身照旧可读**；
5. 复制诊断报告 ⇒ 报告里也不出现该 token；
6. 通知（切后台让 Host 推一条）⇒ 通知正文里没有消息正文与错误原文（既有 D3 §6 政策）；
7. **反向**：普通助手回答的正文在对话、复制、引用三处**照旧可见**（别把安全改动做成功能回退）。
