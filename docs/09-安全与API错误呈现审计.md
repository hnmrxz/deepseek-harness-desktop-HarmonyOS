# 安全与 API 错误呈现审计

日期：2026-09-16  
范围：系统/隐藏提示词、会话投影、搜索、轨迹、复制/引用、诊断日志、API/Host/模型错误及会话窗口提示。

## 1. 结论

当前工程已经有一层重要的防线：`system/message` 被标记为内部事件，`conversationAudienceOf()` 对 `internal` 条目返回 `HIDDEN`，会话可见集合也明确排除 `system/message`；这说明**普通对话气泡层目前不是系统提示词的直接泄露面**。对应 fixture 也明确断言系统角色、内部条目不能进入普通对话。fileciteturn81file0

但当前模型仍然把内部事件保留在 `TrajectoryItem.body` / `trajectoryItems` 中用于诊断，因此安全边界必须从“对话不可见”提升到“任何用户可触达的产品路径都不可见”。尤其需要继续审计轨迹详情、搜索、复制/引用、诊断导出、调试日志、分享/通知等旁路路径。

API 错误方面，当前已经建立专门错误码文案表、重试倒计时与 `lastError` 状态，但**连接错误、请求错误、模型重试、宿主拒绝、参数错误仍存在不同来源汇聚到同一展示层的风险**。会话窗口需要明确区分“这一轮失败”“连接断开”“正在自动重试”“请求被 Host 拒绝”“输入已排队”。

## 2. 系统提示词防泄露

### 2.1 已确认的有效防线

- `system/message` 属于上游事实类型，不进入普通会话可见白名单。
- `TrajectoryItem.internal` 是来源事实标记，不靠正文特征判断。
- `conversationAudienceOf()` 对 `internal` 一律返回 `HIDDEN`。
- fixture 已覆盖：系统角色隐藏、内部条目隐藏、伪装成普通回答的内部条目仍隐藏。
- 对话搜索已经意识到 `system/message.body` 可能是完整 agent 提示词，因此搜索结果不能把内部条目计入对话命中。

这些规则必须继续保持；不能因为“用户看不到”就删除来源标记。fileciteturn74file1 fileciteturn80file0

### 2.2 当前仍需补强的旁路

内部轨迹仍可能保存在状态模型中，因此必须逐一封堵：

1. **轨迹详情**：默认不得展示 `internal=true` 的正文；诊断模式也不能直接渲染完整系统提示词。
   —— **已处理（P8-5）**：这是本轮查出的**真实泄露**。时间线可点，而内部事件也产生格子
   （`system/message` 是 kind=MESSAGE）⇒ 点开「事件详情」就能读到整段系统提示词。
   现在 `model/TrajectoryDetail.trajectoryDetailRows()` 对内部条目**一律不画正文类字段**
   （正文/思考/工具参数/工具结果/错误原文），只留结构化事实（类别/状态/工具名/模型/字符数/耗时），
   并补一行写清"为什么看不见"的说明。判据取自 `Turns.mayExposeBodyToUser()`（来源事实 `internal`），
   与对话可见性同源；fixture 4 条（含"未识别事件原始 JSON 不进详情"）。
2. **复制/引用**：`quoteIntoDraft()`、复制正文、消息操作条必须先检查 `internal`，内部条目不得进入用户草稿。
   —— **已处理（P8-5）**：正文一律经 `Turns.userFacingBodyOf(item)` 取（内部条目给空串）：
   复制在 `TurnView` / `ConversationPane` 两处改为用它，引用在 `Index.quoteIntoDraft()` 用它并给出
   「这条是内部事件…不能引用」的提示。**今天这条路本来走不到内部条目**（对话只渲染可见条目）——
   但按 §2.3「出口必须自带判据」的口径，不能靠"上游调用点恰好没传"。
3. **搜索**：任何会返回可点击结果的搜索接口都必须按 audience 过滤，而不能只在 UI 层隐藏结果。
4. **导出/诊断**：诊断导出只能提供结构化状态、错误码、时间线和必要诊断字段，不得把原始会话事件/系统提示词直接打包给用户。
5. **通知**：后台通知不得携带系统消息正文、隐藏事件正文、工具敏感参数或完整错误堆栈。
6. **日志**：hilog / trace 不得打印系统提示词、token、Authorization、cookie、完整请求头或完整原始 API payload。
   —— **本轮逐行核对，未发现缺陷**：旁路日志（`SessionHub.record()`）只写结构化事实
   （id 前 8/12 位、条数、状态名、错误码、`shape unknown keys=` 的**键名**），没有正文与凭据；
   诊断报告（`Index` 的导出函数）也只有结构化读数 + 旁路日志，并在文案里写明"已剔除凭据与消息内容"。
   这一条**不是**靠门禁保证的（报告是命令式拼接），故在此如实说明取证方式 = 人读了一遍。
7. **附件/工具**：工具参数可能包含内部上下文、密钥引用或系统路径；展示时必须走脱敏/摘要策略。
8. **未知事件兜底**：未知事件不得把原始 JSON 直接当用户消息正文。当前工程已把这一类风险列为内部事件问题，必须持续保持 fail-closed。

### 2.3 安全验收标准

任何包含以下特征的事件：

- `speaker = SYSTEM`
- `internal = true`
- 未知/未确认的上游事件
- 认证、凭据、cookie、token、授权头
- 工具原始参数或内部诊断 payload

均不得进入：

`普通对话 / 搜索结果 / 复制 / 引用草稿 / 用户通知 / 用户导出`。

允许进入开发诊断的数据必须单独定义白名单，并默认脱敏。

## 3. API 错误在会话窗口中的呈现

### 3.1 当前基础能力

当前工程已有：

- `lastError` 状态；
- 46 个上游 RemoteErrorDetailsMap 对应的专门错误文案体系；
- 模型重试条目与倒计时；
- 发送失败后的草稿恢复规则；
- 队列竞态静默收敛；
- 连接层将 `error` 留在 `lastError`，以 WebSocket `close` + 心跳决定连接死亡。

这些能力是对的，但应进一步收敛为**错误来源 → 用户状态 → 操作入口**的一一映射，而不是全部挤到一个“失败提示”里。fileciteturn69file0 fileciteturn70file9

### 3.2 会话窗口必须区分的六类错误/状态

| 来源 | 会话内主提示 | 是否影响会话 | 主操作 |
|---|---|---:|---|
| 连接断开 | “连接已断开” | 是 | 重连 |
| 请求被 Host 拒绝 | “请求未执行” + 人话原因 | 否/取决于请求 | 修改后重试 |
| 模型 API 错误 | “模型请求失败” + 可读原因 | 当前轮失败 | 重试/换模型 |
| 自动重试中 | “正在重试 · 第 n 次 / 倒计时” | 当前轮保持运行态 | 取消/等待 |
| 输入已排队 | “已加入待发队列” | 否 | 查看/撤销 |
| 参数/附件错误 | “本次输入未发送” | 否 | 修改输入 |

禁止把这六类全部写成“操作失败”。

### 3.3 提示位置

会话窗口应优先采用**与失败发生位置一致**的提示：

- 当前轮 API 失败 → 紧贴该轮结束位置的错误行；
- 连接断开 → 会话 Header/状态区域的持久连接状态 + 轻量 banner；
- 自动重试 → 当前轮的 RetryRow；
- 输入参数错误 → Composer 附近，不要滚到顶部；
- 全局 Host 错误 → 全局状态区，但不能遮住输入区和最后一条消息。

错误提示不得覆盖最后一条用户消息、发送按钮或正在编辑的草稿。

### 3.4 错误生命周期

统一采用：

`发生 → 分类 → 投影 → 用户提示 → 操作 → 成功/继续失败 → 清理`

其中“清理”必须明确：

- 新一轮成功后清除旧的 transient error；
- 持久连接问题只有真正恢复连接后才清除；
- retrying 状态不能同时显示成 error + running；
- 同一错误不能因为多个事件重复堆叠多个 banner。

## 4. 敏感错误信息

用户界面不得直接暴露：

- API Key / token / cookie；
- Authorization 请求头；
- 完整 URL 中的 token 参数；
- Node/JS stack trace；
- 本机绝对路径（除非用户主动要求查看路径）；
- 原始 HTTP headers/body；
- 完整系统提示词/隐藏上下文。

技术诊断可以保留错误码与受控摘要，例如：

`模型请求失败 · code=provider/auth-failed · 请检查凭据`

而不是把底层异常对象直接 `.message` 拼到 UI。

## 5. 必须增加的 L0 fixture

1. `system/message` 永远不进入对话、搜索、复制、引用。
2. `internal=true` 即使正文伪装成普通回答也必须隐藏。
3. 未知事件原始 JSON 不得成为用户正文。
   —— **已处理/已核对**：未识别事件只记**类型名**（`unknownTypes`，自证缺口用），不存原始 JSON ；
   它作为 `internal` 条目进轨迹（对话不可见、搜索的对话范围不可见、详情已按第 1 条挡住）。
4. error message 中出现 token / cookie / Authorization 时必须脱敏。
   —— **已处理（P8-5）**：Host 原文进界面前统一过 `Redact.scrubCredentials()`（`FailureText.hostDetail()`
   一处收口，三个调用点共用）；规则本身从 `Notify` 搬进零依赖 `model/Redact.ets`，
   于是它能被 fixture 直接执行（5 种凭据形状 + 脱敏后仍保留证据 + 不误伤普通句子）。
   **仍缺**：诊断报告里的 `traceLines` 未过脱敏（当前核对下来不含凭据，但那是"读出来的结论"，
   不是"门禁保证的结论"）。
5. 模型失败、连接失败、Host 拒绝、参数错误必须得到不同的用户状态。
6. retrying 与 error 不能同时占用冲突状态槽。
7. 新一轮成功后旧 transient error 必须清理。
8. 排队状态不得显示成失败。
9. 失败恢复草稿时不得覆盖用户新输入。
10. 所有错误提示都不得遮挡 Composer 和最后可操作区域。

## 6. L2/L3 必须验证

- API 错误 banner 是否遮挡消息 / Composer；
- 错误出现后滚动位置是否稳定；
- 软键盘出现时错误提示是否覆盖输入区；
- 长错误文案是否被裁切且无法查看完整内容；
- 后台恢复后错误状态是否重复弹出；
- 通知是否泄露错误原文、系统消息或敏感字段。

## 7. DONE 定义

“系统提示词安全”只有同时满足：**对话隐藏、搜索隐藏、复制隐藏、引用隐藏、通知隐藏、导出隐藏、日志脱敏、未知事件 fail-closed** 才能标记 DONE。

“API 错误体验”只有同时满足：**错误分类正确、提示位置正确、文案可操作、不会覆盖内容、不伪成功、不重复堆叠、恢复后清理** 才能标记 DONE。
