# 技术架构与模块

## 1. 总体模型

```text
ArkUI / Entry
    ↓
appstate（状态、投影、纯模型）
    ↓
platform（HarmonyOS 系统能力）
    ↓
HostRuntime / NodeRuntime
    ↓
端侧 dsh Host
    ↓
dshcompat（协议事实）
```

实际调用关系可因模块需要交叉读取，但依赖方向必须保持清晰：UI 不定义协议事实；纯模型不调用系统 API；平台层不持有产品状态。

## 2. 模块职责

| 模块 | 应负责 | 不应负责 |
|---|---|---|
| `entry/` | ArkUI 页面、原生桥、资源、生命周期 | 协议字段的第二份定义 |
| `appstate/` | 会话状态、投影、纯规则、UI 决策 | 直接访问系统 Context |
| `platform/` | 文件、通知、窗口、偏好、系统 API | Agent 业务规则 |
| `hostruntime/` | Node 运行时、核心版本、生命周期 | UI 状态 |
| `dshcompat/` | 端点、事件、协议字段、上游错误码 | 用户文案与视觉 |
| `hostcore/` | Host 入口、fetch/undici 兼容、打包 profile | 端侧 UI |
| `tools/` | 构建、fixture、门禁、打包、合规预检 | 产品运行时状态 |

## 3. 状态原则

唯一状态源必须落在 `appstate`/运行时；视图只消费状态，不自行缓存第二份真相。

多窗口共享一套连接池与会话状态机；窗口实例只保存视图与窗口自身生命周期。任一窗口关闭不得破坏其他窗口。

发送链路遵循：草稿 → 提交 → 成功/已排队/失败。失败时只有“用户没有继续编辑”才允许恢复原稿；已排队不得再次恢复并造成重复发送。

## 4. 协议分层

上游字段、端点、事件类型与错误码全部集中于 `dshcompat`。业务层只通过常量/投影读取，禁止再次散落字面量。

用户可见文案必须与协议码分离。未知错误保留原码与原始信息，同时提供用户可执行的下一步。

## 5. 端侧运行时

Host 使用应用内 Node 运行时。当前运行采用 `jitless`，因此不能依赖 WASM；全局 `fetch` 和 `undici` 模块名解析必须由本项目提供兼容层。该兼容属于运行时基础设施，而不是业务 UI。

核心版本管理必须支持并行安装、健康检查、激活与回滚；新版本不能覆盖唯一可用版本。

## 6. 依赖闭包

新克隆构建前必须具备：Node 头文件、各 ABI 原生库、核心包、Host 入口资源。资源缺失应在预检阶段明确报错，而不是进入 UI 后才失败。

## 7. 架构边界检查

禁止：
- UI 直接调用 `dshcompat` 字面协议之外的端点。
- `appstate` 直接创建系统窗口/Preferences/通知对象。
- 为一个状态再造“视图副本状态”。
- 新增与 `LayoutController` 平行的断点/几何算法。
- 为规避 HarmonyOS 限制而把 Host 改绑到 `0.0.0.0`。
