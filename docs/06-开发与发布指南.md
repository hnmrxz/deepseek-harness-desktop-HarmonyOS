# 开发与发布指南

## 环境

需要 DevEco Command Line Tools、JDK 17、Node.js。Node.js 仅用于仓库脚本；端侧运行使用随包 Node Runtime。本机脚本统一用 `D:\nodejs\node.exe`（v24.19.0；`node` 不在 PATH，勿用系统老 Node 代替）。

核心打包/契约工具的物化树约定：上游源树物化在 `dist/core/work/dsh-core-<version>/`（`node_modules` 在其下）；`tools/protocol-contract.mjs` 用 `DSH_NODE_MODULES` 指向该 `node_modules` 取权威参数表。

## 常用流程

```bash
# ① 端侧 Host 入口脚本：改了 hostcore/app/* 之后**必须**重放 + 校验
node tools/check-host-app-fresh.mjs --fix

devecocli build
node tools/pack-core.mjs --skip-install --place-in-app
```

> **为什么第 ① 步写在这里、而且给了 `--fix`**：2026-09-16 真机验收第一轮就栽在这上面（F9）——
> 改了 `hostcore/app/*` 却忘了 `place-host-app.mjs`，包里的 `main.js` 还是两天前的旧版，
> 表现是**构建绿、设备上没生效**，白跑一整轮。
> 原来门禁红的时候只打印"请再跑另一条命令"，而**"要人记得"正是这个坑能发生的原因**；
> 现在 `--fix` 一条命令把"检查 + 重放 + 复验"合成一件事（不带参数时仍是**只读检查**，
> 门禁在复核场景里不该有副作用）。

先运行仓库已有的门禁/检查脚本，再安装到模拟器或真机。签名材料不进 Git。
本机门禁清单见 [`05-验证与验收.md`](05-验证与验收.md) §1.1；
其中 `check-layout-fixtures.mjs` 需要先设 `DEVECO_CLI_CLT_PATH`（否则**退出码 3 = 没跑成**，不是通过）。

## 资源闭包

新克隆确认以下输入存在：

- `entry/src/main/cpp/node-headers/`
- `entry/libs/<abi>/`
- `entry/src/main/resources/resfile/*.zip`
- `entry/src/main/resources/resfile/resources/app/`

缺失时先修依赖闭包，不要在业务代码里添加临时 fallback 掩盖构建问题。

## 提交规范

一次提交尽量只包含一个明确工作流：例如“协议事实收口”“UI 原生化”“错误恢复”“构建修复”。避免代码、文档、无关格式化同时混入。

提交说明应包含：问题、事实依据、改动边界、验证结果、未验证项。

## 上游升级

升级 dsh 时依次执行：

1. 记录上游 commit / 版本。
2. 更新协议事实与错误码：先跑 `node tools/protocol-contract.mjs`（`DSH_NODE_MODULES` 指向新核心物化树）刷新 `.research/protocol/contracts.json` 基线，再按差集更新 `dshcompat`（`Endpoints.ets` 为自动生成，勿手改）。
3. 搜索新增 `undici` / WASM / 原生模块依赖（0.1.6 新增 `node-addon-require-builtin` 的垫片先例见 `docs/50` §17）。
4. 运行核心闭环 fixture（`check-core-loop.mjs`）。
5. 运行 UI 接线门禁。
6. 检查 API 版本与构建依赖。
7. 在设备上验证 Host、网络、通知、文件、后台。

禁止直接覆盖当前稳定核心；新核心必须 staging → validate → activate。

## 发布

发布前完成：版本号递增、设备类型核对、权限核对、图标/label/入口资源核对、release 构建、签名、安装验证、升级验证、AGC 提审材料准备。

审核说明必须能让审核人员理解如何进入一个可用的 Host/会话状态，避免“安装成功但没有可操作内容”。
