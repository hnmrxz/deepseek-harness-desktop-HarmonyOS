# UI / 交互审计

日期：2026-09-16  
范围：`entry/`、`appstate/` UI、导航、浮层、输入、状态反馈、多形态、页面覆盖与内容裁切。

## 结论

当前 UI 已建立原生化基础，但仍属于“功能密度高、视觉与交互收口不足”的中间状态。主要问题不是缺少组件，而是**状态层次、返回语义、页面进入/退出方式、系统返回、浮层、错误反馈、多形态让步，以及页面可见区域管理没有完全形成统一行为模型**。

本轮静态审计可以确认存在多类**覆盖/显示不全风险**；由于当前远程开发环境没有模拟器/真机，不能把它们全部表述成已发生的像素级缺陷，必须区分“代码结构已证明风险”和“需要 L2/L3 实机确认”。

## P0：返回/关闭语义

### 1. 文件预览的返回优先级存在组合态漏洞
`NavigationController.decideBack()` 当前顺序是“工作区下钻 → 文件预览”。现有 fixture 只覆盖 `wsDrill=0 + previewOpen=true`，因此没有锁住 `wsDrill>0 + previewOpen=true`。

要求：任何仍可见的顶层视觉层必须先关闭，再改变下面页面层级。建议顺序固定为：系统抽屉/Sheet/Choice/Search/详情覆盖层/文件预览/下钻/二级页/首页签/系统退出；并为所有二层以上组合态增加 fixture。

### 2. 返回与显式关闭必须使用同一状态归一化
“返回键关闭”“右上角关闭”“Sheet 下拉关闭”“遮罩关闭”最终必须调用同一状态复位逻辑，不得各自只改一个布尔值。

验收：关闭后不能残留选中项、草稿、详情、预览、搜索条件或焦点。

### 3. 页面返回与系统返回边界必须可见
根层 `EXIT` 是正确的交给系统，而不是页面自己再 push 一个首页。所有需要继续留在应用中的返回动作应被消费；真正根层才交还系统。

## P0：页面覆盖、裁切与可见区域

### 4. “100% 高度”不是“安全区域完整可见”的充分条件
当前多个壳层与 Pane 使用 `.height('100%')`，例如 `AppShell`、`SidebarShell`、`DetailPane`、`FilePreviewPane`、`FileTreePane` 等；这一结构本身不等于已处理状态栏、导航/手势区域、软键盘和动态安全区。静态代码只能确认它们占满父容器，不能证明在真实设备上不会被系统区域或输入法侵入。

**要求**：页面根、滚动内容、固定操作栏、Composer、底部导航和 Sheet 内容必须明确属于“可用内容区”，不得靠 `100%` 让子节点自己碰运气。

### 5. 固定高度/固定宽度组件必须检查窄屏与大字号
仓库中存在固定或半固定尺寸的导航轨道、详情宽度、触控行高度等实现；这些在 2in1 大窗通常安全，但在手机、折叠闭合、分屏、系统字号放大时容易出现：标题被压缩、按钮被挤掉、尾部操作跑出可视区。

**要求**：所有固定宽度容器都要有最小可用宽度与让步顺序；固定高度不能承载不可预测长度文本。

### 6. 文本“省略”不能代替“信息可达”
当前已大量使用 `maxLines + TextOverflow.Ellipsis`，如目标、详情、命令、文件树、工作区、设置项等，这可以防止横向爆框，但也会把真正重要的信息裁掉。

**要求**：
- 标题可以省略，但必须能够进入详情查看完整文本；
- 错误、路径、模型名称等关键诊断信息不能仅靠一行省略；
- 只有纯装饰性/次要摘要允许强制单行；
- 需要区分“视觉截断”和“用户无法获取完整信息”。

### 7. 操作区被内容挤压时不得静默消失
`layoutWeight(1)` + 多个尾部按钮的组合必须验证最小宽度。特别是目标栏、命令行、文件行、设置行、会话 Header、Composer 工具栏，不能出现“正文还在，真正能操作的按钮被挤出屏幕”的状态。

**要求**：操作区优先级高于描述文本；窄屏时优先缩短次级文本、折叠操作或进入菜单，而不是让按钮被裁掉。

### 8. Sheet 内容存在“内容完整但可视高度不一定完整”的风险
工程通过统一 `harmonySheetOptions()` 使用固定级别的 Sheet 高度，并由内部 `Scroll` 承载长内容。这能覆盖常规场景，但仍需验证：键盘出现后 Sheet 是否二次压缩、最后一个按钮是否落在手势区域、动态字体是否导致可视区域不足、拖拽到不同高度后内容是否保持可达。

**要求**：所有 Sheet 必须测试“短内容 / 长内容 / 键盘 / 大字号 / 横屏 / 小窗口”六种情况，并确保首尾操作都能滚动到可见。

### 9. 双栏/三栏覆盖面必须避免“面板覆盖主体但缺少关闭入口”
大屏使用侧边详情面板时，不能只验证面板出现，还要验证：主体最小可视宽度、拖拽后最小宽度、面板关闭入口、窗口缩小后的让步，以及面板内容自身滚动。

**重点验证**：`sidebar width + main width + detail width + resizer` 的总和在窄窗口下不得超过可用宽度；超出时必须按 `LayoutController` 的让步链收缩，而不是靠裁切解决。

## P1：页面层级与导航

1. 一级页签、二级页、详情 Sheet、文件预览、工作区目录下钻必须有明确层级，不允许“视觉像页面、行为像浮层”的混合态。
2. 同一内容不可同时存在两个可见入口却由不同状态源控制。
3. 进入详情后，返回应该回到原上下文，而不是重建会话列表或清空当前选择。
4. 手机使用底部导航/抽屉时，大屏不要强制复用手机的跳转方式。
5. 页签切换不得丢弃正在编辑且尚未提交的内容；若必须清除，必须有明确的提交/取消语义。

## P1：视觉粗糙项

### 首页 / 工作区
- 当前页面层级应更突出“当前工作区 → 当前会话”，避免大量卡片/分组导致视觉重心分散。
- 空态需要提供原因、下一步动作和返回路径，而不是只显示一句说明。
- 列表项的标题、状态、次级信息、操作区必须形成稳定的节奏，避免每个模块自定义间距。

### 会话页
- Header、消息流、轨迹、目标、输入区应形成明显的纵向层次。
- 用户消息、助手消息、系统事件、工具事件不能只靠背景色区分，要有结构层级。
- 长答案、思考、工具调用、错误与重试需要固定视觉槽位，避免内容长度改变整体布局节奏。
- 输入区必须成为“任务终点”：发送、停止、排队、失败恢复、附件、引用建议不能散落在多个位置。

### 设置页
- 设置项按“连接 → 模型 → 凭据 → 核心/插件 → 外观/行为 → 高级/诊断”组织，避免技术实现顺序直接暴露给用户。
- 危险操作必须与普通操作分组，并明确二次确认与结果。
- 只读信息和可编辑字段视觉区分，避免用户误以为可点击。

## P1：状态与反馈

每一个异步操作都必须覆盖：idle / loading / success / empty / disabled / error / retrying（适用时）。

禁止：
- 点击后静默等待；
- 错误只写日志、不在页面反馈；
- 成功后页面没有状态变化；
- “按钮样式”但实际只是 Text；
- 操作已排队却继续保留发送入口导致重复操作；
- 失败恢复时覆盖用户刚刚重新编辑的内容。

## P1：Sheet / Dialog

- `bindSheet` 只用于真正的半模态任务；导航层不得伪装成 Sheet。
- 关闭原因必须可区分：完成、取消、返回、系统关闭、外部状态变化。
- 编辑态关闭前如果有未保存修改，必须有明确的取消/保存策略。
- 同一时刻只允许一个真正的浮层宿主；由状态派生当前浮层类型。

## P1.5：四形态

### 手机
单手热区、底部操作、键盘避让、返回优先级、长列表贴底必须优先于大屏功能密度。必须检查状态栏/手势区域、软键盘、底部导航和 Composer 是否发生互相覆盖。

### 折叠
闭合→展开不得重置导航；展开→闭合要自动让步到单栏，但恢复展开后保留原选择与滚动上下文。半折状态重点检查中缝区域是否遮挡操作或文本。

### 平板
减少 Sheet 数量，更多使用并排详情；主列表应保持稳定宽度，详情承担次级信息。分屏/多窗口后必须重新计算可用宽度。

### 2in1
窗口缩放、hover、右键、快捷键、拖拽与触控必须共同工作；同一操作不能因输入设备不同而产生不同结果。窗口从宽拖到窄时必须验证“隐藏/让步”而不是“裁切”。

## P2：视觉系统收口

- 所有字号、圆角、间距、描边、颜色继续通过 `Tokens/HarmonyTheme/NativePrimitives`。
- 明确层级：页面背景 → 内容面 → 卡片/行 → Sheet → 系统弹窗。
- 所有图标语义统一；避免同一动作出现不同符号。
- 所有“主操作/次操作/危险操作/取消”必须有稳定层级，不按页面临时决定。
- 动效只表达状态变化，不用动画掩盖页面加载或状态不明确。

## P2：文案

错误文案必须回答三件事：发生了什么、是否已经生效、下一步可以做什么。内部错误码只作为诊断信息，不应成为主文案。

## P3：完成度

发布前必须逐页清理：占位文字、无效操作、空白区域、重复标题、过度圆角、无意义卡片、过长说明、隐藏状态、不可解释的图标。

## 覆盖/裁切专项矩阵

| 场景 | 必须验证 | 失败判据 |
|---|---|---|
| 手机竖屏 | 状态栏、Header、Composer、底部导航 | 任一固定操作被系统区域或其它组件盖住 |
| 手机软键盘 | Composer、Sheet、输入触发层 | 键盘遮住输入框/发送键/候选项 |
| 折叠闭合 | 主体与系统手势区 | 文本/按钮落入不可交互区域 |
| 折叠半折 | 中缝两侧内容 | 关键文字或操作跨中缝 |
| 平板分屏 | nav/main/detail 总宽度 | 任一列被裁切或操作区消失 |
| 2in1 缩窗 | 轨道让步链 | 宽度不足时靠裁切而非降级 |
| 动态字体 | 标题、按钮、设置项 | 文本盖住按钮或按钮被挤出 |
| 长路径/错误 | 完整信息可达 | 只剩省略号且无详情入口 |
| 长 Sheet | 首尾动作可达 | 最后一个按钮无法滚动到可见 |

## 静态审计结果

已确认的代码结构风险：

- 多个根 Pane 使用 `height('100%')`，但代码搜索未发现统一的安全区域策略；需要设备验证状态栏/手势区/软键盘是否覆盖内容。
- 多处 `maxLines + Ellipsis` 已正确防止普通文字爆框，但关键诊断/路径/错误场景仍需逐项确认“省略后是否仍可获得完整信息”。
- `layoutWeight(1)` 与固定操作区并用的行需要验证最小宽度，防止窄屏时正文占满后操作被挤出。
- `bindSheet` 有统一高度助手和内部滚动，基础防裁切策略已存在，但键盘/动态字体/横屏等组合态仍属于 L2/L3 验证项。
- AppShell 已将导航、主区、详情和 Resizer 集中管理，但必须验证窗口缩小时总轨道宽度是否始终遵守让步链。

这些项目在没有模拟器/真机的情况下不能被标记为“已复现”，但必须先按风险登记，设备回来后逐条关闭。

## 完成定义

UI 只有同时满足“功能存在 + 状态正确 + 返回正确 + 多形态正确 + 可见区域完整 + 无障碍基本可用 + 无假入口 + 有失败反馈”才可标记 DONE。
