> 本文档于 2026-09-19 由完整版精简为结论摘要；完整过程见 git 历史（本文件压缩前版本）。

现行权威为 `05-验证与验收.md`；协议事实在 `10-协议兼容事实基线.md`（含 §8.7.x 修正链），缺陷与修法在 `13-缺陷编年.md`，端侧运行链路在 `50-端侧核心运行架构.md`，待真机复验项以 `81-待真机复验清单.md` 为准，上游漂移处置见 `40-上游升级手册.md`。POC 各项的目标/步骤/判定定义与进度跟踪表属过程叙述，已删。以下为实测事实、被推翻的归因与实现选型结论。

## 1. 工具与环境事实（实测）

- 本机 `devecocli` **没有** `ui` 子命令（`devecocli ui layout/screenshot` 不存在），`devecocli emulator` 也没有 `fold`；截图用 `hdc shell snapshot_display`，UI 断言用 `hdc shell uitest dumpLayout`。
- API 26 模拟器的 `HostFreeMemMonitor` 要求宿主空闲内存 ≥ 3 GB，不足时启动自行终止；项目纪律：内存不足不启动模拟器。
- `hdc fport` 是宿主→设备方向；设备→宿主用 `rport`（首次用错方向报 `code=2300007`）。
- `hdc rport` 转发会在数秒内失效（3116 被 `CLOSE_WAIT` 占住，3117/3118 同样），宿主侧直连长时间稳定——这是**已知环境限制，不是客户端缺陷**；设备↔宿主长连接验证应改用 hostkit 隧道或真机直连，开发期用 rport 时换新端口号重建。

## 2. 被推翻的归因（教训，均以最终实测为准）

- **`carrier/parse` ≠ 通道问题**：真因是 `checkTarget()` 把 `/api` 当保留 channel 拒掉，导致所有一元 RPC 被守卫拦截；修掉后同一 rport 通道 `session/list` 即通。教训：错误码必须能区分「谁的错」——调用方错误已单列为 `client/endpoint-invalid`，`carrier/parse` 曾同时覆盖「响应解析不了」与「自己拼错 endpoint」两种原因，导致归因建立在猜测上。
- **「$events 开流 27 ms 被关是转发通道问题」是错的**：真因是 ArkTS `WebSocket` 在链路健康时抛 `error code=200 message=undefined` 且**不伴随 `close`**，旧 `RemoteMux` 把它当断线终止全部逻辑流。最终修法：判死只认 `close`（权威信号）+ 库自身心跳，`error` 只记入 `lastError`；中间版「6 s 活性宽限期」也是错的（计时器是连接级的，误杀空闲的 `session/control` 流）。注意后续 `50` 的 E81 表明：在端侧核心场景，`code=200` **就是 WS 升级失败本身**（libwebsockets 把 `Origin` 附加成逗号列表被 fence 判 403）——该结论链以 50 为准。
- **「Host 心跳超时杀长连接」不成立**：心跳阈值约 4–6 s（2 s Ping × `MAX_MISSED_HEARTBEATS=2`，读上游代码确证），实测 27 ms 关闭快两个数量级；「短请求成功、长连接即断」曾指向转发通道，后被上一条推翻。

## 3. 已核实的验收结论（设备/模拟器实测）

- API 26 手机模拟器（`HarmonyOS 7.0.0`）：构建→安装→启动→渲染全链路通过；单栏形态、会话列表、待决聚合页、危险动作权重反转（「拒绝」排第一位）逐条验收通过；宽形态与多窗口因宿主内存限制未验收，不记为通过。
- 设备↔宿主端到端（rport）：token→签名 cookie 认证、mux 物理连接、`session/list` 一元调用通过；4 条真实会话的标题兜底（`title` 实测为 `null` 走 cwd 末段）、副信息、相对时间、状态徽标全部基于真实事实。
- 清桩后复验：未连接空态、失败如实报 degraded、手动重连真的重新认证、工作区文件树真实列出、设置/凭据/插件为真实计数——「没接上」与「正常」在界面上不再一样。
- `workspaceFiles/list` 的根目录必须传 `"."`，传空串被 Host 拒绝（`gateway/bad-request: path is required`）；客户端曾把失败当成空目录显示——「界面说谎」型缺陷，修法详见 `10` §8.7.16。
- 重连链两处缺口已修：`Connection.handleMuxDead` 过去只改状态不驱动重连（现用 `start()` 记下的 `startSink` 重新进入重连循环，策略仍集中在 `ReconnectController`）；`SessionHub` 过去只通过事件流 `onEnd` 感知失败（现 `conn.onStateChange` 把载体事实**映射**到中枢阶段——底层 `CONNECTING` 在中枢是「降级」不是「首次连接中」）。另修：每次 `connect()` 叠加 N 个监听者导致同一降级被处理 N 次。
- POC-3 部分：loopback 下特权方法可达性已证（证据在 `10` §8.4）。POC-10 部分：既有安装（`0.1.2-rc.1`，`dsh web --no-open --port 3111 --host 127.0.0.1`，隔离 `DSH_HOME`）全程零 patch 跑通全部协议实验；「干净上游 checkout 重跑 + 记录 commit SHA」历史待补项。
- POC-1 历史判定口径：设备侧 mux 建立/ready 首帧/5 分钟心跳存活/cancel 未验证前不算通过（当前待验项以 `81` 为准）。

## 4. 实现选型结论（POC-9 凭据安全，已实施）

- `SecretStore` 用 **Asset Store Kit**（`@ohos.security.asset`，HUKS 之上的系统封装）存 token；Host 地址等非敏感项走 `preferences`——分开两个 store 是刻意的，让「哪些字段敏感」在代码结构上成立。
- `Tag.IS_PERSISTENT` 需要 `ohos.permission.STORE_PERSISTENT_DATA`（仅系统应用）：带上会 `201` 且**保存静默失败**。
- 失败时**绝不降级为明文**：失败只影响「下次能否自动重连」，本次连接不受影响。
- `SessionHub.configure(address, name)` 第二参是**显示名，不是 token**，token 从地址串解析；只传裸 baseUrl 会拿空 token 认证，界面报「连接失败（HTTP 0）」，看起来像网络问题。
- 签名 cookie 每次启动重新兑换，不落盘（纳入加密存储为历史待办）。

## 5. 已知限制与设计结论（未被现行文档覆盖）

- 逐条通知按类型路由渠道被 SDK 阻塞：`@ohos.notification` 与 `notificationManager` 的 `SlotType` 枚举不一致，只能先创建三类渠道由用户在系统设置里分别配置，待上游统一后补 `request.slotType`。
- 多窗口启动参数的进程级竞态：`AppStorage` 是进程级的，`dshLaunch*` 四个键不带窗口 id，语义是「最近一次发布的启动参数」；两个窗口几乎同时启动时后发布的覆盖先发布的（新窗口显示上一窗口的会话）。结论：改为每窗口一份（`windowStage.loadContent(path, storage)` 注入 `LocalStorage`，或键名带窗口 id 后缀），**不加锁**——锁只会把竞态变成排队，修不掉归属错误。
- 实测该 Host 用直接 RPC 改设置后**不产生** `settings/document-updated`（事件机制本身正常：建会话即收到 `api-session/added`），故设置页外部改动自动刷新接线正确但本机无法验证。
- 上游基线：`0.1.2-rc.1`（74 端点）→ `0.1.5-rc.1`（84 端点），新增 10 / 移除 0 / 契约变更 1（`commands/execute` 的 `images` → `submittedAttachments`）；`0.1.5-rc.2` 经三层证据确认零协议漂移（描述符逐字节相同），只更新版本矩阵。
