## 0. 验证总则

1. **顺序纪律**：POC-1 是全方案的生死门，未通过前**不得**投入 P1 之后的功能开发；其余可并行。

4. **回写纪律**：任何与 D1/D2 不符的结论，必须在结论落地的同一次提交中修订对应文档。

## POC-1 原生协议往返（**生死门**）

| 项 | 内容 |
|---|---|
| **目标** | 证明 ArkTS 原生客户端能完成 dsh 协议的完整往返：认证 → 一元 RPC → 逻辑流 → 事件流 |
| **为什么是门** | 若原生 ArkTS 无法满足该协议（cookie/WS 心跳/取消/信封校验），整个「原生客户端」架构不成立 |
| **前置** | 可访问的 dsh Host（本机 loopback 或已配对地址）；可部署的最简 ArkTS 工程；`tools/protocol-suite` 的 token 交换能力 |
| **步骤** | 1. 用 `@ohos.net.http` 请求 `GET /?token=<token>`，捕获 `303` 与 `Set-Cookie`；<br>2. 开启 `enableAutoCookie(true)`（或手动管理 cookie），请求任意已确认端点 `POST /api/<endpoint>`，校验 `{type:"server-response", rpcId, result}`；<br>3. 用 `@ohos.net.webSocket` 打开 `wss/ws://<authority>/api/remote.mux`，发送 `{type:"open", streamId, endpoint:"$events", payload:{args:{}}}`；<br>4. 记录帧序列，确认首帧为 `ready`（含 `clientId`、`host.home`），随后收到增量事件；<br>5. 保持连接 ≥ 5 分钟，确认不被 2 s 心跳断开；<br>6. 主动发 `{type:"cancel", streamId}` 并确认流终止 |
| **判定（全部满足）** | ① `303` + cookie 落盘成功；② 至少一次一元调用返回 `ok:true`（用 `session.create` 或等效只读端点）；③ `ready` 首帧到达；④ ≥ 1 条增量事件到达且可解析；⑤ 5 分钟心跳存活（无服务端主动断开）；⑥ `cancel` 生效 |
| **必须记录的抓包事实** | `item` 帧完整字段；`error` 帧完整字段；ArkTS WS 是否自动回 Pong；事件项结构 |
| **失败处置** | **立即评估架构 C**（ArkWeb + 官方 dist + 合法暴露方案），暂停 M2 之后的一切开发，回写 D1 §6.2 与 D2 §7（A-1/A-2/A-5） |
| **产出** | `specs/poc/poc-01-*.md` + `tools/protocol-suite/fixtures/mux/*.jsonl` + `fixtures/events/catalog.md` 首版 |
| **回写** | D2 §1.2、§1.3、§7（A-1/A-2/A-5） |

## POC-2 loopback 直连可行性

| 项 | 内容 |
|---|---|
| **目标** | 确认端侧应用（同机跑 Host 的 2in1/PC 场景）能直连 `127.0.0.1:<port>` |
| **步骤** | 1. 同机启动 dsh Host（默认 `127.0.0.1`，随机端口）；<br>2. 端侧 `http` 请求 loopback 一元端点；<br>3. 端侧 `webSocket` 连接 loopback `/api/remote.mux`；<br>4. 同时用局域网 IP 请求同一 Host（预期被信任栅栏拒绝或 401/403，据实记录） |
| **判定** | HTTP 与 WS 均可达 loopback；且未引入任何 `0.0.0.0` 绑定或 Host/Origin 改写 |
| **失败处置** | 若 loopback 被系统隔离：**只允许**走 L1 隧道（隧道出口回 loopback）。**严禁**绑 `0.0.0.0` 或伪造信任头（D1 §6.4 红线） |
| **产出** | `specs/poc/poc-02-*.md`，含系统版本、结论与失败时的隧道设计草案 |

## POC-4 长连接稳定性与恢复（不重不漏）

| 项 | 内容 |
|---|---|
| **目标** | 弱网、切网、前后台切换各 10 分钟，重连后事件流**不重、不漏** |
| **步骤** | 1. Host 侧记录事件序列（含序号/时间）；<br>2. 端侧订阅 `$events` 并本地落盘收到的序列；<br>3. 依次执行：断 Wi-Fi 60 s → 恢复；切 4G ↔ Wi-Fi；App 切后台 10 分钟 → 回前台；Host 进程重启；<br>4. 每次恢复后按 D2 §3 的退避表核对重试档位；<br>5. 用工具对账两侧序列，输出差异报告 |
| **判定** | ① 重试档位与抖动范围符合 D2 §3；② 对账结果：无重复事件、无缺口；③ 存在缺口时能通过 baseline 补齐到一致；④ `disconnected` 终态后手动重连可恢复 |
| **失败处置** | 修正代次判定与 baseline 补齐策略；若缺口无法从协议层补齐，登记上游缺口（D1 §6.6） |
| **产出** | `specs/poc/poc-04-*.md` + 对账报告（含原始序列样本） |
| **回写** | D2 §3、§7（A-3、A-9） |

| ③ mux 建立、④ ready 首项、⑤ 心跳存活、⑥ cancel | ⏳ **待设备执行** | 依赖 ArkTS `webSocket` 真机行为（是否自动回 Pong、`item`/`error` 帧结构），只能在设备上确认 |

**阻塞条件（未解决，据实记录）**

1. **无真机连接**：`devecocli device list` 报告无活动设备。
2. **模拟器受宿主内存限制**：API 26 镜像（HarmonyOS 7.0.0）与实例均已就绪，但模拟器启动时宿主可用内存约 1 GB，

**解除阻塞的两种方式（择一）**

- 接入一台鸿蒙真机（推荐；同时满足 M8 的真机验收要求）；
- 或释放 ≥3 GB 宿主内存后再启动 API 26 模拟器。

**判定口径**：设备侧 ③④⑤⑥ 未验证前，**POC-1 不通过**，M2 之后的功能开发不启动（本清单的顺序纪律）。
