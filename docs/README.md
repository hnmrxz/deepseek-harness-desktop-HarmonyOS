# 文档总索引

本目录按「先产品、再架构、再计划、最后验证」组织。旧编号文档保留为事实附录或迁移入口，不再作为新的需求源。

## 阅读顺序

1. [`01-产品与功能说明.md`](01-产品与功能说明.md)：产品是什么、为谁服务、做什么、不做什么。
2. [`02-开发计划.md`](02-开发计划.md)：当前阶段与后续实施顺序，适合作为 AI/开发代理的执行入口。
3. [`03-技术架构与模块.md`](03-技术架构与模块.md)：理解代码应该放在哪里，以及哪些边界不能越过。
4. [`04-HarmonyOS多端UI设计规范.md`](04-HarmonyOS多端UI设计规范.md)：手机 / 折叠 / 平板 / 2in1 的 UI 规范与 HarmonyOS 原生化原则。
5. [`05-验证与验收.md`](05-验证与验收.md)：无真机环境如何继续开发，什么时候必须上设备。
6. [`06-开发与发布指南.md`](06-开发与发布指南.md)：构建、检查、调试、发布。
7. [`07-当前状态与缺口.md`](07-当前状态与缺口.md)：项目现状、风险与剩余工作。

## 文档纪律

- 代码事实 > 自动化测试事实 > 上游源码事实 > 文档描述 > 设想。
- 已实现、部分实现、能力边界、待验证必须分开写，禁止把“设计目标”写成“已完成”。
- 每个新增功能必须同时写清：用户价值、协议入口、状态归属、UI 入口、验证方式、失败降级。
- 能用纯模型验证的逻辑不得依赖真机；设备专属行为必须记录真机证据。
- 文档只维护一份权威结论，历史记录保留出处但不再作为第二套规范。
- **README 只放"是什么 / 怎么装 / 怎么读"**：逐轮缺陷记录写进 `13-缺陷编年.md`，状态写进 07，
  能力对等与缺口写进 `parity-matrix.md`——避免 README 越写越长、把入口信息挤掉。
