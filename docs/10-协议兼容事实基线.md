## 1. 载体与端点

### 1.1 一元 RPC（HTTP）

| 项 | 事实 | 来源 |
|---|---|---|
| 方法/路径 | `POST /api/<endpoint>` | 代码 |
| endpoint 构成 | descriptor 的 `namespace` + `method`，以 `/` 连接 | 代码 |
| endpoint 段字符集 | `^[A-Za-z0-9_$.-]+$`，禁止空段、`.`、`..` | 代码（`ENDPOINT_SEGMENT_PATTERN`） |
| channel 约束 | channel 必须匹配 `^/[A-Za-z0-9._~-]+$` 且不得为保留值 `/api`（`/api` 由 Gateway 认领，即 Gateway 服务的 channel、本客户端一元 RPC 使用的 channel） | 代码 |
| 请求头 | `content-type: application/json` | 代码 |
| 请求体 | `{ "type": "client-request", "rpcId": "<uuid>", "method": "<endpoint>", "payload": { "args": { ... } } }` | 代码 |
| 响应体（成功） | `{ "type": "server-response", "rpcId": "<同请求>", "result": { "ok": true, "value": <T> } }` | 代码 |
| 响应体（业务失败） | `{ "type": "server-response", "rpcId": "<同请求>", "result": { "ok": false, "error": { "code": "<string>", "message": "<string>", "details": { ... } } } }` | 代码 |
| 传输失败 | HTTP 非 2xx ⇒ 客户端侧抛 `transport failure for <channel>/<endpoint>: HTTP <status>` | 代码 |
| 信封校验 | `type` 必须为 `server-response`；`rpcId` 必须为字符串且等于请求；`result` 必须为对象；`ok=true` 时 **`value` 键可以不存在**（那是 `void` 端点的合法成功形态，上游有 4 个这样的端点，其中包含审批答复通道 `$events/result`）；`ok=false` 时 `error.code`/`error.message` 为字符串、`error.details` 为对象 | 代码（`parseConnectionResponse`，无 `value` 存在性校验） |
| 取消 | 通过 `AbortSignal` 中止 HTTP 请求；Host 按 descriptor 的 signal 元数据支持取消 | 代码 + 官方文档 |

**待实测**：

- [ ] 未知 endpoint 的响应（预期 404，需确认是否走信封）
- [ ] 超大 payload（图片）时的分块与 `maxRequestBodyBytes` 边界（默认 300 MiB）

### 1.3 事件流（Gateway 内部逻辑流）

| 项 | 事实 | 来源 |
|---|---|---|
| 逻辑端点 | `$events`（`payload = { args: {} }`，`args` 必须是空对象，多一个键即 `gateway/arguments-invalid`） | 代码（`stream-protocol.js`）+ 实测（§8.7.11） |
| 结果回送端点 | `$events/result`（一元），载荷为**扁平** `{ clientId, eventId, outcome }`，**无** `request` 包装层 | 代码（`parseRemoteEventResult`） |
| 首项 | 唯一一个 `{ type: 'ready', clientId, host: { home } }` | 官方文档 |
| 时机 | source factory 在返回 iterable 前**同步**挂好增量 listener，之后才发 ready ⇒ 客户端收到 ready 后发布的 baseline 不会丢增量 | 官方文档 |
| 订阅 | Client 侧 `$on()` 的合法键 = Host 装配声明的转发事件；每订阅归属调用方 fiber；`$events` 投递事件**不需要客户端先订阅**（实测，§8.7.11） | 官方文档 + 实测 |
| 注册时机 | Client Remote 服务激活时即把 `$events` pump 注册为 Connection generation source ⇒ **即使无订阅也会在连接循环启动时打开** | 官方文档 |
| 重放语义 | 普通通知重连后**不重放**；Agent-scoped waterfall 用同一 `eventId` 重放；`clientId` 每次 generation 重新 `randomUUID()`，重连后必变（§8.7.11） | 官方文档 + 实测 |

**已关闭的原待实测项**：事件项结构 → §8.7.7（32 种）；`clientId` 稳定性 → §8.7.11（每代必变）；重连后 baseline 来源 → §8.7.23（`session/follow` 快照 + `session/page` 真实游标）。

## 2. 认证与信任

### 2.1 认证流程

| 步骤 | 事实 | 来源 |
|---|---|---|
| 1 | 进程启动生成**随机启动 token**（每进程一个） | 官方文档 |
| 2 | `dsh web` 打印并打开 `http://<authority>/?token=<token>` | 官方文档 |
| 3 | 仅 `GET /` 接受该 token：校验通过 → 写入**绑定 authority 的签名 cookie** → **303 重定向到干净的 `/`** | 官方文档 |
| 4 | 静态资源保持公开；`/api` 全部方法与全部 WS 流要求同一 cookie | 官方文档 |
| 5 | 缺失/过期/畸形/authority 不匹配的 cookie ⇒ RPC 分发前 **401** | 官方文档 |
| 6 | HTTP 载体**不接受** query token（除根路径交换）与 `Authorization` header token | 官方文档 |

**签名 cookie 属性**：

| 属性 | 值 |
|---|---|
| 密钥 | `ctx.credentials` 中由 `client-connection/browser-session` 拥有的 grant 记录；本地提供方持久化到 `$DSH_HOME/.credentials.yaml` |
| 名称与载荷 | 确定性名称；payload 同时绑定**规范化 hostname 与 port** |
| 绑定 | host-only；`Path=/` |
| 标志 | `HttpOnly`、`SameSite=Strict`；**刻意不设 `Secure`**（载体是 loopback HTTP） |
| 有效期 | 绝对签发/过期区间；`cookieMaxAgeDays` 默认 **30 天** |
| 撤销 | 无 logout 操作；清除客户端 cookie 结束单个会话；删除 owner 凭据记录并重启 dsh 撤销全部会话 |

### 2.2 信任栅栏（`src/api-request-trust.ts`）

| 规则 | 结果 |
|---|---|
| `Host` 为 loopback（`localhost` / IPv6 loopback / `127.0.0.0/8`），或匹配 `trustedHosts` 条目 | 通过 |
| `trustedHosts` 匹配语义：带端口条目按 `host:port` **精确**匹配；不带端口条目匹配**任意端口**；两侧经 WHATWG 归一化 | 通过 |
| 附带 `Origin` 时必须**等于**该 `Host` | 否则 403 |
| `sec-fetch-site: cross-site` | 一律拒绝 |
| 畸形配置 authority | 插件**加载失败** |
| 校验失败 | **403** |
| Host 可信但未认证 | **401** |

> 这些检查**防御 DNS rebinding 与跨站请求，绝不建立身份**——身份由 2.1 的 cookie 承担。

### 2.3 绑定姿态

| 配置 | 行为 | 来源 |
|---|---|---|
| `host` 取值 | 只接受 `127.0.0.1`（默认，仅回环）与 `0.0.0.0`（有意向网络开放；服务器自身**不携带 TLS、认证或来源策略**） | 官方文档（webserver） |
| CLI 姿态 | `dsh web --host 0.0.0.0` **在启动时被拒绝**（安全考虑）；`--trusted-host` 可追加权威 | 官方文档（web-app） |
| LAN 信任采样 | `resolveLanTrust` 启动时采样一次：loopback 绑定不派生 LAN 地址；`0.0.0.0` 绑定加入每个非 internal IPv4 字面量 | 官方文档 |

**结论（本项目的部署红线）**：端侧**永不**依赖 `0.0.0.0` 绑定，也**永不**改写 `Host`/`Origin`。跨设备接入必须让请求在 Host 看来仍来自 loopback（隧道出口回 loopback）或其权威在 `trustedHosts` 中显式登记。

## 3. 连接生命周期

| 状态 | 进入条件 | 来源 |
|---|---|---|
| `connecting` | 浏览器/客户端报告网络可用；或 `reconnect()` 被调用 | 官方文档 |
| `connected` | 收到 `$events` 的 ready 项 | 官方文档 |
| `disconnected`（终态） | 10s 档重试仍失败 | 官方文档 |
| 中断 | `offline` 事件：中断活动工作、发布 `disconnected`、暂停自动尝试 | 官方文档 |
| 恢复 | 下一次 `online`：重置序列，从 **500 ms** 档开始 | 官方文档 |

**退避表（确定性，必须逐档实现）**：

| 档 | 延迟 | 抖动 |
|---|---|---|
| 1 | 500 ms | 50%–100% |
| 2 | 1 s | 50%–100% |
| 3 | 2 s | 50%–100% |
| 4 | 4 s | 50%–100% |
| 5 | 8 s | 50%–100% |
| 6 | 10 s（上限） | 50%–100% |

**generation 失效条件（任一即失效）**：`$events` 结束 / Remote stream error / 收到**非 ready 首项** / 畸形事件项。

**重试前动作**：要求 mux **取消候选或活动 socket**，再重开 `$events`。

**待实测**：
- [ ] 端侧如何在 ArkTS 中获取「网络可用/offline」信号（`@ohos.net.connection` 能力确认）
- [ ] 后台切前后台的连接行为与系统限制（POC-4）

## 5. 备选协议：SDK JSON-RPC（stdio）

| 项 | 事实 | 来源 |
|---|---|---|
| 分帧 | 每个 `\n` 结尾行承载一条 JSON-RPC 2.0 消息 | 官方文档 |
| 帧判别 | 同时含 `id` + `method` ⇒ 请求；仅 `id` ⇒ 响应；仅 `method` ⇒ 通知；格式错误行**忽略** | 官方文档 |
| 错误码 | 无处理器 ⇒ `-32601`；处理器失败 ⇒ `-32603` | 官方文档 |
| 客户端→服务端 | `initialize`（`InitializeParams` → `InitializeResult`）、`session/prompt`（→ 持久入队回执）、`shutdown` | 官方文档 |
| 服务端→客户端 | `session.event`、`session.status`、`subagent.started`、`subagent.finished` | 官方文档 |
| `prompt` 内容块 | 普通内容 + `SdkEncodedImageBlock { type: "image", data, mimeType }`；服务端入队前转成持久引用 | 官方文档 |
| `serverInfo.name` | 固定 `deepseek-harness-sdk-runtime`（协议稳定值） | 官方文档 |
| 无版本协商 | 握手只带 `serverInfo.version`（`0.0.1`），客户端不校验 | 官方文档 |
| 已知限制 | 无取消方法、无会话关闭方法（客户端放弃轮次 = 关进程）；server→client 请求未使用 | 官方文档 |
| 服务端插件 | `@deepseek-ai/dsh-sdk-jsonrpc-server`，应用组合包 `dsh --profile sdk` | 官方文档 |

**本项目用途**：仅 POC-11 与「无 webserver 场景」备选，**不得**作为 v1 主载体（缺少取消/会话关闭，stdio 在移动端更难）。

### 8.2 ArkTS 心跳事实（关闭 A-2）

- `@ohos.net.webSocket` 的 `WebSocketRequestOptions` 提供 `pingInterval`（默认 30s，0 = 关闭）与 `pongTimeout`（默认 30s，须 ≤ `pingInterval`）；SDK **不暴露** `pong()` 之类的控制帧 API。
- 服务端常量（代码级确证，`dsh-api-gateway` 的 `RemoteStreamMuxServer`）：`MAX_MISSED_HEARTBEATS = 2`，配合 `websocketHeartbeatIntervalMs`（默认 2000）⇒ **Host 每 2 s Ping 一次，连续 2 次未收到 Pong（约 4–6 s）主动终止该连接**。
- 实测（§8.7.19）：设备侧 ArkTS 的 `WebSocket` **不回 Pong** ⇒ 长连接约 5–6 s 必被服务端关闭（对照实验：回 Pong 15 s 存活，不回 Pong 5.4 s 被关）。对策：不依赖自动 Pong 也不设客户端心跳选项，靠重连存活——档位用尽后 `reset()` 再按固定 2 s 继续重连并保持 DEGRADED，每次重连用 `session/follow` 的 snapshot 重新同步历史。

### 8.3 mux 帧字段（部分关闭 A-1）

客户端 → 服务端帧字段名：

| 帧 | 字段 |
|---|---|
| 开流 | `type`（值 `"open"`）、`streamId`、`endpoint`、`payload`（形如 `{ args: {...} }`） |
| 取消 | `type`（值 `"cancel"`）、`streamId` |

服务端 → 客户端帧判别与取值：

| 判别 | 取值 |
|---|---|
| 逐项 | `type == "item"` → 业务值在 `value` 字段 |
| 失败 | `type == "error"` → `error.{code,message,details}`（结构待真机抓包确认） |
| 正常结束 | 终止帧 `{type:"end", streamId}`（§8.7.3 修正：**有**终止帧；上层须区分「Host 主动正常结束」与「连接意外断开」，前者不触发重连） |

**上行帧实参字段名必须是 `payload`，不是 `args`**（实测，§8.7.9）：写成 `args` 会被服务端以 `CLOSE code=1008 reason=invalid Remote stream request` 立刻关闭——现象与「心跳超时被断」一样，必须靠 close code/reason 区分。mux open 帧的 `payload` 仍要装 `args`（如 `$events` 要求 `payload:{args:{}}`）。

**未确认**：未知帧类型是否需要回错（本实现选择「忽略，前向兼容」）；单连接最大并发逻辑流数。

#### 8.7.4 审批与提问的完整链路（客户端第一交互）

| 环节 | 事实 | 依据 |
|---|---|---|
| 到达 | 走网关 `$events` 的 **waterfall** 帧：`{type:'waterfall', event, eventId, agentId, request}` | `stream-protocol.d.ts` `RemoteEventInvocationFrame` |

| 审批请求体 | `{agent, toolName, callId?, reason?}`（出网前剥离 `agent`/`signal`） | `dsh-user-approval/lib/types/types.d.ts` |
| 审批结果词汇 | `allowed-once` / `rejected` / `cancelled` / `unavailable`（**无**「始终允许」） | 同上 `ApprovalOutcome` |
| 提问事件名 | `user-questions/request`（`waterfall`） | 白名单 |
| 提问请求体 | `{questions:[{id,question,detail?,header?,options?:[{label,description?}],multiSelect?,intent?}], agent?}` | `dsh-user-questions/lib/types/types.d.ts` |

#### 8.7.6 解析层事实（曾据此修复仓库自身缺陷）

- **`ok=true` 时 `value` 键可以不存在**：上游 4 个 `void` 端点（`credentials/set`、`credentials/unset`、`agentPresets/copy`、`agentPresets/deletePreset`）的成功响应是 `{ok:true}`（无 `value` 键）；其中**包含审批与提问的答复通道 `$events/result`**——网关代码 `return { ok: true, value: undefined }`，`JSON.stringify` 丢弃 `undefined` 键。解析时必须用**键存在性判断**区分「没有 `value` 键」与「`value` 为 null」，否则「用户点了允许、客户端认为调用失败」。
- **`/api` 是 Gateway 服务的 channel，也是本客户端一元 RPC 使用的 channel**：不得被 `checkTarget` 之类的守卫当作「调用方不得使用的保留 channel」拒绝，否则所有一元 RPC 全灭且伪装成载体失败；调用方错误应单列 `client/endpoint-invalid`。
- **端点表的 `params` 必须存线上名（`wire`），不是 TypeScript 形参名（`name`）**：曾因此致 30 个端点参数名错误（所有 Agent 作用域端点记成 `agent`，线上必须发 `agentId`；`workspaceFiles/*` 记成 `workspaceFileScope`，线上是 `workspaceFileScopeId`）。`tools/gen-compat-endpoints.mjs` 与 `tools/compat-drift.mjs` 一律用 `p.wire`。详见 11 号文档 §11.4。

#### 8.7.9 `remote.mux` 上行帧的字段名是 `payload`，不是 `args`（实测）

手工完成 WebSocket 升级直连 `/api/remote.mux` 的探测结果：

| 观察 | 结论 |
|---|---|
| 升级返回 **101**；10 秒窗口内服务端每 2 s 发一次 `ping`、连接**保持** | 握手与**载体本身没问题** |
| 上行 open 帧写成 `{type:'open',streamId,endpoint,args:{}}` → 立刻 `CLOSE code=1008 reason=invalid Remote stream request` | 上行帧的实参字段名**必须是 `payload`** |
| 改成 `payload:{}` 后连接稳定，但收到一帧 `gateway/arguments-invalid`：`forwarded Remote event stream requires an empty args object` | 服务端接受了帧；但 `$events` 要的是**一个空的 `args` 对象**，即 `payload:{args:{}}`（§8.7.11） |

**两个极易写错的点**：① 上行帧字段是 `payload`，写成 `args` 被以 1008 立刻关闭——现象与「心跳没回 Pong 被断」一样（都是快速断开），必须靠服务端 close code/reason 区分，不能凭「断得快」下结论。② mux 的 open 帧与一元 RPC 的包装不同：一元是 `payload:{args:{…}}`，而 open 帧的 `payload` **仍然要装 `args`**。

#### 8.7.10 ArkTS `WebSocket` 的 `error` 事件不是「连接已断」（实测）

设备内部探测（`ws://127.0.0.1:3116/api/remote.mux`，8 s 窗口，有无客户端心跳配置各测一次）：

| 观察 | 数值 |
|---|---|
| 升级成功 | `connected=true` |
| 窗口内是否收到 `close` 事件 | **`closed=false`（从未收到）** |
| `error` 事件到达时间 | **73–198 ms** |
| `error` 内容 | `code=200 message=undefined` |
| 连接是否存活整个观察窗口 | **是**（`closedAt=-1ms`） |
| 有无客户端心跳配置的差异 | **无**（`pingInterval=5000/pongTimeout=4000` 与不带心跳表现一致） |

**结论**：ArkTS 的 `WebSocket` 会在**链路健康**的情况下抛出 `code=200 message=undefined` 的 `error` 事件，且**不伴随 `close`**。`error` ≠ 连接已断；判死只认 WebSocket 层的 `close` 事件（权威信号）或连接级探活（Ping/Pong），**不能用「这条流最近有没有推数据」当判据**（有些流本来就是静默的）。`code=200` 是 WebSocket 库自己的错误码空间，不代表 HTTP 200。

#### 8.7.11 `$events` 的实参与投递行为（实测）

| # | 结论 | 证据 |
|---|---|---|
| 1 | `$events` 的 open 帧实参必须是 **`{args:{}}`**，不是 `{}` | 传 `{}` → `gateway/arguments-invalid`：「forwarded Remote event stream requires an empty args object」；实参错形态时服务端只回一帧 error，**开流调用本身不报错**（表现为「开流成功但收不到任何事件」） |
| 2 | `$events` **确实投递事件**，且**不需要客户端先订阅** | 建一个会话即收到 `emit:api-session/added`（完整会话摘要，含 `projections.values`） |
| 3 | **Host 侧 RPC 写入不触发** `settings/document-updated` / `credentials/reference-updated` | 一次 `settings/mutate` 与一次 `credentials/set`+`unset` 之后，`$events` 在 14 秒窗口内**只收到 `ready`** |
| 4 | 但**直接编辑 Host 的设置文档确实会触发**它 | 在 `$settings.yaml` 里改 `fontSize: 14` → `15` 后立即收到 `emit:"settings/document-updated",args:["ui-theme",9]` |

**ready 帧原文**（外层是 mux `item` 帧）：

```json
{"type":"item","streamId":"observer","value":{"type":"ready",
 "clientId":"40dd3e00-…","host":{"home":"C:\\Users\\aotian"}}}
```

- `host.home` 是**真实 Host 主目录**，`clientId` 是本次连接的会话 id（诊断页应显示两者）。
- **Host 核心包版本在协议面上不存在**：ready 帧只有 `{type:'ready', clientId, host:{home}}`，没有任何版本字段 ⇒ 设备页的「核心包版本」只能显示**未知**，版本判定只能得到 `unverified` 并写明原因，不能拿「受支持版本矩阵」冒充 Host 的版本。
- `session/follow` 在**协议侧完全正常**（同一手工客户端发送与客户端一致的实参形态：开流成功、快照立即到达、连接保持）——设备上的 `follow error carrier/transport send 失败 code=-1` 是客户端侧「socket 已不可用之后仍然发帧」，不是帧形态或服务端问题。

#### 8.7.16 `workspaceFiles/list` 的根目录必须传 `"."`（空串被拒）；Host 版本号协议里读不到（实测）

**事实 1**：请求根写 `"."`，回复的 `path` 仍是 `""`：

```
POST /api/workspaceFiles/list  { workspaceFileScopeId: <sess>, path: "" }
→ 200 {"ok":false,"error":{"code":"gateway/bad-request","message":"path is required"}}

POST /api/workspaceFiles/list  { workspaceFileScopeId: <sess>, path: "." }
→ 200 {"ok":true,"value":{"path":"","entries":[{"name":".git","type":"directory"},
     {"name":"docs","type":"directory"},…],"truncated":false}}
```

1. **请求词法与回复词法不是一回事**：请求根 `"."`，回复 `path` 为 `""`。
2. 这个错误**不会表现为错误**：把失败当空目录时用户看到「该目录暂无文件」，与真相相反——**没有报错，但有错**。
3. 子目录直接传工作区相对路径即可（`path: "docs"` 正常返回 8 个条目）。
4. 客户端把「请求路径」与「子节点路径前缀」拆成两个参数，`WORKSPACE_ROOT_REQUEST_PATH = '.'` 由单测钉住。`workspaceFiles/read` 不需要这个区分（传的是文件路径）。

**事实 2**：见 §8.7.11——Host 版本号协议里读不到。

**结论**：文件端点的作用域是会话级，会话是唯一能提供 `workspaceRoot` 的东西。「工作区」页必须先选定一个 cwd 属于该目录的会话才能列目录；客户端把「文件浏览作用域」与「当前查看的会话」解耦（`SessionHub.openWorkspace`）。

#### 8.7.17 附件链路实测：`fileUploads/upload` 的线上名是 `agentId`；`readAll` 给的就是可上传的 base64（实测）

**① 正确形态（接受）**
```
fileUploads/upload { agentId: <sessionId>, request: { data: <base64>, name: "probe-readme.txt" } }
→ {"ok":true,"value":{"receiptId":"c4cb0e3b-…",
     "file":{"attachmentId":"sha256:4e3e5b3d…","name":"probe-readme.txt","bytes":48}}}
```
`receiptId` 是回执；`file.attachmentId` 是 **`sha256:` 前缀的内容寻址 id**（不是路径、不是带授权的 URL）。

**② 故意写错参数名（拒绝，负向证据）**
```
fileUploads/upload { agent: <sessionId>, request: {...} }
→ {"ok":false,"error":{"code":"gateway/arguments-invalid",
     "message":"typert gateway: fileUploads/upload: args fields do not match the descriptor:
                missing \"agentId\"; unexpected \"agent\"","details":{"endpoint":"fileUploads/upload"}}}
```

**③ 缺 `request`（拒绝）**：`fileUploads/upload { agentId: <sessionId> }` → `gateway/arguments-invalid: missing "request"`。

> **与 `commands/execute` 那条的区别**：`images → submittedAttachments` 是**上游改名**，归 `PARAM_ALIASES` 管（按错误码换旧名重试一次）；本条是**客户端写错**（上游一直叫 `agentId`），**不能**放进别名表——那会把客户端 bug 伪装成上游漂移，永远掩盖真正的改名事件。构造载荷以**生成上表的 `params`（wire 名）** 为准，不以 `.d.ts` 形参名为准。

**④ `workspaceFiles/readAll` 给的就是附件需要的字节**
```
workspaceFiles/readAll { workspaceFileScopeId: <sessionId>, path: "README.md" }
→ {"ok":true,"value":{"absolutePath":"D:\\…\\README.md","version":"…","bytes":19021,
     "offset":0,"data":"<25364 字符 base64>","eof":true}}
```
`data` 可直接作为 `fileUploads/upload.request.data`。「投喂 Host 侧文件」**不需要任何新端点**：读整文件字节 → 上传拿回执 → 放进 `session/prompt.request.content[].type='file'`。（`bytes = 19021` 与 `data.length = 25364` 正是 base64 的 4/3 膨胀。）

**⑤ 收据的生命周期（客户端必须遵守的两条）**：
- 收据是**会话（Agent）作用域**的 ⇒ 切会话必须清空本地待发附件；
- 收据在**成功进入某个 prompt 的收件箱后即被 Host 回收（retire）** ⇒ 发送成功后必须清空本地列表，否则再次发送被判未知回执，而用户以为附件还在。「上传后长期缓存收据、以后再发」不成立。

#### 8.7.19 长连接必断的根因是**心跳**（实测收敛；推翻早先「转发通道是元凶」的归因）

对照实验（唯一变量「客户端回不回 WebSocket Pong」）：

| 客户端行为 | 结果 |
|---|---|
| 回 Pong | 15 s 观察窗内连接**保持** |
| 不回 Pong | 服务端在 **5.4 s** 主动 `CLOSE` |

设备侧把地址换成**完全不经 hdc 转发**的 `10.0.2.2:3115` 后症状一模一样（约 5–6 s 后 `control error carrier/closed`；设备日志里两次成功一元调用之间正好隔 5.3 s）。

**结论**：**服务端心跳是硬要求**（每 2 s Ping，漏两次即 terminate），而设备侧 ArkTS 的 `WebSocket` 不回 Pong（HarmonyOS 官方 FAQ 只承诺「服务器要对客户端的 Ping 回 Pong」，对反向要求只字未提）。归因必须靠「换一条不经转发的通道复现」——换了通道症状不变，所以元凶不是转发通道。

**客户端对策（不改上游）**：① 重连**不进终态**——档位（6 档，末档 10 s）用尽后 `reconnector.reset()` 再按固定 2 s 继续重连并**保持 DEGRADED**（「降级但仍可用」是真话，报终态是说谎）；每次重连用 `session/follow` 的 snapshot 把整段历史重新同步，会话仍可读可发，可见延迟 ≈ 重连周期。注意 `reset()` 不可省——只 `setTimeout` 重新 `schedule` 而不 `reset()` 会让计数器只增不减、永不真正发起连接。② **不设客户端心跳选项**（去掉 `pingInterval/pongTimeout`）：关连接的是服务端，保留只会让「谁关的」更难分辨。

#### 8.7.20 结论：**任务能跑通**（真正的回复已产出）；缺的是凭据，不是链路（定案）

**① Agent 不需要客户端订阅也会跑完整轮**：先发 prompt、完全不订阅，12 秒后再开 `session/follow`，快照里读到完整一轮（`snapshot records=19`：`permission/preset, sandbox/mode, approval/policy, agent/inbox/spliced, turn/start, agent/inbox/spliced, step/start, system/message, user/message ×3, request/header, request/context, session/title, session/title-llm-request, assistant/message, step/end, turn/end`）。⇒ 长连接约 5 秒必断的平台限制**不会丢任务**：Host 照旧算完并落盘，客户端下次重连用 follow 快照重新同步即可看到答案。

**② 之前「什么都没发生」的真正原因是缺模型凭据**：`turn/end` 的 reason 直接写着 `llm-deepseek: no API key for provider route "deepseek-official"; store DEEPSEEK_API_KEY through the credentials service (the web Models page writes it), or export DEEPSEEK_API_KEY`。补上密钥后同一实验产出真实回复（`assistant/message {role:'assistant', content:[{type:'text',text:'HDSH-OK'}], source:{kind:'model',provider:'deepseek-official',model:'deepseek-flash'}}`，整轮 6.2 秒）。⇒ **「能执行任务」= 凭据 + 一次 `session/prompt`（一元）**。

**③ `session/page` 对实时记录恒返回空——不要用它轮询**：三轮实验里 `session/page` 都是 `{records:[], hasMore:false}`，而同一时刻 follow 快照里有 19 条（原因见 §8.7.23：游标必须真实，`-1` 只返回空页）。读会话内容只信 `session/follow` 的快照与增量。

**④ 载体恢复后必须重开 `session/follow`**：`CONNECTED` 时要刷新会话列表并重开当前会话的 follow（同会话但流已断 ⇒ 重开；「清空附件/排队项」限定真的换了会话时才做，否则重连会把用户刚加好的附件悄悄丢掉）。否则一次断线后轨迹永远停在断开那一刻——Host 早算完了而用户看到「发出去了、永远不回」。

**⑤ `requestId` 幂等的第二重含义**：同一 `requestId` 重复提交也返回 `{accepted:true}`（D2b §1.2），因此 `{accepted:true}` 无论如何都不能当作「落地成功」的证据。

#### 8.7.22 「这一轮跑完了」只能靠 `turn/end` 事件判定（实测）

`session/follow` 的快照里**没有 `running`**（形状是 `header/cursor/records/hasMore/projections`，§8.7.2 第 9 条），`projections.values` 里也没有它。**唯一可靠的「轮次结束」信号是 `turn/end` 事件**；失败与否在 `data.reason.kind`。实测失败轮次：

```
turn/end {turn:1, reason:{kind:'error', error:{message:'llm-deepseek: no API key …'}}}
```

判据**只认 `'error'`**：其它取值（含将来新增的）一律按正常完成——把正常完成误报成失败会让用户白查一场。（「某个投影里没有这个字段」本身是一条事实，必须查证并记下来，不能默认它在。）

#### 8.7.23 `session/page` 能读整段历史，但**游标必须真实**；`-1` 不是「到末尾」（实测）

**请求体是 `{address, throughSeq}`，不是 `{sessionId}`**：

```
{ request: { sessionId } }
  → gateway/input-invalid: wire field "request" failed boundary validation
{ request: { address: {kind:'session',sessionId}, throughSeq: -1 } }
  → {ok:true, value:{records:[…], hasMore:false}}
```

`throughSeq` **必填**；少字段的错误码是 `gateway/input-invalid`（读起来像格式问题，必须与「这个会话没有记录」分清：前者是我方 bug，后者是事实）。

`throughSeq` 实测矩阵：

| `throughSeq` | 结果 |
|---|---|
| `-1` | `{ok:true, records:[], hasMore:false}` —— **一条都没有** |
| `0` | 1 条（含 seq 0） |
| `1` | 2 条 |
| `5` | 6 条 |
| `100` | ❌ `gateway/bad-request: session page through seq 100 is past cursor 18` |
| `18`（= `session/list` 的 `projections.asOfSeq`） | **19 条**（整段历史，含 `assistant/message`） |
| `19` | ❌ `past cursor 18` |

三条可直接依赖的结论：

1. **`throughSeq` 是包含式上界**（`0` 就返回第 0 条），超过游标会**明确报错**——错误消息里带着真实游标。
2. **`-1` 不是「到当前末尾」**：照上游类型注释写的读法会得到一页空记录，而空记录与「这个会话是空的」长得一模一样。**上游类型注释里的「特殊取值语义」必须实测。**
3. **游标从 `session/list` 的 `projections.asOfSeq` 取**（实测与上界完全一致）。纯一元客户端的读法：`session/list` → 取该会话的 `asOfSeq` → `session/page{throughSeq:asOfSeq}`。

**`session/page` 的 `records` 与 `session/follow` 快照的 `records` 同形**（都是 `{type:'event', event:{type,seq,time,data}}`），同一条 `projectWireRecord()` 可直接复用——客户端因此有了一条**不依赖长连接**的读历史通路：开流失败/流被终结时按 3 秒节奏读回历史，流一旦开起来就让位。
