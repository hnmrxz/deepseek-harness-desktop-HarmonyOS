## 1. 载体与端点

### 1.1 一元 RPC（HTTP）

| 项 | 事实 | 来源 |
|---|---|---|
| 方法/路径 | `POST /api/<endpoint>` | 代码 |
| endpoint 构成 | descriptor 的 `namespace` + `method`，以 `/` 连接 | 代码 |
| endpoint 段字符集 | `^[A-Za-z0-9_$.-]+$`，禁止空段、`.`、`..` | 代码（`ENDPOINT_SEGMENT_PATTERN`） |
| channel 约束 | channel 必须匹配 `^/[A-Za-z0-9._~-]+$` 且不得为保留值 `/api`（`/api` 由 Gateway 认领） | 代码 |
| 请求头 | `content-type: application/json` | 代码 |
| 请求体 | `{ "type": "client-request", "rpcId": "<uuid>", "method": "<endpoint>", "payload": { "args": { ... } } }` | 代码 |
| 响应体（成功） | `{ "type": "server-response", "rpcId": "<同请求>", "result": { "ok": true, "value": <T> } }` | 代码 |
| 响应体（业务失败） | `{ "type": "server-response", "rpcId": "<同请求>", "result": { "ok": false, "error": { "code": "<string>", "message": "<string>", "details": { ... } } } }` | 代码 |
| 传输失败 | HTTP 非 2xx ⇒ 客户端侧抛 `transport failure for <channel>/<endpoint>: HTTP <status>` | 代码 |
| 信封校验 | `type` 必须为 `server-response`；`rpcId` 必须为字符串且等于请求；`result` 必须为对象；`ok=true` 时 **`value` 键可以不存在**（那是 `void` 端点的合法成功形态，上游有 4 个这样的端点，其中包含审批答复通道 `$events/result`）；`ok=false` 时 `error.code`/`error.message` 为字符串、`error.details` 为对象 | 代码（`parseConnectionResponse`）+ **2026-09-10 修正**（原记录为「`ok=true` 时须有 `value`」，已在 D2 §8.7.6 记录修正经过） |
| 取消 | 通过 `AbortSignal` 中止 HTTP 请求；Host 按 descriptor 的 signal 元数据支持取消 | 代码 + 官方文档 |

**待实测**：

- [ ] 未知 endpoint 的响应（预期 404，需确认是否走信封）
- [ ] 超大 payload（图片）时的分块与 `maxRequestBodyBytes` 边界（默认 300 MiB）

### 1.3 事件流（Gateway 内部逻辑流）

| 项 | 事实 | 来源 |
|---|---|---|
| 逻辑端点 | `$events`（`payload = { args: {} }`） | 代码（`stream-protocol.js`） |
| 结果回送端点 | `$events/result`（一元，用于 waterfall 结果回送），载荷含 `clientId`/`eventId`/`outcome` | 代码 |

## 2. 认证与信任

### 2.1 认证流程

| 步骤 | 事实 | 来源 |
|---|---|---|
| 1 | 进程启动生成**随机启动 token**（每进程一个） | 官方文档 |
| 2 | `dsh web` 打印并打开 `http://<authority>/?token=<token>` | 官方文档 |
| 3 | 仅 `GET /` 接受该 token：校验通过 → 写入**绑定 authority 的签名 cookie** → **303 重定向到干净的 `/`** | 官方文档 |
| 4 | 静态资源保持公开；`/api` 全部方法与全部 WS 流要求同一 cookie | 官方文档 |
| 5 | 缺失/过期/畸形/authority 不匹配的 cookie ⇒ RPC 分发前 **401** | 官方文档 |
| 6 | HTTP 载体**不接受** query token（除根路径交换）与 `Authorization` header token | 官方文档 |

**签名 cookie 属性**：

| 属性 | 值 |
|---|---|
| 密钥 | `ctx.credentials` 中由 `client-connection/browser-session` 拥有的 grant 记录；本地提供方持久化到 `$DSH_HOME/.credentials.yaml` |
| 名称与载荷 | 确定性名称；payload 同时绑定**规范化 hostname 与 port** |
| 绑定 | host-only；`Path=/` |
| 标志 | `HttpOnly`、`SameSite=Strict`；**刻意不设 `Secure`**（载体是 loopback HTTP） |
| 有效期 | 绝对签发/过期区间；`cookieMaxAgeDays` 默认 **30 天** |
| 撤销 | 无 logout 操作；清除客户端 cookie 结束单个会话；删除 owner 凭据记录并重启 dsh 撤销全部会话 |

### 2.2 信任栅栏（`src/api-request-trust.ts`）

| 规则 | 结果 |
|---|---|
| `Host` 为 loopback（`localhost` / IPv6 loopback / `127.0.0.0/8`），或匹配 `trustedHosts` 条目 | 通过 |
| `trustedHosts` 匹配语义：带端口条目按 `host:port` **精确**匹配；不带端口条目匹配**任意端口**；两侧经 WHATWG 归一化 | 通过 |
| 附带 `Origin` 时必须**等于**该 `Host` | 否则 403 |
| `sec-fetch-site: cross-site` | 一律拒绝 |
| 畸形配置 authority | 插件**加载失败** |
| 校验失败 | **403** |
| Host 可信但未认证 | **401** |

> 这些检查**防御 DNS rebinding 与跨站请求，绝不建立身份**——身份由 2.1 的 cookie 承担。

### 2.3 绑定姿态

| 配置 | 行为 | 来源 |
|---|---|---|
| `host` 取值 | 只接受 `127.0.0.1`（默认，仅回环）与 `0.0.0.0`（有意向网络开放；服务器自身**不携带 TLS、认证或来源策略**） | 官方文档（webserver） |
| CLI 姿态 | `dsh web --host 0.0.0.0` **在启动时被拒绝**（安全考虑）；`--trusted-host` 可追加权威 | 官方文档（web-app） |
| LAN 信任采样 | `resolveLanTrust` 启动时采样一次：loopback 绑定不派生 LAN 地址；`0.0.0.0` 绑定加入每个非 internal IPv4 字面量 | 官方文档 |

**结论（本项目的部署红线）**：端侧**永不**依赖 `0.0.0.0` 绑定，也**永不**改写 `Host`/`Origin`。跨设备接入必须让请求在 Host 看来仍来自 loopback（隧道出口回 loopback）或其权威在 `trustedHosts` 中显式登记。

## 3. 连接生命周期

| 状态 | 进入条件 | 来源 |
|---|---|---|
| `connecting` | 浏览器/客户端报告网络可用；或 `reconnect()` 被调用 | 官方文档 |
| `connected` | 收到 `$events` 的 ready 项 | 官方文档 |
| `disconnected`（终态） | 10s 档重试仍失败 | 官方文档 |
| 中断 | `offline` 事件：中断活动工作、发布 `disconnected`、暂停自动尝试 | 官方文档 |
| 恢复 | 下一次 `online`：重置序列，从 **500 ms** 档开始 | 官方文档 |

**退避表（确定性，必须逐档实现）**：

| 档 | 延迟 | 抖动 |
|---|---|---|
| 1 | 500 ms | 50%–100% |
| 2 | 1 s | 50%–100% |
| 3 | 2 s | 50%–100% |
| 4 | 4 s | 50%–100% |
| 5 | 8 s | 50%–100% |
| 6 | 10 s（上限） | 50%–100% |

**generation 失效条件（任一即失效）**：`$events` 结束 / Remote stream error / 收到**非 ready 首项** / 畸形事件项。

**重试前动作**：要求 mux **取消候选或活动 socket**，再重开 `$events`。

**待实测**：
- [ ] 端侧如何在 ArkTS 中获取「网络可用/offline」信号（`@ohos.net.connection` 能力确认）
- [ ] 后台切前后台的连接行为与系统限制（POC-4）

## 5. 备选协议：SDK JSON-RPC（stdio）

| 项 | 事实 | 来源 |
|---|---|---|
| 分帧 | 每个 `\n` 结尾行承载一条 JSON-RPC 2.0 消息 | 官方文档 |
| 帧判别 | 同时含 `id` + `method` ⇒ 请求；仅 `id` ⇒ 响应；仅 `method` ⇒ 通知；格式错误行**忽略** | 官方文档 |
| 错误码 | 无处理器 ⇒ `-32601`；处理器失败 ⇒ `-32603` | 官方文档 |
| 客户端→服务端 | `initialize`（`InitializeParams` → `InitializeResult`）、`session/prompt`（→ 持久入队回执）、`shutdown` | 官方文档 |
| 服务端→客户端 | `session.event`、`session.status`、`subagent.started`、`subagent.finished` | 官方文档 |
| `prompt` 内容块 | 普通内容 + `SdkEncodedImageBlock { type: "image", data, mimeType }`；服务端入队前转成持久引用 | 官方文档 |
| `serverInfo.name` | 固定 `deepseek-harness-sdk-runtime`（协议稳定值） | 官方文档 |
| 无版本协商 | 握手只带 `serverInfo.version`（`0.0.1`），客户端不校验 | 官方文档 |
| 已知限制 | 无取消方法、无会话关闭方法（客户端放弃轮次 = 关进程）；server→client 请求未使用 | 官方文档 |
| 服务端插件 | `@deepseek-ai/dsh-sdk-jsonrpc-server`，应用组合包 `dsh --profile sdk` | 官方文档 |

**本项目用途**：仅 POC-11（端侧 Host 可行性）与「无 webserver 场景」备选。**不得**作为 v1 主载体——它缺少取消/会话关闭，且 stdio 载体在移动端反而更难（需进程内管道）。

## 6. 协议探测工具要求（`tools/protocol-suite`）

### 8.2 ArkTS 心跳对策（关闭 A-2 的设计侧）

**新事实（ArkTS SDK，API 21+）**：`@ohos.net.webSocket` 的 `WebSocketRequestOptions` 提供
`pingInterval`（默认 30s，0 = 关闭）与 `pongTimeout`（默认 30s，须 ≤ `pingInterval`），
即**客户端可主动发起心跳**，但 SDK **不暴露** `pong()` 之类的控制帧 API。

**风险**：Host 每 2s 发 Ping 并「若下一周期前未收到 Pong 则主动终止」。若 ArkTS 客户端不自动回 Pong
（无法在 ArkTS 层验证），连接会在 ~4s 内被 Host 断开。

**本项目对策**：不假设自动 Pong，改为**显式开启客户端双向心跳** `pingInterval=5000ms, pongTimeout=4000ms`。
链路上因此始终存在双向流量；即使对端把「有流量」视为保活，也不会在 2s 判定窗口内被判静默。
该决策已实现于 `connection/src/main/ets/protocol/RemoteMux.ets`，并在 POC-1 步骤⑤以 300s 存活观察做最终判定。

**信任栅栏与认证的实测边界（POC-3 的正面证据）**

| 场景 | 实测 | 对应文档 |
|---|---|---|
| 无 cookie 调 `POST /api/pluginInventory/list` | **401** | ✅ D2 §2.2「Host 可信但未认证 401」 |
| 有有效 cookie，但 `Host` 头伪造为 `192.168.1.50:3111`（非 loopback、未登记 `trustedHosts`） | **403** | ✅ D2 §2.2「Host/Origin 校验失败 403」 |
| 有有效 cookie + 真实 loopback | **200** | ✅ 基线 |
| `credentials/describe`（特权方法）经 loopback | **200** | ✅ 特权方法在 L0 路径可达 |

> **对 §6.4（设备接入与安全设计）的直接支撑**：该实验证明「伪造 `Host` 头」这条路**必然 403**——
> 这正是社区方案需要打 patch 才能绕过的围栏。本项目的 L1/L2 走**隧道出口回 loopback**，
> 因此无需伪造任何头即可满足该围栏；反之，任何试图直接连 Host 对外地址的做法都会被 403 拒绝。

**由此确立的三条实现纪律**

1. **404 与业务失败必须分开处理**：404 意味着「该 endpoint 在本 Host 上不存在」⇒ 上层应做**能力探测与入口置灰**（D1 7.9.2），而不是当作网络错误重试。
2. **错误码前缀是分层信号**：`gateway/*` = 调用契约错误（我方 bug，不应重试）；其他前缀 = 域内业务结果（应呈现给用户）。`Connection.call` 的 `RemoteFailure.code` 因此必须原样保留。
3. **参数包装名必须逐端点查描述符**：`session/list` 用 **`_request`**（带下划线），其余多数用 `request`，还有多个是扁平具名参数（`refs` / `id` / `namespace` 等）。**禁止按方法名猜参数形状**——这是本项目 v1 枚举阶段踩到的真实错误（首版假设 `workspace/list` 存在，实测 404）。

#### 8.7.3 对 §8.3 / §8.4 的事实修正

| 原记录 | 修正后 | 依据 |
|---|---|---|
| §8.3：「正常结束即流结束（**无终止帧**）」 | **有终止帧**：`{type:"end", streamId}` | 上游 `dsh-api-gateway/lib/types/stream-protocol.d.ts` 的 `RemoteStreamServerMessage` 三态：`item` / `error` / **`end`** |
| §8.4：「流式端点走一元 → `gateway/signature-invalid`」 | **取决于参数是否先通过校验**：参数不合规时为 `gateway/input-invalid`（`session/follow` 实测）；参数合规后才由 `invoke()` 抛 `gateway/signature-invalid` | 上游 `index.js`：先 `prepareInvocation` 校验参数，再判 `descriptor.mode === 'stream'` |
| §1.3：`$events/result` 未记录参数形态 | **扁平** `{clientId, eventId, outcome}`，**无** `request` 包装层 | 上游 `parseRemoteEventResult(payload.args)` |

> **「`end` 帧」为什么重要**：漏处理它不会立刻报错（上游随后也会关闭逻辑流），
> 但会让上层无法区分「Host 主动正常结束」与「连接意外断开」——前者不该触发重连，
> 后者必须触发。已据此修正 `connection` 的 `RemoteMux`（`end` 帧 → `sink.onEnd()`，
> 与 `error` 分支分开）。

#### 8.7.4 审批与提问的完整链路（本次补齐，客户端第一交互）

此前只知道「有待决事项」，本次拿到**到达路径**与**答复路径**的完整契约：

| 环节 | 事实 | 依据 |
|---|---|---|
| 到达 | 走网关 `$events` 的 **waterfall** 帧：`{type:'waterfall', event, eventId, agentId, request}` | `stream-protocol.d.ts` `RemoteEventInvocationFrame` |
| 审批事件名 | `approval/request`（转发模式 `waterfall`） | `dsh-api-remotes/lib/types/remote-events.d.ts` 白名单 |
| 审批请求体 | `{agent, toolName, callId?, reason?}` | `dsh-user-approval/lib/types/types.d.ts` |
| 审批结果词汇 | `allowed-once` / `rejected` / `cancelled` / `unavailable`（**无**「始终允许」） | 同上 `ApprovalOutcome` |
| 提问事件名 | `user-questions/request`（`waterfall`） | 白名单 |
| 提问请求体 | `{questions:[{id,question,detail?,header?,options?:[{label,description?}],multiSelect?,intent?}], agent?}` | `dsh-user-questions/lib/types/types.d.ts` |
| 提问答案体 | `{answers:[{id, selected:string[], custom?}]}` | 同上 |
| 答复通道 | 一元 RPC `$events/result`，args = `{clientId, eventId, outcome}`；`outcome` 为 `{kind:'next'}` \| `{kind:'result', value}` \| `{kind:'rejected', error}` | `stream-protocol.d.ts` `RemoteEventResult` |
| 「我不处理」 | 回 `{kind:'next'}`，把请求**交还** Host 的应答者链条 | `TypertRemoteEventOutcome` |

> **纪律**：`{kind:'next'}` 是我们处理**未知 waterfall 事件**的唯一正当回应。
> 回一个空 `result` 会让 Host 认为已有人应答，从而**永久丢掉这次审批**。
> 白名单共 19 条事件，其中只有 2 条是 `waterfall`，其余 17 条是单向 `emit`——
> 完整白名单已落为 `dshcompat.FORWARDED_EVENTS`（可直接用于升级时逐条比对）。

#### 8.7.6 本次整合中发现并修正的**仓库自身缺陷**（不是上游变化）

这些不是上游改了什么，而是**我们自己的工具与解析层错了**。它们共同的特征是：
编译通过、运行时也不报错，只在特定调用路径上静默给出错误结论。

| # | 缺陷 | 症状 | 修正 | 为什么长期没被发现 |
|---|---|---|---|---|
| 1 | 端点上表的 `params` 存的是上游 **TypeScript 形参名**（`name`），不是**线上名**（`wire`） | **30 个端点**的参数名是错的：所有 Agent 作用域端点记成 `agent`（线上必须发 `agentId`），`workspaceFiles/*` 记成 `workspaceFileScope`（线上 `workspaceFileScopeId`） | `tools/gen-compat-endpoints.mjs` 与 `tools/compat-drift.mjs` 一律改用 `p.wire`（含 `shapeOf` 的包装名判定）；重新生成上表 | 仓库里**没有任何代码读上表的 `params`**（`buildArgs` 只按 `shape` 装配），所以错值从未被使用过——纯粹是「等着将来有人用」的陷阱 |
| 2 | `connection/Envelope.ets` 要求 `ok:true` 响应**必须**带 `value` 字段 | 上游 **4 个 `void` 端点**的成功响应是 `{ok:true}`（没有 `value` 键，`JSON.stringify` 丢弃 `undefined`），会被解析层判为「畸形响应」而失败。**其中包含审批与提问的答复通道 `$events/result`**——即「用户点了允许、客户端认为调用失败」 | 新增 `rpcOkVoid()`；解析时**先用键存在性判断**再取值（区分「没有 value 键」与「有 value 键但值为 null」） | 之前的实测只覆盖了有返回值的只读端点，而 `$events/result` 需要真实审批才能触发，设备未到位就一直没跑到 |
| 3 | `connection/RpcTypes.checkTarget()` 把 `/api` 当成「被 Gateway 保留、调用方不得使用」的 channel **拒绝**它 | 而 `Connection.call()` 正是用 `surface.apiChannel`（= `/api`）调它 → **每一次一元 RPC 全被守卫拦下**，返回 `carrier/parse`（伪装成网络问题）。会话列表 / 发送提示词 / 取消轮次 / **审批答复**全都是死的；只有认证（直连 `HttpClient`）与流（走 `RemoteMux`）是活的 | `checkTarget` 不再拒绝 `/api`（它就是 Gateway 服务的 channel，也是本客户端唯一使用的）；调用方错误单列 `client/endpoint-invalid`，**不再伪装成载体失败** | 认证与流都不经过该守卫，「能认证、能开流」造成了「连接正常」的错觉。单元测试里那条 `checkTarget(API_CHANNEL, 'session/list').ok === true` **一直在指着它**，但旁边一条自相矛盾的 `it('rejects the reserved /api channel')`（`API_CHANNEL` 就是 `/api`）把错误行为写成了预期——两条测试不可能同时通过，直到**把测试真正跑起来**才暴露 |

> 缺陷 2 的上游代码实证：网关对 `$events/result` 的成功分支直接写
> `return { ok: true, value: undefined };`（`dsh-api-gateway/lib/types/index.js`）。
> 这是**权威证据**，不是推断。

**一次被推翻的「推翻」（方法论教训，值得留档）**

升级过程中有一位复核者提出：先前记录的「`commands/execute` 的 `images` → `submittedAttachments`
是破坏性线上改名」属于**假阳性**。**该结论本身是错的**，错因比结论更值得记住：

- 它拿**已提交上表里的 `name`**（受缺陷 1 影响，存的是形参名）去比**契约里的 `wire`**——
  两个字段不对等；
- 而这个端点上 `name` 与 `wire` **恰好同名**，于是比对看起来是「两边都是新名」，
  实则只证明了「新版的 name 等于新版的 wire」。

两端 `wire` 直接比对的结果（证据）：

| 版本 | `commands/execute` 的 params（`wire<-name`） | kind | cancellable |
|---|---|---|---|
| `0.1.2-rc.1` | `[agentId<-agent, line<-line, images<-images]` | `direct` | `true` |
| `0.1.5-rc.1` | `[agentId<-agent, line<-line, submittedAttachments<-submittedAttachments]` | `direct` | `true` |

**结论：这是真实的线上改名**，先前的 `PARAM_ALIASES` 条目是对的，予以保留。

**教训**：跨来源比对必须先确认两边取的是**同一个字段**。否则会得到一个看起来很有说服力的
错误结论——**比没有结论更危险**，因为它会让人主动删掉正确的防护。

#### 8.7.7 门禁升级：`tools/arch-check.mjs`

原先 CI 里用一条 `grep -rnE "session/|settings/|..."` 检查「上游接口细节是否泄漏出 `dshcompat`」。
它有两个致命问题，本次一并修掉：

1. **命中注释**——说明性文档里写端点名是必要的，于是门禁长期一片红，人开始忽略它（门禁失效）；
2. **无法自检**——没人能证明那条正则真的会命中，还是写错了永远不命中。

现在改为 `tools/arch-check.mjs`：

- 用**懂字符串的状态机**剥掉注释后再生效匹配（朴素地找 `//` 会剥掉 `'http://…'` 的后半行，
  从而**漏掉真正的违规**——自检里专门有一条样例守这个）；
- 只匹配**字符串字面量内部**的 `ns/method`，避免把除法运算误判成端点名；
- 内置 `--self-test`：8 个正/负样例（含注释、块注释、URL、除法、双引号、正确导入写法），
  证明检测器真的会命中。

```sh
node tools/arch-check.mjs --self-test   # 证明门禁有效
node tools/arch-check.mjs               # 期望：无违规，exit 0
```
