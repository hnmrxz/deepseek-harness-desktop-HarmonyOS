## 2. 权限清单（最小化：**2 项**）

| 权限 | 等级 | 用途 | 代码证据 |
|---|---|---|---|
| `ohos.permission.INTERNET` | normal | 连本机 `127.0.0.1` 上的 Host、以及用户显式配置的远端 Host | `HttpClient`（`http.request`）、`RemoteMux`（WebSocket）、`NodeRuntime`（就绪探活） |
| `ohos.permission.KEEP_BACKGROUND_RUNNING` | normal | 长任务后台继续（`DATA_TRANSFER`），否则切后台即被冻结 | `KeepAlive.ets`（`startBackgroundRunning` / `stopBackgroundRunning`） |

已删除 `GET_NETWORK_INFO`（全仓无 `getDefaultNet/hasDefaultNet/getNetCapabilities` 调用点，"离线"判据来自中枢状态；理由串一并删除）。刻意不申请：`READ_PASTEBOARD`（粘贴走系统文本域菜单，见 parity-matrix `hdsh-clipboard`）、公共存储/媒体（文件只在沙箱；选文件走 `DocumentViewPicker` 单次授权）、`GET_WIFI_INFO`、位置、通讯录、相机（附件走系统选择器）。

## 3. 数据与网络（隐私姿态）

| 问题 | 事实（代码可核实） |
|---|---|
| 遥测/埋点/崩溃上报 | **没有**；无第三方统计 SDK、无外部上报路径；诊断报告只在用户点"复制"时进剪贴板 |
| 数据发到哪里 | ① 本机回环 `127.0.0.1:<port>` 上的 Host（**只绑回环，绝不 `0.0.0.0`**）；② 用户在「连接」页**显式填写**的远端 Host |
| 设备标识 | **不收集**（无 ODID/AAID/序列号读取；`InputDevices` 的 `getDeviceInfoSync(deviceId)` 是输入设备编号，无 `@permission`，不落盘不外发） |
| 会话内容 | 只落应用沙箱（`filesDir` / `DSH_HOME`）；诊断导出**显式剔除凭据与消息内容**（`Index.exportDiagnostics`） |
| 凭据 | 客户端不落明文（写入走中枢/Host 侧）；`CredentialSheet` 明文只在一次请求内存在 |
| 剪贴板 | 只**写**（复制消息/诊断报告）；读已按 E370 删除 |

### 3b. 应用内隐私说明（P7-11）与门禁对账

设置 → 设备 → 隐私与权限说明（折叠块）：数据做法 6 条（不收集个人信息 / 只在本机沙箱 / 网络只连两处 / 不读设备标识 / 剪贴板只写不读 / 导出剔除敏感项）+ 申请的权限 2 项逐条用途 + 版本日期 `v1.0（2026-09-15）`（AGC 那份以此为基准，改一侧必须同步另一侧）。
第 10 道门禁 `tools/check-compliance.mjs`：① `module.json5` 的 `requestPermissions` 与 `PrivacyDisclosure.PERMISSION_DISCLOSURES` **完全一致**（多一项少一项都红）；② 12 项**刻意不申请**权限的禁用清单（读剪贴板/位置/相机/麦克风/通讯录/日历/媒体/健康/Wi-Fi/跨设备同步…）出现即红——要加就得先改这张表（改产品原则的有意识决定）；③ 界面出口必须真实渲染。归真验证：塞 `READ_PASTEBOARD` ⇒ 两条红；还原 ⇒ 绿。AGC 侧仍需填隐私政策文本与"个人信息收集清单"（可如实写"不收集个人信息"）及数据安全声明；应用内那份是它的摘要。

## 4. 受限能力自查（上架红线）

| 红线 | 本项目 |
|---|---|
| 动态下发并执行代码 | **不做**：Node 运行时与 dsh 核心树**随 HAP 打包**（`libnode.so.127` + `dsh-core-*.zip`），运行随包内容；插件安装（上游 `pnpm` 路径）**明确不做**（鸿蒙不允许创建进程） |
| JIT / ACL 等受限权限 | **不申请**：统一按 `--jitless` 运行（`docs/50` §4.4），设计前提而非妥协 |
| 后台保活滥用 | 只在有长任务时 `startBackgroundRunning(DATA_TRANSFER)`，任务结束即 `stopBackgroundRunning` |
| 常驻通知 | 无 |

## 5. 体积（已知取舍，登记备查）

release HAP 实测 **270 MB / 74 文件**：`libnode.so.127` 115 MB + `dsh-core-rc.2` 67 MB（旧版）+ `dsh-core-rc.3` 67 MB（当前版）+ 其余 ~21 MB（libvips/rsvg/glib/koffi 等原生件 + modules.abc + 资源）。**两个核心版本是刻意的**：端侧没有下载通道，"切回上一版"必须本机就有那一版（`BundledCore.installBundledCores` 逐个落地）；若要压体积，先确认"保留上一版"这个能力要不要（不要就去掉旧版并同步删回滚入口），而不是"顺手删一个 zip"。x86_64 仅 1.3 MB（模拟器用），不做 ABI 分流。

## 6. 发布构建与签名

### 6.0 出包：`node tools/build-release.mjs`（`--check` 只体检不构建）

做三件事：① 先体检签名材料（`.p12`/`.cer`/`.p7b` 不在本机就先说清"会产未签名包 + 上架前还差什么"）；② 用正确环境变量（CLT / `DEVECO_SDK_HOME` / `JAVA_HOME`）跑 `hvigorw assembleHap -p buildMode=release`；③ 报告产物：签名状态、体积 Top、**可疑内容**（sourcemap/测试包/源码）。本机实跑（2026-09-15）：三个签名文件不在本机（在开发机 `C:\Users\hnzy1\.ohos\config\`），构建停在 `SignHap`（`Invalid storeFile value`），产 `entry-default-unsigned.hap` 269.7 MB，可疑内容**无** ⇒ 除签名材料外链路已通，且包里没有不该发出去的东西。

### 6.1 release 打包链路（本轮修通）

六个模块补齐 `obfuscation-rules.txt`（`platform`/`hostruntime` 原先声明了却缺文件 ⇒ 只有 release 会红），内容统一为"**混淆保持关闭**"：协议层按字符串字段名读上游 JSON（`getString(value,'sessionId')`），开混淆前必须 `-keep-property-name` 列出全部 wire 字段名并用 `check-core-loop.mjs` 回归。**6.3 混淆**：当前关闭（`enable: false`），理由与开启前提同上；上架不要求混淆。

### 6.2 仍然缺的：release 签名

`build-profile.json5` 的 `signingConfigs` 是 **DevEco 调试证书**（`keyAlias: "debugKey"`），三个文件（`.p12`/`.cer`/`.p7b`）都在开发机 `C:\Users\hnzy1\.ohos\config\` 下 ⇒ 本机与 CI 都无法签名。上架需要（**必须在 AGC + DevEco 完成**）：

1. 在 AGC 创建应用，生成**发布证书**（`.cer`）与**发布 Profile**（`.p7b`），下载 `.p12`（密钥库口令另存）；
2. 在 DevEco 的 `Project Structure → Signing Configs` 新建 **release** 配置指向它们（**不要把调试证书用于上架包**）；
3. 建议**不要把签名配置提交进仓库**：口令字段虽经 DevEco 加密（换机即失效），发布密钥库一旦入库就是事故；可行做法见 §7。

### 6.4 提交步骤（照抄即可，P7-12）

**第 0 步 仓库侧自检（本机）**：`node tools/check-compliance.mjs`（权限对账 + 包元数据/资源预检，必须绿）；`node tools/build-release.mjs --check`（应报"缺三个文件"）；`node tools/check-arkts-entry.mjs`（0 error）。
**第 1 步 AGC 建应用**：应用名称 `HDSH`（与 `AppScope` 的 `app_name` 一致，改名要同步资源）；包名 `com.hnmrxz.hdsh`（不可改，与 `app.json5` 逐字一致）；分类工具/效率；支持设备手机+平板+PC/2in1（与 `deviceTypes` 一致，门禁核对）；版本 `1000000`/`1.0.0`（每次提交递增）；隐私政策=应用内「设置→设备→隐私与权限说明」文本（单一真值 `PrivacyDisclosure.ets`）；权限说明两项（`INTERNET` 连你指定的 Host、`KEEP_BACKGROUND_RUNNING` 长任务后台继续）与 §2 表格逐字一致（门禁强制）。
**第 2 步 生成发布签名材料（AGC + DevEco）**：AGC → 证书管理 → 新建发布证书（`.cer`）→ 按提示生成 `.p12`（口令另存）；AGC → Profile 管理 → 新建发布 Profile（`.p7b`）绑定证书与包名；DevEco → Signing Configs → 新建 release 配置指向三个文件；**不把发布材料提交进仓库**（§6.2/§7）。
**第 3 步 出包（本机，1–2 分钟）**：`node tools/build-release.mjs`。确认做对了：报告签名状态=**已签名**（非 `SignHap` 失败）；产物 `entry-default-signed.hap`；`可疑内容：无`。
**第 4 步 AGC 提交材料**：已签名 HAP（**不要**用 `-unsigned.hap`）；商店图标 216×216 PNG（另备，包内分层图标是 1024×1024）；截图手机/平板/PC 三形态各 3–5 张（覆盖会话、工具卡、设置、图片消息）；描述/更新说明（说清"本机优先、不动你的数据"）；测试账号/复现说明**必须**（写清如何得到可连的 Host，或提供演示 Host 与令牌）。
**第 5 步 真机验收留证（可与提审并行）**：`device-validation.md` 的 D 系列是"声称可用"的证据；上架前至少做 D1–D5 与 D29–D31（安装启动、连接、发消息、看图、发图、图片解码器状态）。

## 7. 仓库卫生（登记待决策，未擅自改动）

`signingConfigs` 目前把 `certpath`/`profile`/`storeFile`/口令写进受版本控制文件：路径开发机专属（换机即无效）；发布密钥若照此办理就会入库。二选一：① 文件只放调试配置，发布签名在 DevEco 另建（提交前确认口令字段替换为占位）；② `signingConfigs` 移到本地不追踪文件（DevEco 支持多份 build-profile 片段）。改动会直接影响使用者本机调试安装，故不擅动。

## 8. 编译告警的定性（P8-7，提审前跑一次 `devecocli build` 逐条核对）

- `connection` 模块 6 处 `INTERNET` / `KeepAlive` 的 `KEEP_BACKGROUND_RUNNING` 权限告警：**良性**（库模块级）——权限由 **HAP** 声明，`entry/src/main/module.json5` 已声明并由门禁与「应用内隐私说明」逐项对账；HAR 里再声明反而错误（不生效且造成两处真值）；
- `Local dependencies detected during har packing of module dshcompat`：**良性**——本仓从不安装 HAR（HAP 从源码构建），本地依赖是设计；
- `'getContext' / 'encode' has been deprecated`：**已修（P8-7）**——调用方传上下文 / `encodeIntoUint8Array`；`currentWindowId()` 零调用点删除；
- `Function may throw exceptions`（`CoreStore` 三处 `accessSync`）：**已修（P8-7）**——统一走 `FileProbe.fileExists()`；仓库级反面规则禁止直接使用 `accessSync`。
