## 1. 审批语义与上游能力的偏离（v1.1，实测驱动，仍有效）

- 上游 `0.1.5-rc.1` 的审批结果词表是封闭四值 `allowed-once | rejected | cancelled | unavailable`（`dsh-user-approval` 的 `ApprovalOutcome`），**没有**「始终允许/记住这次选择」；真正的免问只能改 Host 侧 `approval/policy`（`ask` ↔ `never`），那是环境配置，不是一次审批答复能表达的。
- 客户端按最保守方式处理（已实现并逐字注释）：「按策略允许」降级为**纯客户端**的「本会话内同类不再打扰」；发往 Host 的 outcome 仍是 `allowed-once`——绝不伪造上游不认识的词；`decisionIsClientSideOnly(decision)` 供 UI 如实告知作用域。
- 更诚实的替代方案是直接去掉该按钮（只留「拒绝 / 仅本次允许」，与上游能力一一对应）；若保留，文案必须写明「仅在本设备有效，Host 仍会逐次询问」。
- 审批卡其余仍有效规则：涉及删除/外发/凭据的危险动作，主按钮改为**拒绝**（视觉权重反转）并显示风险等级；拒绝可附理由回传 Host；同一审批三处可达（会话轨迹内、待决聚合页、系统通知直达）；超时或已被其他端处理时卡片置为「已由其他端处理」，不静默消失。

## 2. ArkUI 响应式陷阱（2026-09-11 实测，实现纪律）

共同特征：数据完全正确、界面显示旧值，且不报错、不告警。

1. **条件渲染各分支结构相同时会被复用**：`if/else` 分支只是文案不同时，必须用三元表达式写一个 `Text`；只有各分支结构确实不同才用条件渲染。
2. **`ForEach` 的 key 必须覆盖该行的全部渲染输入**（本项目凭据行用 `ref|configured|writable|interactive|source`）；只用「业务主键」在数据可变时会得到静默的旧界面。
3. **ArkUI 只在它「看得见的」表达式上建立依赖**：`@Builder` 内联表达式调用 struct 方法不可靠（方法体内部读的字段不被追踪），同文件模块级纯函数正常——`@Builder` 里的取值逻辑优先写成模块级纯函数。
4. 排查方法（可复用）：怀疑「数据对了但界面没变」时，在 `@Builder` 里临时加一行 `Text` 把组件实际收到的字段值打到界面上，先把「数据链路」与「渲染」切成两半再查。

## 3. 断点与让步（04 未细化的实现约定）

- 硬规则：顶层形态只用**窗口**断点；可复用小部件内部的自适应只用**容器**断点（`ContainerReader`，API 26 起）；混用会导致分屏/多窗场景破版。
- 让步链：详情栏收窄 → 详情栏关闭 → 导航栏收为 56vp 图标条 → 导航栏抽屉化。让步只改几何不改数据，重新变宽自行恢复（不把 store 中的宽度当渲染真值）；详情栏关闭不保留占位；挤压重排期间禁止滚动锁定。

## 4. 仍有效的量化口径（05 未含具体数值）

- 冷启动到可交互 ≤ 1.5 s（P50）；1000 项列表滑动 ≥ 55 fps；会话切换 ≤ 200 ms 显示首屏；流式增量呈现 ≤ 150 ms；长会话（500+ 事件）滚动 ≥ 55 fps；折叠态切换无可见白屏、重排 ≤ 1 帧；通知点击到卡片可操作 ≤ 800 ms；内存 ≤ 150 MB（典型会话），> 250 MB 触发告警日志。
- 大输出策略：工具结果 > 8 KB 只显示首 2 KB + 「查看完整输出」（打开全屏文本视图，支持搜索与复制），避免长会话卡顿。
