## 0. 一句话更正

> **HDSH 不是「PC 上 dsh 的遥控器」。HDSH 本体就是 DSH 的运行载体：应用内自带 DSH 核心运行能力，
> 在自己这一端把 Host 跑起来，客户端页面（ArkUI 原生页面）讲的是本地 Host 的协议；
> 并支持插件的增删启停与核心版本的安装 / 切换 / 回滚。**

原方案（远程客户端）保留为**一种可选接入方式**（连接别人的 Host），但**不再是产品目标**，
也不再是验收口径。凡是「必须有另一台机器在跑 dsh」才成立的功能，都不能算完成。

## 1. 不变式（设计的硬边界）

1. **零上游 patch**：不 fork、不魔改 dsh 业务代码；端侧差异只走 dsh 自己的组合面（profile / `cordis.patch.yml` / bundle）。
2. **不打洞**：默认只监听 `127.0.0.1`；不绑 `0.0.0.0`、不伪造 `Host`/`Origin`。端侧 Host 与端侧客户端同进程，**这两条本来就自然满足**——这是本架构相对社区的 Electron-on-鸿蒙方案的结构性优势。
3. **状态与代码分离**：`$DSH_HOME`（会话/设置/凭据/工作区注册）在应用沙箱里**只有一份**，跨核心版本共享；核心代码树按版本各存一份。升级核心不得动用户数据。
4. **能力降级而非崩溃**：dsh 的 `boot()` 是 **fail-loud**（任一插件行挂载失败 → 进程 `exit(1)`），所以端侧必须用 profile 精确控制「哪些行启用」，而不是指望它自己降级。
5. **界面不说谎**：核心没起来、版本不匹配、插件装失败，页面必须如实说明并给出下一步动作（沿用 D3 §4 纪律）。
6. **上架优先：不申请任何特殊权限**（2026-09-12 新增）。不用 JIT 类 ACL 权限、不用需特批的能力；
   运行时统一以 **jitless** 方式工作，权限面只保留普通权限（网络 = `ohos.permission.INTERNET`）。
   **任何"靠申请特殊权限才能成立"的方案都不进入本项目的选型**（详见 §4.4）。

## 2. 目标架构

```
┌─ HDSH（HAP / APP）────────────────────────────────────────────────────────┐
│  UI 层（ArkUI 原生页面，一多自适应）        ← 「客户端页面」                │
│    └ 复用现有 9 个视图 + 三形态导航（手机/折叠屏/平板/2in1）               │
├──────────────────────────────────────────────────────────────────────────┤
│  状态层 appstate（SessionHub 单一连接与会话状态中枢）                      │
├──────────────────────────────────────────────────────────────────────────┤
│  协议层 connection + dshcompat（84 端点 / 4 流，漂移门禁保护）              │
├──────────────────────────────────────────────────────────────────────────┤
│  ★ 新增：端侧核心运行层 hostruntime                                       │
│    ├ DshHost      核心生命周期：准备 → 起 → 健康检查 → ready → 停/重启     │
│    ├ CoreStore    多版本核心仓库：解包 → 校验 → 激活 → 回滚（§6）          │
│    ├ Profiles     端侧 profile / bundle（哪些 dsh 行启用，§5）             │
│    ├ Plugins      插件清单与增删启停（§6.2）                              │
│    └ Runtime      运行时载体：libnode.so / NAPI 引导（§4）                │
├──────────────────────────────────────────────────────────────────────────┤
│  设备能力层 platform（通知 / 长时任务 / 剪贴板 / 分享 / 窗口 / 密钥存储）    │
└──────────────────────────────────────────────────────────────────────────┘
        │ 进程内 loopback：HTTP POST /api/<endpoint> + WS /api/remote.mux
        ▼
┌─ 端侧 dsh Host（Node 运行时，跑在本应用进程内的线程上）───────────────────┐
│  webserver(127.0.0.1:port) ├ /api ├ /api/remote.mux ├ $events            │
│  dsh 本体：agent / 工具 / 会话持久化 / 投影 / 设置 / 凭据 / 插件清单       │
│  DSH_HOME = <应用沙箱>/dsh/home（跨版本共享，唯一一份用户数据）           │
└──────────────────────────────────────────────────────────────────────────┘
```

**为什么是同进程（而不是 HNP 子进程）**：设备之间/进程之间的 loopback 在鸿蒙 NEXT 上可能被隔离
（社区 Electron 方案必须绑 `0.0.0.0` + 改写 `Host` 头来绕开，见 `.research/ref-harmony` 的
`src-main/main.js` 与 `profiles/desktop/cordis.patch.yml`）。**同进程内 loopback 不跨隔离边界**，
因此本架构不需要绕，也就没有「必须打洞」的结构性压力。
子进程（HNP / `childProcessManager`）作为**崩溃隔离**的后续优化项，不作为 v1 前提。

**② 端侧 profile 把不可用的原生行精确关掉、可用的行打开**，
**③ 核心/插件的版本管理（dsh 本身**没有**提供，必须我们自己建，见 §6）**。

## 4. 运行时路线（含回退）

### 4.0 已决策：分两阶段（2026-09-12 拍板）

| 阶段 | 载体 | 目的 | 状态 |
|---|---|---|---|
| **阶段一（打通）** | **复用 Electron-on-鸿蒙 运行时**（`harmonypc-electron`，Electron 37 / Node 22.17.0）——**只跑 Node 与 dsh Host，不创建 Chromium 窗口** | 最快拿到「端侧自足 Host + 现有 ArkUI 页面 + @ohos-ports 原生能力」的**可运行系统**，把所有端侧集成问题（沙箱 HOME、symlink、loopback、profile、解包、核心版本切换）一次问清楚 | ← 当前 |
| **阶段二（目标形态）** | **自建 `libnode.so`**（官方 Node 源码 `--dest-os=ohos --dest-cpu=arm64 --shared`）+ NAPI 引导，替换掉 Electron 运行时 | 去掉 ≈172 MB 的 Chromium 负载、摆脱第三方运行时依赖、覆盖手机形态（HNP/`executableBinaryPaths` 主要在 2in1/tablet 可用） | 阶段一跑通后启动 |

> 两阶段的**接口必须一致**：ArkTS 侧只见 `DshHost`（start / status / stop），底下换载体不动上层。
> 这也是把 §4.1 与 §4.2 分开写的原因——**阶段一的产物不能泄漏到状态层与 UI 层**。

#### 4.1.1 阶段一实测状态（2026-09-13，产物已到位）

用户已提供华为侧产物 `v37.2.3-20260825.1-release.zip`（353.3 MB）。解包与校验已脚本化并入库
（`tools/electron-runtime/{extract.ps1,verify.ps1,README.md}`）。实测：

| 项 | 实测值 |
|---|---|
| release zip 内条目 | **1 个**：`libelectron_138.tar.gz`（373.9 MB） |
| 解开后的关键库 | `libelectron.so` **172.7 MB**、`libadapter.so` 7.33 MB、`libffmpeg.so` 2.10 MB |
| `libc++_shared.so` | 包里**没有**，从 OHOS SDK 的 `native/llvm/lib/aarch64-linux-ohos/` 复制补齐（1.20 MB） |
| 可直接引入的模块 | `libelectron/ohos_hap/{electron,web_engine}` + `{AppConfig,hvigor}` |
| 未 strip 的符号版 | `libelectron/lib.unstripped/libelectron.so` 1.19 GB —— **解包时排除** |
| ELF | 四个库均为 ELF64 / AArch64 / `ET_DYN` |
| **签名** | 四个库**都只有 `.note.ohos.ident`、没有 `.codesign`** ⇒ **未签名** |

**对"未签名为何仍可用"的判断依据（写清楚以免被误读成乐观）**：XPM 拦的是**执行**未签名二进制
（社区方案被拒绝的正是 `resources/resfile/electron` 这个**可执行路径**）；而这四个 `.so` 是
**随 HAP 打包、由 `dlopen` 加载**，签名覆盖来自 **HAP 自身**；同一批产物已被社区在真机
（HarmonyOS 6.1.0.135 / API 24）上跑通。**同时如实记为风险**：若平台对 in-HAP 的 `.so` 也强制
代码签名，需用 `binary-sign-tool` / `self-sign.py` 补签后再打包。

> 阶段二的自建路线同样在推进：OpenHarmony 公开 SDK（含 Linux NDK，clang 15.0.4）已成功获取，
> Node v22.23.2 源码已解包并推进到 `deps/ncrypto` 编译；当前阻塞点是
> **该文件用了 C++20 的 `<=>`，而 gyp 传的是 `-std=gnu++17`**（且 SDK 自带 clang 15 偏旧，
> 上游 OHOS 移植 CI 用的是 LLVM-19）。阶段一不再依赖它，因此它转为并行轨道。

#### 4.1.2 阶段一的启动链与三条硬约束（源码精读结论，2026-09-13）

对解包出的 `electron` / `web_engine` 两个模块做了逐文件精读（含 `libadapter.so` / `libelectron.so` 的符号与字符串），结论如下：

**启动链（谁真正把 Node 起起来）**
```
module.json5 srcEntry → AbilityStage extends WebAbilityStage
  → WebAbilityStage.onCreate → runTaskAsync → JsBindingUtils.initNativeContext(0)
      → libadapter.so 的 GetNativeContextByType （**只返回上下文，不启动 Node**）
  → JsBindingMethod.bind()（注册约 40 组 *AdapterBind）+ Inject + SetContextPaths
  → 【关键】WebWindow 的 XComponent .onLoad → nativeContext.runBrowser(argv)
      → libadapter.so 的 RunBrowser/ChildMain → libelectron.so（内含 Node 22.17.0 + Electron）
      → 按 Electron 原生机制加载 resources/resfile/resources/app/package.json 的 main
```

**三条因此被钉死的约束：**

1. **必须有 ArkUI 窗口/表面，但不需要 Electron 窗口。**
   `runBrowser` **只能**从组件生命周期触达（`XComponent.onLoad` / `aboutToAppear`），而 `.onLoad` 要在
   `windowStage.loadContent()` 之后、表面就绪才触发 ⇒ **ArkTS 侧删不掉窗口**。
   但 Node 在那之前就已经起来了，`main.js` **只要不 `new BrowserWindow`、不 `loadURL`，就不会有 Chromium 渲染进程**。
   ⇒ 端侧形态是"一个不可见/最小化的窗口 + 我们的 ArkUI 页面"，**不能 `terminateSelf`/`destroy()`**（表面一没，运行时即死）。

2. **`web_engine` 删不掉**——启动链全在它里面；`electron` 模块只是几十行的薄壳子类。
   精简只能到"保留启动所需的那几个类 + `JsBindingMethod` 裁剪"，属阶段二优化。

3. **阶段一需要 JIT 权限，与"不申请特殊权限"冲突（已在 D6 §4.4 预言）。**
   `web_engine` 自行声明 `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY`（`definePermissions`），
   而它是 V8 JIT 的前提。⇒ **阶段一只能作为开发期验证通道**（决策 D-7 得到证实），
   上架形态必须是阶段二自建 **jitless** 的 `libnode.so`。

**其它已确认的事实（写下来以免重复考古）**：
- `main.js` 的落点是 **`web_engine/src/main/resources/resfile/resources/app/main.js`**，靠 Electron 原生
  `process.resourcesPath + appSearchPaths` 解析（两个 `.so` 里都**没有**硬编码 `resources/app`），
  所以**不需要**改运行时、也不需要 HNP。
- 原版 `deviceTypes` 只有 `2in1`/`tablet` ⇒ **手机装不上**，必须加 `phone`（我们的真机正是 phone）。
- 参考工程里 `WebAppAdapter*` / `KVStore` 是**死代码**（`WebAppAdapterBind` 从未被 `bind()` 调用）。
- 无窗口时 `app.on('window-all-closed')` **永不触发**，别把停机逻辑挂在那儿。

#### 4.1.3 P5 探针真机结论（2026-09-13，**两条都取证了**）

在真机（HUAWEI Mate 70 Pro+ / `deviceType=phone` / API 26 / OpenHarmony-7.0.0.105）上，
通过 `entry@ohosTest` 的 `OnDeviceProbe` 用例取证（`aa test`，165 用例 / 164 通过）：

| 问题 | 真机读数 | 结论 |
|---|---|---|
| **沙箱能否创建符号链接**（R3） | `symlinkOk=false errCode=13900012 msg=Permission denied` | **不能**。dsh 启动时由 `healProfilesModuleFallback` 在 `$DSH_HOME/profiles/node_modules` 下建符号链接的那条路**在这台设备上必然失败** ⇒ 必须走替代方案（预置结构 / 走 pkg-ESM-proxy 分支 / 登记为端侧差异），**不能假设它会成功** |
| **同进程回环是否可用**（R4） | `listenOk=true connectOk=true`（listen 127.0.0.1 成功，同进程 connect 成功） | **可用**。⇒ §2 的架构前提成立：**不绑 `0.0.0.0`、不改写 `Host` 头、不需要隧道**这条主线是对的 |

> **R3 的处置（下一步）**：`13900012` 是权限拒绝，不是"路径不存在"。因此顺序是：
> ① 先看 dsh 是否有"不建符号链接"的组合路径（它对自己 pkg 形态有 ESM-proxy 分支）；
> ② 否则在端侧预先把 `profiles/node_modules` 物化成**真实目录/硬链接**；
> ③ 仍不行才作为端侧差异登记（并记入 D5 的降级策略）。
> **注意**：这与"对 dsh 上游零 patch"的纪律直接相关——优选项是 ①，最次才是 ③。

> **R4 的另一半仍待验**：本探针证明的是**同一进程内**回环可用。
> 若将来把 Host 挪到子进程（崩溃隔离），跨进程回环是否可用**需要重新取证**，
> 不能把这条结论外推（社区正是在"渲染进程 ↔ 主进程"之间被隔离的）。

#### 4.1.4 R3 的处置：**用 dsh 自带的"ESM proxy"分支，零上游 patch**（2026-09-13）

R3 的实测结论是"沙箱全局禁符号链接"（三个目录全部 `13900012`）。顺着这个约束读 dsh 源码后，
找到了一条**不需要改上游**的路：

`dsh-app-boot` 的 `resolveModuleFallbackEntries` 里，链接形态是**二选一**的：

```js
entries: !isPackagedExecutable()
  ? [...links].map(... { kind: "symlink" })    // 普通 Node → 写符号链接（鸿蒙禁止）
  : [...links].flatMap(... { kind: "proxy" })  // pkg 打包 → 写真实目录 + entry-N.js
```

而：

| 事实 | 依据 |
|---|---|
| `isPackagedExecutable()` 的实现只有一句 `return process.pkg !== void 0` | `dsh-app-boot/lib/index.js:485-486` |
| proxy 分支的实现 `ensureModuleProxy` **只用普通文件 API**（`mkdirSync` + `writeFileSync`），写出的 `entry-N.js` 是 `export * from "<file:// URL>"` | 同文件 `:548-579` |
| `packageProxySource` 也只用真实路径（`packageDir` + `pathToFileURL`） | 同文件 `:510-540` |
| pkg 只出现在那段代码的**动机注释**里，运行路径上没有 pkg 虚拟文件系统依赖 | 同文件 `:542-547` |

⇒ **处置**：在我们的宿主入口 `hostcore/app/main.js` 里，于导入 dsh 之前设置
`process.pkg = process.pkg || {}`，让 dsh 选 proxy 分支。**不改 dsh 一行代码**，
`$DSH_HOME/profiles/node_modules` 会变成一堆小目录而不是一堆链接。

**风险（必须真机验证，不得当成已解决）**：
1. 其它依赖若也探测 `process.pkg` 并据此改变行为，可能被这一行影响；
2. 文件数变多（每个包一个目录 + N 个 entry 文件）；
3. 这条路径原本是为 pkg 设计的，**没有人在非 pkg 场景下验证过它**——
   与 `--shared` 在 OpenHarmony 上"已接线但未测试"属同一类风险。

#### 4.1.6 挂载 RuntimeHost 后的真机诊断：缺的是**能力代理**，不是运行时（2026-09-13）

[WebEngine]: ContextAdapter --> No active proxy. use default proxy

- `AbilityManager.getProxy failed` + `ContextAdapter: No proxy can be used`

`addProxy` 注册与上下文路径回调；同时确认 `WebBaseAbility.getContentPath()` 返回的
`pages/Index` 会落到**我们的**页面（本模块同名的 `pages/Index` 正好是我们挂 RuntimeHost 的那页）。

### 4.4 JIT：**本项目不申请该特殊权限**（为顺利上架，各端统一 jitless）

> **产品决策（2026-09-12，用户拍板）**：**各端都不涉及 JIT 特殊权限相关的能力**，以确保顺利上架。
> 即：**不申请** ACL 权限 `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY`，也不使用任何依赖它的方案。
> 运行时必须在**无 JIT 权限**的前提下工作 —— 这对**所有设备形态**成立，不只是手机。

V8 依赖**可写可执行的匿名内存**，鸿蒙默认拦截。两条路的对比（本项目只走右边那列）：

| | ❌ 有 JIT（本项目不采用） | ✅ **无 JIT（本项目唯一形态）** |
|---|---|---|
| 权限 | 需 ACL 权限 `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` | **不申请任何特殊权限** |
| 可获得性 | **仅平板 / PC-2in1 应用可申请**，且须适配「坚盾守护模式」 | 各端一致，无差别 |
| 上架 | 特殊权限 + 额外适配，风险与成本都高 | **普通权限即可**（网络只需 `ohos.permission.INTERNET`） |
| 运行时要求 | 默认构建即可 | 必须以 **jitless** 方式运行 V8（`--jitless` / `v8_jitless=true` 构建） |
| 代价 | — | 计算密集 JS 显著变慢、**WebAssembly 不可用** |

**由此推出的两条硬约束（会影响选型，必须前置验证）**：

1. **运行时不能"默认启用 JIT"**。阶段一若走 Electron-on-鸿蒙 运行时，它的 V8 是带 JIT 编译的；
   必须验证它能否在设备上以 jitless 方式启动（Node 侧 `--jitless`，或 `--js-flags`），
   **否则阶段一只能当"开发期验证通道"，不能作为上架形态**；上架形态回到阶段二自建 `v8_jitless=true` 的 `libnode.so`。
   （社区资料亦指出 Electron-on-鸿蒙 的 fork/子进程方案本身依赖 JIT —— 这与"不申请该权限"直接冲突，必须实测。）
2. **依赖 WebAssembly 的功能要提前排查**。jitless 下 `WebAssembly` 为 `undefined`，
   凡是靠 wasm 的依赖（部分解析器/图像/加密库）在端侧会直接不可用。这一项要作为端侧 profile 的能力探测项之一。

**POC-13（项目级门，不再是"手机专用"）**：在**无 JIT 权限**的前提下跑真实会话——

1. 确认运行时确实以 jitless 起来（能读到 V8 的 jitless 状态，且没有申请任何特殊权限）；
2. 跑一次真实会话（含工具调用与长轨迹渲染），记录：首 token 延迟、单次 RPC 处理耗时、轨迹滚动帧率、内存峰值；
3. 判据：端侧额外开销相对网络往返**不成为瓶颈**（例如单次 RPC 处理 < 50 ms、轨迹渲染不掉帧）即为可用。

> dsh 的端侧负载以**网络等待 + I/O + JSON 处理**为主，不是计算密集；"慢 10~100 倍"针对计算密集场景，
> 因此 jitless 是否可接受必须**用真实会话实测**，而不是按经验判死。

**本项目对机型覆盖的判断（在"统一 jitless"下重新表述）**：
jitless 让**各端的技术约束变得一致**（不再有"平板能申请 JIT、手机不能"的差异），
这反而简化了目标：**四形态共用同一份运行时与同一套 profile**，差别只在布局与输入。
剩下的风险从"权限可得性"变成"**jitless 的性能是否够用**"，由 POC-13 用真实会话回答。

> **机型覆盖结论（当前）**：四形态**同技术前提**（不申请任何特殊权限、统一 jitless），
> 因此**四形态都在目标内**；某个形态若被 POC-13 判为不可用，才**如实降级**该形态的能力
> （而不是假装各端等价，也不是靠申请特殊权限去换性能）。
> 另一条好消息：无 JIT 权限后，**上架不再受"仅平板/PC 可申请"的限制**，手机形态也不再有权限层面的排他。

## 5. 端侧 profile：哪些 dsh 行必须关、哪些可以开

| 行 id | 包 | 硬依赖 |
|---|---|---|
| `subprocess` | `@deepseek-ai/dsh-subprocess-local` | `node-pty` + `koffi`（且静态 import `dsh-win32-process`） |
| `sandbox` | `@deepseek-ai/dsh-sandbox-local` | `koffi`（经 `dsh-sandbox-windows-acl`） |
| `attachment-local` | `@deepseek-ai/dsh-attachment-local` | `sharp` |

> **已决策（2026-09-12）：优先换成鸿蒙移植版，而不是一上来就禁用。**
> 即把这三个包按 `npm:@ohos-ports/...` 别名接进端侧核心树，尽量保留完整能力（终端 / 沙箱 / 图片）。
> 但必须带上失败预案：那批移植件对应的是**更早的 dsh 一代 + 不同的 Node ABI**（阶段一是 Electron 37 / Node 22.17），
> 因此**每一个移植件都要单独验证能不能在本运行时里加载并工作**；
> 验证不通过的，退回「禁用该行 + 在界面如实标注能力缺失」，不允许让核心起不来。
>
> 验证顺序（按风险从低到高）：`sharp`（Node-API，ABI 稳定）→ `koffi`（Node-API）→ `node-pty`（历史上有 NAN 成分，ABI 相关）。

### 5.2 建议关闭 / 需要显式选择

| 行 id | 原因 | 处置 |
|---|---|---|
| `tool-fs-search` | 依赖随包的 `rg` 可执行文件 | 有鸿蒙可执行的 rg 就开，否则关（按调用失败降级不致命） |

### 5.3 端侧 profile 的落地形态

沿用 dsh 自己的扩展点（**零上游 patch**）：

1. 一个 bundle 包 `@hdsh/bundle-ondevice`，声明 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`；
2. profile 目录 `<cores>/<ver>/profiles/ondevice/package.json` 里 `dsh.profile.bundles = ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "@hdsh/bundle-ondevice"]`；
3. 能力**探测结果**（运行时有没有 koffi/sharp/pty、有没有 rg）在启动前由 ArkTS 侧算好，作为 `--patch` 覆盖层或生成 profile 的 `cordis.patch.yml`——**同一份核心树可以按设备能力起出不同能力的 Host**。

## 6. 核心版本与插件（dsh 没提供，本项目自建）

### 6.1 核心版本：激活事务（stage → verify → switch → rollback）

dsh 现状（实测结论）：**没有** `$DSH_HOME/packages`、没有候选核心的 staging 目录、没有健康检查、
没有 activate/rollback、没有 A/B 启动、没有自更新。「切版本」今天只有一种办法：换掉那一棵扁平安装树再重启进程。

因此端侧实现：

```
<files>/dsh/cores/
  ├─ 0.1.5-rc.2/            # 已激活
  ├─ 0.1.6-rc.1.staging/    # 正在解包/校验（未激活）
  └─ …
<files>/dsh/state.json      # { current: "0.1.5-rc.2", previous: "...", history: [...] }
```

切换流程（每一步都可失败且可回滚）：

| 步 | 动作 | 失败处置 |
|---|---|---|
| 1 | 下载/导入新核心包到 `.staging` | 保持 current 不变 |
| 2 | 校验（清单/大小/摘要；离线包校验签名） | 删除 staging |
| 3 | 解包到 `cores/<ver>/`（原子 rename） | 删除半成品目录 |
| 4 | **健康检查**：用该版本起一次 Host，直到 `/api` 可用且 `$events` 收到 `ready`；超时即失败 | 记 `health: fail` 并保留证据（日志摘要） |
| 5 | **激活**：写 `state.json.current = <ver>`，重启核心 | 重启失败 → 自动回滚到 `previous` |
| 6 | 清理旧版本（保留最近 N 个 + 永远保留 previous） | — |

**用户数据不动**：`$DSH_HOME` 独立于核心树，升级/回滚不迁移、不删除会话。

### 6.2 插件

dsh 现状（实测结论）：插件**没有** Remote 安装/启停端点；`pluginInventory.list` 只读；
唯一变更路径是改 profile 的 `dsh.profile.bundles` / `cordis.patch.yml`，或 `dsh plugin --profile <name> <pnpm args>`
（它 `spawnSync("pnpm", …)`）。因此：

| 能力 | 端侧做法 |
|---|---|
| 列出/查看状态 | 直接用现有 `pluginInventory.list`（只读，已经有） |
| 安装/卸载 | 端侧包管理：把插件包下载/解包进 `<files>/dsh/plugins/<name>`，用 Node 侧脚本改 profile 的 `dependencies` + `bundles`（**不依赖系统 pnpm**：可以自带一个纯 JS 安装器，或在可用时用运行时内的 pnpm） |
| 启用/停用 | 写 profile 的 `cordis.patch.yml`（`{id, disabled:true}`），核心重启或热加载生效 |
| 回滚 | profile 目录整体做快照，失败即还原 |
| **含原生 `.node` 的插件** | **不能热装**：鸿蒙只允许加载 HAP 内的、已签名的 `.so`（E14）。这类插件只能两种方式支持：① 随应用发布（打包进 HAP，作为"随包插件"）；② 走 HNP 分发（E7/E15，且仅平板/PC）。**界面必须把"纯 JS 插件可装、原生插件需更新应用"如实区分**，不允许点了没反应 |

> **这条约束会让"支持各类插件"的语义变具体**：纯 JS 插件（dsh 的绝大多数 `dsh-*` 客户端/服务端插件都是 JS）可以运行时安装；
> 带原生模块的插件必须经过应用发版。设计插件页时必须把这两类分开呈现，并把"为什么不能装"写清楚。

> 界面上「插件」页（现有 `SettingsPane` 的插件页签）从「只读清单」升级为**可操作**，但每个动作都要有
> 成功/失败/回滚三态，不允许"点了没反应"。

## 9. 风险

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | `libnode.so` 构建失败（交叉编译/工具链/签名） | 中 | **致命** | 限时；失败转 F1/F2；每次尝试都要留下可复现脚本与错误原文 |
| R2 | 鸿蒙商用版拒绝加载未签名或签名不匹配的 `.so` | 中 | **致命** | E5 的签名流程前置到 M0′；把它当验收项而不是收尾项 |

| R5 | 体积/内存超预算（Node + dsh ≈ 200 MB+ 解包） | 高 | 中 | 核心树按能力裁剪（§5.3）；默认不打包浏览器 UI 资源以外的冗余 |
| R6 | `@ohos-ports` 移植件版本落后于我们锁定的 dsh 版本 | 高 | 中 | 端侧 profile 以**能力探测**决定启用哪些行；移植件只作增强，不作前提 |
| R7 | dsh 上游升级引入新的硬原生依赖 | 中 | 中 | 沿用 D5 漂移门禁；新增包必须过「端侧可行性」检查（是否新增 `.node`） |
| **R8（最高）** | **不申请 JIT 权限的前提下，jitless 是否够用**（E13 + 上架约束） | **高** | **高（决定整个产品是否成立）** | POC-13 前置实测；若 jitless 不可用，退路是"缩小端侧职责"（例如端侧只做会话/审批，重负载留给可选的远程 Host），**不得**回头去申请特殊权限 |
| R11 | 阶段一 Electron-on-鸿蒙 运行时**无法以 jitless 启动**（其 V8 带 JIT，社区方案还依赖 JIT 做 fork） | 中高 | 中 | 明确把阶段一定位为"开发期验证通道"；上架形态以阶段二自建 `v8_jitless=true` 的 `libnode.so` 为准（§4.2/§4.4 约束 1） |
| R12 | jitless 下 `WebAssembly` 不可用，某些依赖直接失效 | 中 | 中 | 把"是否依赖 wasm"纳入端侧 profile 的能力探测项（§4.4 约束 2） |
| R9 | `libnode.so` 的 `--shared` 在 OpenHarmony 上未经验证（E12） | 中 | 中（阶段二） | 阶段一不被它阻塞；阶段二先用 `--shared` 构建最小验证（能 dlopen + 打印版本）再谈集成 |
| R10 | 原生插件无法热装（E14） | 高 | 中 | 插件页区分纯 JS / 原生两类（§6.2）；原生走随包或 HNP |
