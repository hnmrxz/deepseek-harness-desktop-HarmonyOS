# 端侧核心运行架构（On-Device Core Architecture）—— D6

> 本文档于 2026-09-19 由完整版精简为结论摘要；完整过程记录见 git 历史（本文件压缩前版本）。

## 0. 一句话更正

HDSH 不是「PC 上 dsh 的遥控器」，本体就是 DSH 的运行载体：应用内自带 DSH 核心运行能力，在自己这一端把 Host 跑起来，ArkUI 原生页面讲本地 Host 的协议；支持插件增删启停与核心版本的安装/切换/回滚。远程客户端保留为可选接入方式，不再是产品目标与验收口径；凡「必须有另一台机器在跑 dsh」才成立的功能都不算完成。本文为历史架构记录（原 v1.0，2026-09-12）；新增决策以 docs/03 / docs/07 为准，上位文档 `docs/00-开发任务书.md`（D1）。

## 1. 不变式（设计的硬边界）

1. **零上游 patch**：不 fork、不魔改 dsh 业务代码；端侧差异只走 dsh 自己的组合面（profile / `cordis.patch.yml` / bundle）。
2. **不打洞**：默认只监听 `127.0.0.1`；不绑 `0.0.0.0`、不伪造 `Host`/`Origin`。端侧 Host 与客户端同进程，天然满足。
3. **状态与代码分离**：`$DSH_HOME`（会话/设置/凭据/工作区注册）在应用沙箱里只有一份，跨核心版本共享；核心代码树按版本各存一份；升级核心不动用户数据。
4. **能力降级而非崩溃**：dsh `boot()` 是 fail-loud（任一插件行挂载失败 → `exit(1)`），必须用 profile 精确控制「哪些行启用」。
5. **界面不说谎**：核心没起来、版本不匹配、插件装失败，页面必须如实说明并给出下一步动作。
6. **上架优先：不申请任何特殊权限**：不用 JIT 类 ACL 权限；运行时统一以 **jitless** 方式工作，权限面只保留普通权限（网络 = `ohos.permission.INTERNET`）。

## 2. 目标架构

```
┌─ HDSH（HAP / APP）────────────────────────────────────────────────────────┐
│  UI 层（ArkUI 原生页面，一多自适应）        ← 「客户端页面」                │
│    └ 复用现有 9 个视图 + 三形态导航（手机/折叠屏/平板/2in1）               │
├──────────────────────────────────────────────────────────────────────────┤
│  状态层 appstate（SessionHub 单一连接与会话状态中枢）                      │
├──────────────────────────────────────────────────────────────────────────┤
│  协议层 connection + dshcompat（84 端点 / 4 流，漂移门禁保护）              │
├──────────────────────────────────────────────────────────────────────────┤
│  ★ 新增：端侧核心运行层 hostruntime                                       │
│    ├ DshHost      核心生命周期：准备 → 起 → 健康检查 → ready → 停/重启     │
│    ├ CoreStore    多版本核心仓库：解包 → 校验 → 激活 → 回滚（§6）          │
│    ├ Profiles     端侧 profile / bundle（哪些 dsh 行启用，§5）             │
│    ├ Plugins      插件清单与增删启停（§6.2）                              │
│    └ Runtime      运行时载体：libnode.so / NAPI 引导（§4）                │
├──────────────────────────────────────────────────────────────────────────┤
│  设备能力层 platform（通知 / 长时任务 / 剪贴板 / 分享 / 窗口 / 密钥存储）    │
└──────────────────────────────────────────────────────────────────────────┘
        │ 进程内 loopback：HTTP POST /api/<endpoint> + WS /api/remote.mux
        ▼
┌─ 端侧 dsh Host（Node 运行时，跑在本应用进程内的线程上）───────────────────┐
│  webserver(127.0.0.1:port) ├ /api ├ /api/remote.mux ├ $events            │
│  dsh 本体：agent / 工具 / 会话持久化 / 投影 / 设置 / 凭据 / 插件清单       │
│  DSH_HOME = <应用沙箱>/dsh/home（跨版本共享，唯一一份用户数据）           │
└──────────────────────────────────────────────────────────────────────────┘
```

同进程而非 HNP 子进程：鸿蒙 NEXT 上跨进程/跨设备的 loopback 可能被隔离（社区 Electron 方案必须绑 `0.0.0.0` + 改写 `Host` 头绕开），同进程内 loopback 不跨隔离边界，无「必须打洞」的结构性压力；子进程崩溃隔离只是后续优化项。真机已证同进程回环可用（listen `127.0.0.1` + 同进程 connect 成功）。

## 3. 可行性证据（结论摘录）

- Node 官方支持 OpenHarmony/arm64（≥5.0，Experimental，PR #58350 已合入 main）；官方 dist 无任何 ohos 预编译包，亦无预编译 `libnode.so`，须自建。
- `@ohos-ports/*`（koffi / node-pty / sharp / better-sqlite3 等）为现成鸿蒙移植；实测移植 `.node` 同时带 `.note.ohos.ident` 与 `.codesign`。
- 核心树可在 Windows 上物化为 openharmony/arm64 形态（`npm install --os=openharmony --cpu=arm64` + overrides 别名；518 包 / 约 2.7 万文件 / 约 293 MB）。
- **JIT 是权限闸门**：`ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` 仅平板/PC-2in1 可申请，手机不可 ⇒ 统一 jitless（§4.4）。
- **`.node`/`.so` 必须随 HAP 打包**：热更新下载的 so 缺合法签名被系统拦；运行时解包到沙箱的原生库 `dlopen` 同样被拦 ⇒ 核心树原生件必须由 HAP `libs/` 提供。
- 原生子进程（`childProcessManager`）仅平板/PC-2in1 可用，**手机禁止三方应用创建进程** ⇒ `dsh plugin add`（`spawnSync("pnpm")`）在端侧永不成立。
- 监听 `127.0.0.1` 只需普通权限 `ohos.permission.INTERNET`（seccomp 白名单含 socket/bind/listen/accept/connect）。
- `--jitless` 是 Node 一等选项：关掉 turbofan/sparkplug/maglev，并隐含 `--no-expose-wasm`（`WebAssembly` 变 `undefined`）。
- OHOS 用 `libappspawn_helper` 拦截应用进程 `exit()`：**任何 `process.exit()` 都变成 SIGABRT**；dsh 的 fail-loud `exit(1)` 必须由入口脚本拦截。
- 手工放进 `entry/libs/` 的预编译 `.so` 绑不上 ArkTS import；**必须走 hvigor 的 CMake 路径**构建原生模块（`externalNativeOptions`）。
- gyp 的 `OS` 由构建宿主决定（=linux），Node 所有 `OS=="openharmony"` 分支是死代码 ⇒ 端侧 `process.platform=linux`；移植件需按 `linux_arm64` 复制别名命中 loader。
- 打包流程从不给内嵌 `.so` 签名（原样字节进包）；**实测 HAP 内只有 `.note.ohos.ident`、无 `.codesign` 的 `.so` 也能加载执行**（签名覆盖来自 HAP 自身）。
- 核心树唯一 WASM 产物是 sharp 的 wasm32 回退变体（实际用原生变体）⇒ 除 Node 内建 undici（§4.4 已垫片）外，依赖集在 jitless 下成立。
- **主链已真机跑通**：HAP 内嵌自建 Node（22.23.2）+ dsh Host 监听 `127.0.0.1:3120`（`/proc/net/tcp` LISTEN）+ ArkUI 客户端 token 接入 + 真实模型对话。

工程量集中在：① 可被 HAP 加载的 Node 运行时；② 端侧 profile 精确控制行启停；③ 核心/插件版本管理（dsh 没有，自建，§6）。

## 4. 运行时路线（含回退）

### 4.0 已决策：分两阶段

阶段一（复用 Electron-on-鸿蒙运行时，只跑 Node 不建 Chromium 窗口）曾作为打通通道，**现已彻底移除**（`web_engine` 依赖、`libelectron.so`/`libadapter.so`/`libffmpeg.so`、`runtime/` 全删，HAP 减约 190 MB；该链路曾有未解的引导期 `exit(1)`，且需 JIT 权限、与上架约束冲突）。**阶段二是唯一现存路径**；两阶段接口一致：ArkTS 只见 `DshHost`（start/status/stop），换载体不动上层。

### 4.2 阶段二（目标形态）：`libnode.so` + NAPI 引导（同进程）

- 构建链已跑通并入库：`tools/node-runtime/{fetch-ohos-sdk.sh,build-node-ohos.sh,toolchain-env.sh}`（`OHOS_ARCH=arm64|x64` 参数化）。修补点：`common.gypi` 改 `gnu++20`、关 zlib ARMv8 CRC32 SIMD、目标链接去 `-latomic`、`deps/uv` 的 `uv__use_io_uring` 无条件 `return 0`（否则 io_uring syscall 被 seccomp 杀）。`--dest-os` 合法值是 `openharmony`；make 不带 `CC/CXX` 导出会静默用宿主编译器污染目标树（`diagnose-toolchain.sh` 核对非 AArch64 对象数必须为 0）。
- `libdshhost.so` 由 `entry/src/main/cpp/CMakeLists.txt` 经 hvigor 构建并按 `libs/<abi>/lib<name>.so` 打包，导出 `runtimeVersion/startHost/isHostRunning/stopHost`。
- **libnode 加载顺序（关键）**：`libdshhost` 构造函数用 `dladdr` 取自身路径，对同目录 `libnode.so.127` 以**绝对路径首载** `dlopen(RTLD_NOW|RTLD_GLOBAL)`，再 `dlsym` 取 `node::Start`——保证 `napi_*` 符号在全局作用域供后续 `.node` 解析；不能靠 `DT_NEEDED` 先载（musl 不把已局部加载的库提升为全局）。
- **R4（签名判据，`tools/pack-core.mjs` 引用）**：门禁判据必须是 **`.codesign` 段的存在**——只有 `.note.ohos.ident` 不构成「已签名」的证据（`binary-sign-tool` 签过的 `bin/node` 两者都有；未签名产物只有前者，且正是后者出现在 XPM 拒绝日志里）。实测现状：包内 `.so` 无 `.codesign` 也能加载。
- **原生库重定向**：沙箱内 `.node` 的 `dlopen` 被系统拦 ⇒ 入口脚本同时接管 `fs.existsSync` 与 `Module._extensions['.node']`，把沙箱 `.node` 请求重定向到 HAP `libs/` 扁平文件（约定 `lib<stem>.so`）；hvigor 只打扁平 `libs/<abi>/*.so`，不能按 loader 原始候选路径摆放。
- **Host 启动契约**：配置通道是**环境变量而非 argv**——`HDSH_CORE_DIR/HDSH_HOME/HDSH_SANDBOX_HOME/HDSH_PORT/HDSH_PROFILE` 全部由引导层 `setenv` 传入（裸 libnode 下 `main.js` 无自定位能力）；`--jitless` 必须排在脚本路径之前；Node argv 不认 dsh 应用级选项（`--port/--host/--no-open` 走 `runProfile` 的 args；当前核心版本**没有** `--skip-auth`）。启动 token 只出现在 `dsh web: http://127.0.0.1:<port>/?token=…` stdout 行，入口脚本拦截 stdout 写 `host-ready.json`；客户端走 token→cookie 兑换（`GET /?token=` → 303 + `Set-Cookie`），token 每进程重新生成。
- 运行时必须满足（dsh 源码实测）：`node:zlib` 的 zstd（Node ≥22.15 默认可用，无需 `--experimental-zstd`）、`node:worker_threads`、版本下限 **22.17.0**（自建 22.23.2）、`HOME` 指向沙箱可写目录、启动路径不依赖系统 shell。
- 入口脚本还负责：`runProfile` 前清理孤儿写锁（`dsh-atomic-write` 的 `*.lock` 在持有者被杀时永久残留，端侧用户无法手删）；钉死 `os.tmpdir()` 与 `NO_PROXY`（不覆盖已有值）。

### 4.3 回退路线

F1（HNP 分发 `node` 可执行文件）**在手机上不成立**（原生子进程仅平板/2in1）⇒ 手机唯一可行路线是同进程 `libnode.so` + jitless；F2（停留在阶段一）已随阶段一移除而废弃；F3（只读缓存 + 可选远程 Host）不满足目标，必须如实关闭目标而不是伪装完成。

### 4.4 JIT：本项目不申请该特殊权限（各端统一 jitless）

- 不申请 `ALLOW_WRITABLE_CODE_MEMORY`；运行时统一 jitless。代价：WebAssembly 不可用、计算密集 JS 变慢；dsh 负载以网络等待 + I/O + JSON 为主，真实会话实测可用（POC-13 口径：单次 RPC 处理 <50 ms、轨迹渲染不掉帧）。
- **undici/WASM 事实链**（jitless 的核心工程问题，已解决）：`node:http` 的惰性 undici 加载器（`lazyUndici`）在访问 `http.Agent` 等属性时初始化 undici 全局 dispatcher ⇒ jitless 下抛 `WebAssembly is not defined`。修法：入口脚本用 `defineProperty` 封掉 `node:http` 全部惰性 getter（`maxHeaderSize/globalAgent/WebSocket/CloseEvent/MessageEvent`）。
- 全局 `fetch/Request/Response/Headers` 由 `fetch-shim.js` 补齐（标准 Fetch 签名；`Response` 支持 string/Buffer/Blob/stream/空体且总给 `Headers`，含 `static json/redirect/error`；缺哪个全局补哪个）。
- `dsh-web-fetch-http` 直接 `await import("undici")`（WASM llhttp）⇒ `undici-shim.mjs` 把 `undici` 模块名接到 http 垫片并把 `dispatcher` 翻译为 `lookup`（**保住上游 DNS 钉住/SSRF 防护**）；`undici-loader.mjs` 用 `module.register` 解析钩子，**只在 WebAssembly 不可用时注册**；同源跳转仍被跟随、跨源跳转仍被拒 `WEB_REDIRECT_BLOCKED`（安全语义不降级）。已固化为 `tools/check-web-fetch-jitless.mjs` 双臂对照门禁（真机待验：`register()` 钩子线程在端侧是否允许）。
- 规矩：端侧/jitless 相关 harness 一律用 CJS `require` 取 `node:http`（ESM `import 'node:http'` 在 `--jitless` 下进程崩溃退出）。

## 5. 端侧 profile：哪些 dsh 行必须关、哪些可以开

- dsh `boot()` 要求所有行 activate；**任一必装行失败 → `exit(1)`** ⇒ 端侧 profile 是「能不能起来」的前提，不是优化。
- 原始判定必须禁用的硬依赖行：`subprocess`（node-pty+koffi）、`sandbox`（koffi）、`attachment-local`（sharp）。处置是换成鸿蒙移植件/自建件并逐个验证，验证不过则禁行并如实标注能力缺失；端侧实际默认禁用 shell/沙箱链（手机无进程创建能力）与 `tool-fs-search`（沙箱内无系统 `rg`）。建议关闭/显式选择：`session-query-sqlite`（保持 `openAt: never` 或确认 `node:sqlite`）、`directory-picker` 挂 `-browse`、`session-telemetry-otel` 默认关、`client-hmr` 生产关。
- **禁一行不是局部操作**：会沿服务依赖链把消费者拖成 pending（`attachment-local`→`file-upload`→`session-controller`；`bash/pwsh-sandbox`→`permission-presets`），而 boot 要求全部行 activate。patch 行 **id 与包名可能不同名**（`permission-presets` 包的行 id 是 `permission`），写错静默不生效。
- 端侧 preset `presets/ondevice/`：复制 standard 并禁 `tool-pwsh/tool-bash/tool-fs-search`（都依赖 `ctx.subprocess`）；`session/create` 用 `agent-presets.default: ondevice`。`permission` 行需 `shell` 服务而端侧无法提供 ⇒ 权限预设三档在端侧**不可切换**（上游硬约束），界面显示宿主投影的真实值（`workspace-write`）。
- `web-runtime` 行显式覆盖 `surfaceContext: false`（端侧不是 Web GUI，删掉注入的假系统提示）；`printUrl: true` **必须保留**（token 正是从这行 stdout 抓的）；`openBrowser: false`。
- 落地形态（零上游 patch）：bundle 包 `@hdsh/bundle-ondevice` 声明 `cordis.patch.yml`；profile 目录 `profiles/ondevice/` 引 `@deepseek-ai/dsh-base` + `dsh-web-app` + 该 bundle；能力探测在启动前算好作覆盖层——同一棵核心树可按设备能力起出不同 Host。用户启停行写 `<profile>/.hdsh-plugin-rows.yml`（种子+用户行，入口脚本每次启动重组 `cordis.patch.yml`，`patchReload: 'startup'`）。
- profile 相关沙箱事实：`$DSH_HOME/profiles/node_modules` 建符号链接被禁（`13900012`）⇒ 入口脚本设 `process.pkg = process.pkg || {}` 让 dsh 走 pkg 形态的 **ESM proxy 分支**（真实目录 + entry-N.js，零上游 patch）；会话日志发布用 `link(2)` 也被禁 ⇒ `pack-core` 的 `patchLinkForSandbox()` 改为存在性检查 + rename（上游漂移即报错退出）。

## 6. 核心版本与插件（dsh 没提供，本项目自建）

### 6.1 核心版本：激活事务（stage → verify → switch → rollback）

- dsh 无候选核心 staging、无健康检查、无 activate/rollback、无自更新 ⇒ 端侧自建**多版本仓库**：`<files>/dsh/cores/<ver>/`（`.staging` 后缀被忽略）+ `<files>/dsh/state.json`（`{current, previous, history}`）。用户数据（`$DSH_HOME`）独立于核心树，升级/回滚不迁移不删除。
- 事务：导入 `.staging` → 校验（哨兵文件：`@deepseek-ai/dsh/package.json`、`koffi.node`、`profiles/ondevice/cordis.patch.yml`；刻意不做全树计数，避免主线程大遍历）→ 原子 rename 解包 → 健康检查（起一次 Host 到 `/api` 可用）→ 激活写 `state.json` → 清理旧版本（保留最近 N 个 + 永远保留 previous）。
- **切换/回滚的端侧形态**：同进程内第二次 `node::Start` 会让进程 SIGABRT（libnode 单进程只设计为启动一次）⇒ 切换/回滚实现为「**安排激活 + 重启应用生效**」（只写状态、不起候选；宿主未运行时仍走原路径）。真机已验：点切换不再崩溃 → 完全退出重开 → 新版本运行 + 自动接入。
- **换包必须能生效**：`BundledCore` 用资源包大小做指纹（`<coreDir>/.hdsh-bundled-stamp`），不一致就删旧树重装。**删除 2.5 万文件必须异步**——主线程同步删树会锁死 ArkUI 被 `LIFECYCLE_TIMEOUT`/`SYS_FREEZE` 杀（修法：`renameSync` 到 `.stale-<ts>.tmp` + 末尾异步清理）。
- 核心分发包容器是 **zip**（决策 D-6）：鸿蒙侧只有 `@ohos.zlib.decompressFile`；`pack-core.mjs` 自带最小 zip 写入器（约 66 MB / 约 2.9 万条目，未触及 zip64）。

### 6.2 插件

- dsh 无插件 Remote 安装/启停端点（`pluginInventory.list` 只读；`dsh plugin add` = `spawnSync("pnpm")`）⇒ **运行时安装/卸载在端侧永不成立**（与纯 JS 还是原生无关）；启停 = 写 profile 用户行 + 重启核心生效（§5）。
- 实测（`tools/scan-core-plugins.mjs`，可复跑）：核心树 518 包 / 27250 文件，含 `.node` 的包**恰好 3 个**（koffi、node-pty、`@ohos-ports/img-sharp-openharmony-arm64`）；152 个插件行 = 146 纯 JS / 6 依赖原生（`session-persistence-jsonl`、`attachment-local`、`subprocess`、`sandbox`、`web-startup`、`web-runtime`）/ 0 未知。
- **原生性是依赖闭包的属性，不是插件包自身**——6 行无一自带 `.node`；判据必须沿 dependencies 闭包走到底。判据只有一份（`tools/lib/core-inventory.mjs`，scan 与 pack-core 共用），结果写进树内 `hdsh-core.json`，端侧只读该 JSON；pack-core 写完读回逐字段核对，不符即打包失败。
- 原生件的实际供给：**koffi 3.x 自建**（dsh 要求 `koffi ^3.1.0` 而 `@ohos-ports` 只有 2.16.2，2.x 缺 `.size` 导致 fail-loud；`fetch-koffi.mjs` 取 npm 包自带源码编成 CMake MODULE 目标 ⇒ `DT_NEEDED libnode.so.127` 由链接器保证）；node-pty 用 `@ohos-ports` 版 + `patch-native-needed` 修补 `DT_NEEDED`；sharp = libvips 全套 45 库搬进 HAP `libs/arm64-v8a/`（改名 + 改 SONAME + 改各依赖方 `DT_NEEDED` + RPATH 改 `$ORIGIN`，`collect-libvips.mjs`），加载失败则退回「会报错但能挂载」的 stub（pack-core 有 `assertSharpImplIsReal()` 闸门防「桩假可用」）。
