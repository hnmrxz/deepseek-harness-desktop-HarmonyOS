## 0. 参数包装（`args` 的形状）——先看这个再查下面的表

线上签名形态判别规则（来源：`.research/protocol/remote-signatures.txt`，每行形如 `'ns/method': (p1, p2, signal?) => ...`）：

| 线上签名形态 | `args` 该长什么样 | 例 |
|---|---|---|
| `(request: T)` | `args = { request: {...T 的字段...} }` | `session/prompt` |
| `(_request: T)` | `args = { _request: {...} }` | `session/list` |
| `(agentId, request: T)` | `args = { agentId, request: {...} }` | `fileUploads/upload` |
| `(from, id, name?)` | `args = { from, id, name }`（扁平具名） | `agentPresets/copy` |
| `()` | `args = {}` | `session/modelCatalog` |

> **`agentId` 的语义（易错）**：`agent` 参数在 Host 侧是 `source: "lookup"` 的 **Agent 作用域**，Host 端由 Typert 把线上 `agentId` 解析成 Agent 对象再注入。对客户端而言，`agentId` **就是 Session Id**（`SessionId` 类型）。`session/prompt.request.sessionId`、`commands/execute.agentId`、`goals/*.agentId`、`fileUploads/upload.agentId` 是**同一个东西**。`source`: `.research/protocol/typert-extracted.json` → `faces["dsh-commands#host"].invocations[?method=list].parameters[0]` `{ name: "agent", wire: "agentId", source: "lookup", lookup: "agent" }`，其 `codec.typeSymbol` = `@deepseek-ai/dsh-session/types#SessionId`。

> **`signal` 不是 `args` 字段**。它是 `@Remote` 的取消参数，走 mux 的 `cancel` 帧或 HTTP `AbortSignal`，**绝不放进 `args`**（D2 §1.1/§1.2）。

## 1. `session` 命名空间（18 个端点）

来源总表：`dsh-api-session-controller/lib/typert.remote-client.d.ts` → `interface TypertRemoteMap`。

### 1.1 只读与会话生命周期

#### `session/list` — 包装 `_request`（**带下划线**）

- `args = { _request: {...} }`，`source`: `dsh-api-session-controller/lib/types/types.d.ts` → `interface SessionListRequest`

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `cursor` | `string` | 否 | 预留游标。0.1.5 的 Host 实现**忽略**该字段；不要依赖它做分页 |

- **回复** `SessionListValue` = `{ items: SessionSummary[] }`，`source`: 同上 → `interface SessionListValue` / `interface SessionSummary`

`SessionSummary` 字段：`sessionId`(string)、`updatedAt`(number, epoch ms)、`running`(boolean)、`blank`(boolean)、`parentSessionId?`(string)、`origin?`(`'subagent'`)、`cwd?`(string)、`projections?`(`{ asOfSeq: number; values: SessionProjectionValues }`)。

`projections.values` 是**稀疏对象**，可能出现的键见 §7.3 的 `SessionProjectionMap`。

> 实测佐证：`session/list` 带 `_request` 返回 `200 {"items":[]}`；不带则 `gateway/arguments-invalid`（D2 §8.4/§8.6）。

#### `session/search` — 包装 `request`

`args = { request: { query: string } }`；`query` 必填（字面量内容查询，非正则）。
**回复** `SessionSearchValue` = `{ items: SessionSearchItem[]; hasMore: boolean }`，`SessionSearchItem` = `{ sessionId, snippet }`。
上限：`SESSION_SEARCH_RESULT_LIMIT = 20`、`SESSION_SEARCH_SNIPPET_MAX_CODE_POINTS = 240`（同一 `.d.ts` L161/L163）。

#### `session/create` — 包装 `request`

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `workspaceId` | `string` | 否 | 归属工作区；**与 `cwd` 互斥**（同传报 `gateway/bad-request`） |
| `cwd` | `string` | 否 | 直接指定目录 |
| `sessionId` | `string` | 否 | 显式指定/幂等认领既有 Session |
| `agentPreset` | `string` | 否 | Agent 预设 id |

**回复** `SessionCreateValue` = `{ sessionId, agentPreset? }`。

#### `session/rename` — 包装 `request`

`{ sessionId: string, title: string }`；**回复** `SessionRenameValue` = `{ title, seq }`（`seq` 是提交该标题的持久事件序号）。

#### `session/fork` — 包装 `request`

`{ sessionId: string, atSeq?: number }`（`atSeq` 必须是**已完成轮次**内的安全整数）；**回复** `{ sessionId }`。
失败码：`session/fork-unavailable`、`session/not-found`。

#### `session/selectModel` — 包装 `request`

| 字段 | 类型 | 必填 |
|---|---|---|
| `sessionId` | `string` | **是** |
| `provider` | `string` | **是**（来自 `ModelSelection`） |
| `model` | `string` | **是** |
| `reasoningEffort` | `string` | 否 |

**回复** `SessionSelectModelValue` = `{ selected: { provider, model, reasoningEffort? } }`（Host 归一化后的值，可能与请求不同）。

#### `session/openWorkspacePath` — 包装 `request`

`{ action?: 'reveal', path: string }`。`action` 省略 ⇒ 用默认程序打开；`'reveal'` ⇒ 在文件管理器中定位。`path` 不可为空字符串。**回复** `{ opened: true }`。

#### `session/canOpenWorkspacePath` — 无参数

`args = {}`；**回复** `boolean`（不是对象）。

#### `session/modelCatalog` — 无参数

**回复** `ModelCatalog`：

```
{
  default: { provider, model, reasoningEffort? },      // ModelSelection
  routableProviders: string[],                          // 当前可路由的 provider id
  groups: { id, name, models: { id, name, description?,
              reasoning?: { efforts: {id,name,description?}[], defaultEffort? } }[] }[],
  failures: { id, name, message }[]                     // 模型目录加载失败的 provider
}
```

### 1.2 发消息、附件与队列

#### `session/prompt` — 包装 `request`（**最高频、最重要**）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `requestId` | `string`（brand `session-request-id`） | **是** | **客户端自铸**的幂等 id。Host 用它做去重（同 id 重复提交返回 `{accepted:true}`），并把它持久化进 `user/message.source.rpcId` 用于乐观回显对账。**必须客户端生成，不可复用** |
| `sessionId` | `string` | **是** | 目标 Session |
| `mode` | `'queue' \| 'steer'` | **是** | `'queue'` = 排到下一轮；`'steer'` = 插进当前轮最近的一步 |
| `content` | `PromptContentPart[]` | **是** | 见下表。必须至少含一个非空白文本片段**或**一个附件，否则 `gateway/bad-request` |
| `clientTimeZone` | `string` | 否 | `'UTC'` 或合法 IANA `Area/Location`。非法报 `session/invalid-time-zone` |

`PromptContentPart` 判别联合（`type` 为判别字段）：

| `type` | 字段 | 含义 |
|---|---|---|
| `'text'` | `text: string` | 纯文本 |
| `'image'` | `mediaType: 'image/png'\|'image/jpeg'\|'image/webp'\|'image/gif'`、`data: string`（**base64**）、`name?: string` | 内联图片；Host 会转成持久引用。模型不支持图片输入时报 `session/attachment-invalid` + `details.reason = 'MODEL_DOES_NOT_SUPPORT_IMAGES'` |
| `'file'` | `receiptId: string` | **0.1.5 新增**。指向此前 `fileUploads/upload` 返回的收据；Host 用 `fileUploads.resolve(agent, receiptId)` 换取持久引用，换不到报 `session/attachment-invalid` + `reason:'FILE_NOT_STAGED'` |

**回复** `SessionPromptValue` = `{ accepted: true }`（**只有这一个字段，没有 messageId**）。要拿到真实消息 id 必须靠 §7.1 的 `session/follow` 或 `session/page`。

> 图片要么走 `session/prompt.content[].type='image'`（内联 base64，受 `imageLimits` 约束），要么先 `fileUploads/upload` 或 `POST /api/session/uploadFileBinary` 拿 `receiptId`，再用 `content[].type='file'`。两条路都合法。

#### `session/attachment` — 包装 `request`

`{ sessionId: string, attachmentId: string }`。
**回复** `SessionAttachmentValue` = `{ attachment: ImageAttachmentRef; data: string }`。
`ImageAttachmentRef` = `{ attachmentId, mediaType, bytes, width, height, name?, originalDimensions?: {width,height} }`；`data` 是 base64。
授权规则：`attachmentId` 必须被该 Session 日志引用过，否则 `session/attachment-invalid` + `reason:'ATTACHMENT_NOT_REFERENCED'`。

#### `session/updateQueue` — 包装 `request`

| 字段 | 类型 | 必填 |
|---|---|---|
| `sessionId` | `string` | 是 |
| `itemId` | `string`（`MessageId`） | 是（来自 `SessionQueuedItem.id`） |
| `action` | `QueueAction` | 是 |

`QueueAction` 判别联合（`kind` 为判别字段）：

| `kind` | 附带字段 | 语义 |
|---|---|---|
| `'edit'` | `content: ContentBlock[]` | 替换队列项内容。**只接受纯文本块**，含非 `text` 块报 `session/attachment-invalid` + `reason:'QUEUE_EDIT_NON_TEXT'` |
| `'remove'` | — | 移除队列项 |
| `'steer'` | — | 把队列项改成 steer 插队。仅当该项位于 `next-turn` **且** Agent 正在运行，否则 `session/steer-unavailable` |

**回复** `{ accepted: true }`。

#### `session/cancel` — 包装 `request`

`{ sessionId: string }` ⇒ **回复** `{ accepted: true }`。
语义：取消**当前活动轮次**但**保留**待处理收件箱（`agent.cancel({kind:'user'}, {keepInbox:true})`）。Session 未附着（无 live Agent）⇒ `session/not-found`。

#### `session/page` — 包装 `request`

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `address` | `SessionAddress` | **是** | 见下 |
| `throughSeq` | `number` | **是** | 包含式日志切点。`-1` 表示「到当前末尾」。必须 `>= -1` 的安全整数（实测注意：`-1` 会返回空页，游标须取 `session/list` 的 `projections.asOfSeq`，见 D2 §8.7.23） |
| `beforeSeq` | `number` | 否 | 向前分页游标，非负安全整数 |
| `maxMessages` | `number` | 否 | 正整数，默认 **50**（`DEFAULT_MAX_MESSAGES`） |

`SessionAddress` 判别联合（`kind` 为判别字段）：
- `{ kind:'session', sessionId }`
- `{ kind:'subagent', parentSessionId, childSessionId, mode:'one-shot'|'continuable' }`

**回复** `SessionPage` = `{ records: SessionHistoryRecord[]; hasMore: boolean }`，`SessionHistoryRecord` = `{ type:'event', event: SessionWireEvent }`。

## 2. `workspaceFiles` 命名空间（**0.1.5-rc.1 新增，7 个端点**）

来源总表：`dsh-api-workspace-files/lib/typert.remote-client.d.ts`（L20-26）。类型权威：`.research/dsh-src/packages/api/workspace-files/src/types.ts` 与同包 `src/index.ts`。

### 2.0 `workspaceFileScopeId` 是什么？客户端从哪拿？

**结论（有确证）**：`workspaceFileScopeId` **就是 Session Id**（`SessionId`，字符串）。它**不是**工作区 id，也**不是**新造的句柄。

| 问题 | 答案 | 来源 |
|---|---|---|
| 线上字段类型 | `SessionId`（字符串） | `dsh-api-workspace-files/lib/typert.remote-client.d.ts` L11-17 → 签名第一个参数写作 `workspaceFileScopeId: SessionId` |
| Host 端如何解析 | Typert lookup：`register('workspaceFileScope', { parameter:'workspaceFileScope', wire:'workspaceFileScopeId', wireTypeSymbol:'@deepseek-ai/dsh-session/types#SessionId' })` | `dsh-api-workspace-files/lib/index.js` L373-376；同 `src/index.ts` L201-220 |
| lookup 返回什么 | `WorkspaceFileScope = { sessionId, workspaceRoot }`；`workspaceRoot` 取 `header.cwd`，无 cwd 时回落 `sandboxPolicy.workspaceRoot` | `dsh-api-workspace-files/lib/types/index.d.ts` L33-39；`src/index.ts` L207-218 |
| 作用域粒度 | **会话级**（每个 Session 一个 workspaceRoot）。是「哪个会话的根目录」，不是「哪个工作区」 | 同上 |
| 冷会话可用吗 | 可以。live Session 读内存 header，冷的走 `sessionPersistence.stat(sessionId)` 只读 header，**不激活 Agent、不读事件正文** | `src/index.ts` L207-220 |
| 客户端从哪拿 | **直接用自己正在看的 Session Id**。0.1.5 自己的客户端就是这么做的：`remote.workspaceFiles.stat(sessionId, path, signal)`，其中 `sessionId` 来自资源地址 `dsh-resource://file/session/<sessionId>/<path>` | `.research/dsh-src/packages/api/workspace-files/src/client/provider.ts` L58-61、L118-121 |

> **错误码**：`workspace-file/not-found`、`workspace-file/outside-workspace`、`workspace-file/too-large`、`workspace-file/not-text`、`workspace-file/not-regular-file`、`workspace-file/not-directory`（`source`: `src/types.ts` L145-165 的 `RemoteErrorDetailsMap`）。

### 2.1 `workspaceFiles/list` — 命名参数

`args = { workspaceFileScopeId, path }`（两者都必填）。

**回复** `WorkspaceDirectoryListing`（`source`: `src/types.ts` L89-104）：

```
{
  path: string,                    // 被列举目录的「工作区相对路径」；工作区根为空串
  entries: { name: string,         // 目录内 basename；子项全路径 = path + '/' + name
             type: 'file' | 'directory' | 'other',
             size?: number           // 仅常规文件且后端报告时存在
           }[],
  truncated: boolean               // 是否因条目上限被截断
}
```

**关键事实**：
- **不是树，是「某一层目录的直接子项」扁平列表**。要建树必须逐层调用（子项路径 = 父 `path` + `'/'` + `name`）。
- **无 `mtime` / `version` / `isDirectory` 布尔**：类型判别字段叫 `type`（取值 `file|directory|other`），不是 `kind`/`isDirectory`。
- **无分页**。用部署上限截断：`maxEntries` 默认 **2000**，超出部分**丢弃**并把 `truncated=true`。
- 符号链接报告**目标**类型；但 `read` 仍拒绝软链（`workspace-file/not-regular-file` + `kind:'symlink'`）。
- **只有 `list` 受工作区包含约束**：目标解析出工作区外报 `workspace-file/outside-workspace`。
- **路径词法**：`list` 说「工作区路径」（相对工作区根，或绝对）；`read`/`readBytes`/`stat`/`changes` 说「文件系统执行世界的绝对路径」。这是 `src/types.ts` 文件头明确写的两套词法。
- **请求根必须传 `"."`**（空串报 `gateway/bad-request: path is required`；请求 `"."` 时回复 `path` 仍为 `""`，实测见 D2 §8.7.16）。

### 2.2 `workspaceFiles/stat` — 命名参数

`args = { workspaceFileScopeId, path }`。
**回复** `WorkspaceFileStat` = `{ absolutePath: string, version: string, bytes?: number }`。
- `version` 是**不透明新鲜度令牌，永不被解析**（`src/types.ts` L31-32）。客户端只做「与上次不同 ⇒ 内容变了」的比较。
- `bytes` 是**完整文件**大小（不是窗口大小），后端不报告时缺省。

### 2.3 `workspaceFiles/read` — 命名参数（**文本按行**）

`args = { workspaceFileScopeId, path, range }`。`range` **必填**（可为 `{}`）。
`range: WorkspaceFileRange` = `{ offset?: number; limit?: number }`：

| range 字段 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `offset` | `number` | **1** | **行号，1-based**。不是字节偏移 |
| `limit` | `number` | `maxLines`（默认 **5000**） | **行数上限**，不得超过 `maxLines` |

**回复** `WorkspaceFileText` = `WorkspaceFileStat & { offset: number, text: string, lines: number, eof: boolean }`：
- `text` 是页内各行用 `'\n'` 连接，**末行后无终止符**。
- `lines` 是页内行数；`offset` 越过文件末行时为 **0**（此时 `text` 为空串）。
- `eof` 表示本页是否包含文件最后一行。返回**文本**，不是 base64。
- 行按 `\n` 结束；文件末尾的 `\n` **终止最后一行**而不新起一个空行。

**拒答边界**：单页文本超过 `maxBytes`（默认 **2 MiB**）⇒ `workspace-file/too-large`（**拒绝而非截断**）。内容非 UTF-8 或含 NUL ⇒ `workspace-file/not-text`。非普通文件 ⇒ `workspace-file/not-regular-file`。

### 2.4 `workspaceFiles/readBytes` — 命名参数（**原始字节按窗口**）

`args = { workspaceFileScopeId, path, range }`，`range` **必填**。
`range: WorkspaceByteRange` = `{ offset?: number; length?: number }`：

| range 字段 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `offset` | `number` | **0** | **字节偏移，0-based** |
| `length` | `number` | `maxBytes`（默认 2 MiB） | **字节数**，不得超过 `maxBytes` |

**回复** `WorkspaceFileBytes` = `WorkspaceFileStat & { offset, data: string, eof: boolean }`：`data` 是窗口字节的 **base64**；`eof` 表示是否含文件最后一个字节。
与 `read` 的区别：**不解码、不拒绝二进制**（可以读 exe/zip 的片段）。

### 2.5 `workspaceFiles/readAll` — 命名参数（**整文件**）

`args = { workspaceFileScopeId, path }`（**无 `range`**）。
**回复** 与 `readBytes` 同型：`WorkspaceFileBytes`，恒有 `offset = 0`、`eof = true`。
约束：完整文件超过 `maxFileBytes`（默认 **32 MiB**）⇒ `workspace-file/too-large`（**拒绝，永不截断**）。大文件应用 `readBytes` 分窗。

### 2.6 `workspaceFiles/readRelated` — 命名参数

`args = { workspaceFileScopeId, path, relativePath }`（三字段全必填）。
`path` = 基准文件；`relativePath` = **相对文件系统路径**（不是 URL、不是绝对路径、不得含 NUL），相对**基准文件所在目录**解析。返回整文件（等价于对解析出的路径调 `readAll`，**同样受 `maxFileBytes` 与文件种类检查约束**）。
非法 `relativePath` ⇒ `gateway/bad-request`。

### 2.7 `workspaceFiles/changes` — **流式**，命名参数

`args = { workspaceFileScopeId }`。逐项结构见 **§7.4**。

> **`read` / `readBytes` / `readAll` / `readRelated` 不受工作区包含限制**——只做普通文件检查，允许读工作区外的可读路径。**只有 `list` 与 `changes` 是工作区受限的**。

### 2.8 四个读端点速查

| 端点 | `range` 类型与单位 | 回复里的内容字段 |
|---|---|---|
| `read` | **行**：`{ offset?: number, limit?: number }`，`offset` 1-based 行号、`limit` 行数 | `WorkspaceFileText`：`text`（UTF-8 文本）+ `lines` + `eof` |
| `readBytes` | **字节**：`{ offset?: number, length?: number }`，`offset` 0-based 字节偏移、`length` 字节数 | `WorkspaceFileBytes`：`data`（**base64**）+ `eof` |
| `readAll` | 无 `range`，读整文件 | `WorkspaceFileBytes`（`offset` 恒 0、`eof` 恒 `true`） |
| `readRelated` | 无 `range`，`relativePath` 相对**基准文件所在目录**解析 | `WorkspaceFileBytes`（等价于对解析结果调 `readAll`） |

> **`range` 在三个带 `range` 的端点上都是必填参数**（要么传 `{}` 用默认值，要么传具体字段）。省略整个 `range` 键会报 `gateway/arguments-invalid`。
> **单位不要混**：`read` 的 `offset`/`limit` 是**行**；`readBytes` 的 `offset`/`length` 是**字节**（`limit` vs `length` 的命名是刻意的不对称）。
> **`read` 返回文本，`readBytes`/`readAll`/`readRelated` 返回 base64。** 只有 `read` 会拒绝二进制（`workspace-file/not-text`）。

### 4.1 「void 回复」的线上形态

`credentials/set`、`credentials/unset`、`agentPresets/copy`、`agentPresets/deletePreset` 的 `result.typeSymbol` 是 `void`。它们的成功响应体是：

```json
{ "type": "server-response", "rpcId": "...", "result": { "ok": true } }
```

**`result.value` 键不存在**（不是 `null`）。原因：Host 构造 `{ ok: true, value: await this.invoke(...) }`，业务方法返回 `undefined`，`JSON.stringify` **丢弃值为 `undefined` 的键**。
`source`: `dsh-api-gateway/lib/index.js` → `invokeRpc()`；`dsh-client-connection/lib/index.js` → `fullResponse(rpcId, result)`。

**规则**：客户端解析器 `parseConnectionResponse` **只要求** `result.ok === true`，然后无条件读 `result.value`；**缺失 `value` 是合法的**，解析结果是 `value === undefined`。
`source`: `dsh-client-connection/lib/client.js` → `parseConnectionResponse`（**无存在性校验**）。

> **对端侧的直接含义**：ArkTS 的响应解析**不得**把「`ok:true` 但没有 `value` 字段」判为畸形信封，否则四个 void 端点会全部失败。

### 6.2 `fileUploads`（**0.1.5-rc.1 新增**）

`fileUploads/upload` — 命名（可取消）：`args = { agentId: string, request: EncodedFileUploadRequest }`。

> **⚠ 线上参数名是 `agentId`（已实测，2026-09-11）**：该端点 `.d.ts` 的形参名与线上名不一致；写成 `{agent, request}` 会被拒：`gateway/arguments-invalid: … missing "agentId"; unexpected "agent"`。构造载荷以**生成上表的 `params`（wire 名）** 为准，不以 `.d.ts` 的形参名为准。

| `request` 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `data` | `string` | **是** | 文件字节的 **base64**（规范编码） |
| `name` | `string` | 否 | 显示名；Host 会消毒成存储叶子名 |

**回复** `FileUploadValue` = `{ receiptId: string, file: FileAttachmentRef }`，`FileAttachmentRef` = `{ attachmentId, name, bytes }`。
`agentId` 必须是**普通会话**（非 subagent）；subagent 会话报 `subagent/attachment-invalid` + `reason:'SUBAGENT_FILE_UNSUPPORTED'`。
收据是 **Agent 作用域**的：换一个 Session 用同一 `receiptId` 会被 `fileUploads.resolve()` 判为未知 ⇒ `session/attachment-invalid` + `reason:'FILE_NOT_STAGED'`。

#### 完整上传流程（两条路）

上传后拿到的 `receiptId` 有两个消费口：`session/prompt.request.content[].type='file'` 与 `commands/execute.submittedAttachments[].type='file'`。

| 路 | 步骤 | 载体 | 说明 |
|---|---|---|---|
| **A. RPC 内联 base64** | 一次 `fileUploads/upload`，请求体里带完整 base64 | 一元 RPC `POST /api/fileUploads/upload` | base64 膨胀 ≈33%，整个文件在一条 JSON 里；适合中小文件 |
| **B. 原始字节流式路由** | `POST /api/session/uploadFileBinary?sessionId=<id>[&name=<n>]` | **HTTP 路由，不是 RPC**；`content-type: application/octet-stream`；请求体是裸字节流 | **支持分块/流式上传，无 base64 膨胀**（Host 端 `request.body` 逐块读取）。**适合大文件** |

- 路径常量：`FILE_UPLOAD_PATH = '/api/session/uploadFileBinary'`（`source`: `.research/dsh-src/packages/client/file-upload/src/protocol.ts` L2）
- 响应：HTTP **200** + JSON `{ ok: true, value: FileUploadValue }` 或 `{ ok: false, error: { code, message, details } }`；非 `POST` ⇒ 405；`content-type` 不是 `application/octet-stream` ⇒ 415；缺 `sessionId` ⇒ 400
- 认证：与其他 `/api` 路由同一 cookie（D2 §2.1）
- `source`: `.research/dsh-src/packages/client/file-upload/src/http-route.ts` L22-67

**关于「进度」（已核实）**：
- **协议层（线上）没有任何进度帧**。`uploadFileBinary` 的响应是**一次性** JSON（上传完成后才返回）；`fileUploads/upload` 更是一次性 base64 提交。
- **客户端可以在发送侧拿到逐块进度**：0.1.5 的 Web 客户端把请求体包成 `ReadableStream`，在 `pull()` 里累计 `loaded += chunk.byteLength` 并回调 `onProgress({ loaded, total? })`（`source`: `.../client/runtime.ts` L111-131、L193-209）。
- **端侧结论**：用 `@ohos.net.http` 的流式上传（或按块分写）**在发送侧统计已发送字节数**驱动进度条；不要等 Host 回传进度。

**收据的生命周期**：`receiptId` 在**成功进入某个 prompt 的收件箱**之前有效；一旦对应的 `user/message` 事件以该 prompt 的 `requestId` 落盘，Host 就**回收**收据（`retire`）。「上传后长期缓存收据、以后再发」不成立——必须在上传后尽快随 prompt 提交。
`source`: `.research/dsh-src/packages/client/file-upload/src/index.ts` L241-254、L152-181。

## 7. 事件流（本文的核心）

### 7.1 `session/follow` 的逐项结构

`args = { request: SessionFollowRequest }`，`SessionFollowRequest = { address: SessionAddress, maxMessages?: number, assistantStream?: true }`。

**`type` 是判别字段，三种取值**：

| `type` | 何时出现 | 载荷 |
|---|---|---|
| `'snapshot'` | 每一代**恰好一次**，且是**首项** | `header`、`cursor`、`records`、`hasMore`、`projections`、`assistantStream?` |
| `'event'` | 快照之后的**持久事件**，`seq` 严格连续递增 | `event: SessionWireEvent` |
| `'assistant-stream'` | **仅当请求带 `assistantStream: true`**；进程本地，重连**不重放** | `frame: SessionAssistantStreamFrame` |

**`SessionWireEvent` 信封**（`source`: `types.d.ts` L397-407）：


> - **消息** → `user/message`、`system/message`、`assistant/message`（第 7 条带 `usage` 与 `interrupted`）。

> - **子代理事件** → `session/follow` 上的 `subagent/catalog`、`subagent/descriptor`；**另**有 Host 事件 `subagent/start` / `subagent/end`，但它们**不在** `$events` 转发白名单里（§8.2），所以端侧只能通过父会话的 `subagent/catalog` 事件或 `subagents/list` 端点感知。
> - **目标事件** → `goal/change`（会话日志）；`$events` 上另有 `goal/activation-changed`（§8.2 第 10 项）。
> - **任务/作业事件** → **不在 `session/follow` 上**。作业在 `session/control` 的 `jobs` 帧（§7.2）。
> - **错误事件** → 两个层次：轮次内错误是 `turn/end` 的 `reason.kind==='error'`；轮次外错误走 `$events` 的 `api-session/error`（§8.2 第 5 项）。
> - **轮次边界** → `turn/start` / `turn/end`（另有 `step/start` / `step/end`）。
> - **token/用量** → `assistant/message.data.usage`（`TokenUsage = {inputTokens, outputTokens, totalTokens?, cacheReadTokens?, cacheWriteTokens?, reasoningTokens?}`）。**没有独立的 usage 事件**——`SessionEventMap` 注释明确写「there is no separate usage record」。
> - **文件/交付物事件** → `session/follow` 上**没有**通用的「交付物」事件类型。文件相关事实来自：`tool/call`/`tool/result`（写文件的工具）、`commands/execute` 的返回、以及独立的 `workspaceFiles/changes` 流（§7.4）。**「交付物」是 Web 客户端从原始事件派生出来的呈现，不是协议事件**。

### 7.4 `workspaceFiles/changes` 的逐项结构

`args = { workspaceFileScopeId }`。

**`kind` 是判别字段，两种取值**：

| `kind` | 载荷 | 语义 |
|---|---|---|
| `'ready'` | — | Host 已开始观察 **instrumented 文件系统操作**并已解析工作区根。是每代**首项**，恰好一次 |
| `'change'` | `change` 字段，二者之一：`{ absolutePath: string, version: string }` 或 `{ absolutePath: string, absent: true }` | 一次观察 |

> **关键语义（直接决定客户端能不能用）**：
> 1. **帧是「观察」，不是「增删改差量」**。上游注释原文：*"Frames report observations, not deltas: a consumer already holding `version` learns nothing new from the frame and can ignore it."* 即客户端若已持有同一 `version`，该帧**可以安全忽略**。
> 2. **不是 OS 级文件监听**。只有经 `ctx.fs` 的 instrumented 操作会发 `fs/observed`；用别的程序改文件**不会**产生帧（`changes.ts` 文件头：*"Instrumented filesystem operations emit these observations; the operating system is not watched."*）。
> 3. **只有 `change` 帧带路径**；`ready` 无载荷。
> 4. `version` 是不透明令牌（§2.2），**只能比较相等，不能解析**。
> 5. 帧**按发射顺序**到达；工作区外目标被过滤掉（`ctx.fs.contains(root, target)`）。
> 6. 生成器在**根解析完成前**就挂好监听，所以解析期间产生的观察不会丢，会在 `ready` 之后按序补发。

### 8.3 会话列表能否只靠 `$events` 维持？

**结论：不能，但可以只靠 `$events` + 一次 `session/list` 维系。**

- 初始 baseline 必须来自 **`session/list`**（`{ _request: {} }` ⇒ `{ items: SessionSummary[] }`）。`$events` 的 `ready` **不带任何会话数据**（只有 `clientId` 与 `host.home`）。
- 之后：`api-session/added` 提供**完整**新行；`api-session/removed` 删除；`api-session/status` 只改 `running`；`api-session/activity` 只改 `updatedAt`。
- **缺口**：没有「标题变更」的转发事件。标题变化只能通过 `session/follow` 的 `session/title` 事件或 `projections`（`title` 键）感知——即**必须按会话订阅**。
- 端侧的正确形态：`session/list`（列表 baseline）+ `$events`（增删/运行态/活跃度增量）+ 按需 `session/follow`（单会话内容与标题）。

### 8.4 `$events` 事件权威声明中**未转发**的事件（避免误等）

| 事件 | 声明包 | 为什么收不到 |
|---|---|---|

## 9. 审批与用户提问的应答通路（**关键结论：不走 RPC 端点**）

### 9.1 总览

审批与提问都是 **`$events` 上的 waterfall 帧**，不是一元端点。客户端「应答」= 把结果 POST 回 `$events/result`。

```
Host: ApprovalService.request() / UserQuestions.ask()
   ↓ ctx.waterfall('approval/request' | 'user-questions/request', req, next)   [Agent 作用域]
dsh-api-remotes: 白名单命中 waterfall → 包装成 dispatch 推入 RemoteEventQueue
   ↓
dsh-api-gateway: startRemoteEvent() → 分配 eventId → 帧 { type:'waterfall', event, eventId, agentId, request }
   ↓ 广播给每个 $events 客户端
客户端: ctx.remote.$on('approval/request', (request, next) => ...)
   ↓ 用户作答
客户端: POST /api/$events/result  { args: { clientId, eventId, outcome } }
   ↓
dsh-api-gateway: receiveRemoteEventResult() → 解决该 pending waterfall
```

### 9.2 应答审批

**接收**（`type='waterfall'`，`event='approval/request'` 时 `request` 的字段）：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `toolName` | `string` | **是** | 请求决策的工具名 |
| `callId` | `string` (`ToolCallId`) | 否 | 关联的工具调用，可用于拉取工具自有详情 |
| `reason` | `string` | 否 | 提问方给出的可读理由 |

> `ApprovalRequestEvent` 的**类型定义**含 `agent: Agent` 与 `signal?: AbortSignal` 两个字段，但 `projectRemoteEventRequest` 在出网前**显式剥离**这两个键。**线上 `request` 里只有 `toolName`/`callId?`/`reason?`**。

**应答**：`POST /api/$events/result`，`args = { clientId, eventId, outcome }`：

| 字段 | 类型 | 来源 |
|---|---|---|
| `clientId` | `string` | 本代 `ready` 帧的 `clientId` |
| `eventId` | `string` | waterfall 帧的 `eventId` |
| `outcome` | 见下 | — |

**审批 `outcome` 取值域**（`source`: `dsh-user-approval` → `OUTCOMES` 常量与 `ApprovalOutcome` 声明）：

| 值 | 谁产生 | 语义 |
|---|---|---|
| `'allowed-once'` | **客户端** | **唯一的授权结果**——只授权本次动作 |
| `'rejected'` | **客户端**（也由 `'never'` 策略直接产生） | 拒绝 |
| `'cancelled'` | Host（请求信号被中止） | 已取消（客户端**不必**发） |
| `'unavailable'` | Host（无 answerer / answerer 抛错 / 返回值不在词表内） | **fail-closed** 兜底（客户端**不必**发） |

> **只有两个字面量是客户端该发的**：`'allowed-once'` 与 `'rejected'`（Web 客户端审批面板正好只有这两颗按钮）。
> **没有「总是允许」客户端结果**。要「不再问」必须改策略：`approval/policy` 会话事件（`'ask' | 'never'`），**不是**审批应答的一个 outcome。
> **fail-closed 语义**：answerer 缺失或抛错 ⇒ `'unavailable'`；返回词表外的值也归一成 `'unavailable'`。客户端**绝不能**靠「不发应答」来表达允许——不发就是拒绝。
> **策略 `'never'` 在服务自己内部判定**，在派发 waterfall 之前就返回 `'rejected'`：即使某个监听器用 `prepend: true` 抢在前面也无法绕过。

**审计对**：每次审批都会在**发起它的会话日志**里落一对事件 `approval/asked`（`{id, toolName, callId?, reason?}`）→ `approval/decided`（`{id, outcome}`）。这对事件必须在**一个打开的轮次内**。客户端也能从 `session/follow` 读到审批历史。

### 9.3 应答用户提问

**接收**（`type='waterfall'`，`event='user-questions/request'` 时 `request` 的字段）：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `questions` | `AskUserQuestionItem[]` | **是** | 问题批次 |
| `agent` | `Agent` | 否 | 出网前被剥离 |
| `signal` | `AbortSignal` | 否 | 出网前被剥离并转为客户端 delivery 生命周期 |

`AskUserQuestionItem`：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | `string` | **是** | 稳定问题 id，**应答里要原样回传** |
| `question` | `string` | **是** | 展示的问题文本 |
| `detail` | `string` | 否 | 附加说明（markdown），渲染在问题下方但**不进入选项标签** |
| `header` | `string` | 否 | 短标题/分组标签 |
| `options` | `{ label: string, description?: string }[]` | 否 | 可选项；**没有 id，应答用 `label` 字符串** |
| `multiSelect` | `boolean` | 否 | 是否多选（默认单选） |
| `intent` | `{ kind: 'plan-review', approve: string }` | 否 | **纯呈现意图**，不改变应答编码。`approve` 指定哪个**选项 label** 表示批准；其他选项表示拒绝 |

**应答**：同样的 `POST /api/$events/result`，`outcome = { kind: 'result', value: <AskUserQuestionAnswer> }`，其中：

```
AskUserQuestionAnswer = { answers: AskUserQuestionAnswerItem[] }
AskUserQuestionAnswerItem = {
  id: string,          // 对应提问的 question.id
  selected: string[],  // 选中的【选项 label 字符串】；跳过的题传 []
  custom?: string      // 自由文本「其他」答案
}
```

**答案词表与约束**：
- `selected` 的元素是**选项的 `label` 原文**（不是索引、不是 id）。`source`: `types.ts` L51-58；Web 客户端 `decide(label)` 传的就是 label。
- 多选题允许 `selected` 与 `custom` **同时**存在。单选时客户端会二选一。
- **跳过**某题 = 该题 `{ id, selected: [] }`（`source`: client.js 的 `value.skipped` 分支）。
- **取消整组**在客户端是**拒绝**该 waterfall（`ASK_CANCELLED`），**不是**发一个空答案。请求生命周期结束时客户端 `abort` ⇒ `ASK_ABORTED`，同样不是答案。

## 10. 取消运行中的轮次 / 发新 prompt（含图片与附件）

### 10.1 取消 / 中断正在运行的轮次

| 场景 | 做法 | 请求 | 回复 | 结果 |
|---|---|---|---|---|
| 取消**普通会话**当前轮次 | `session/cancel` | `args = { request: { sessionId } }` | `{ accepted: true }` | 保留收件箱（`keepInbox: true`）；落盘 `turn/end` 且 `reason = {kind:'aborted', reason:{kind:'user'}}` |
| 取消**可续子代理**当前运行 | `subagents/interruptByParent` | `args = { childSessionId, parentSessionId, mode: 'continuable' }` | `{ accepted: true }` | **不是** `session/cancel` 的替代：`session/cancel` 对 subagent 拥有权的会话会报 `apiSessionSubagentOwnershipError` |
| 取消**正在进行的 RPC 调用本身**（尚未进入轮次） | mux `cancel` 帧（流式）或 `AbortSignal`（一元） | `{ type:'cancel', streamId }` | 无 | 见 D2 §1.2 |

**要点**：
- `session/cancel` 只对 **live（已附着）** Agent 生效；Session 未附着 ⇒ `session/not-found`，消息是 `session "<id>" not found (not attached)`。取消**不会**把冷会话唤醒。
- `session/cancel` **不清空收件箱**。要清队列得逐项 `session/updateQueue` 的 `remove`。
- `session/cancel` 的 `request` **只有 `sessionId` 一个字段**，没有 `reason`、没有 `turn`。
- 取消是**异步生效**：`{ accepted: true }` 只表示「已把取消请求送达 live Agent」。真正的结束信号是 `session/follow` 上的 `turn/end`（`reason.kind==='aborted'`），或 `session/control` 上该会话的 `jobs` 帧。

### 10.2 发新 prompt（含图片 / 附件）

**最小可用调用**：

```jsonc
// POST /api/session/prompt
{ "args": { "request": {
    "requestId": "<客户端自铸的 uuid>",
    "sessionId": "<sessionId>",
    "mode": "queue",                       // 或 "steer"
    "content": [ { "type": "text", "text": "你好" } ],
    "clientTimeZone": "Asia/Shanghai"      // 可选
} } }
// → { ok:true, value: { accepted: true } }
```

**带内联图片**：

```jsonc
"content": [
  { "type": "text",  "text": "这张图里有什么？" },
  { "type": "image", "mediaType": "image/png", "data": "<base64>", "name": "shot.png" }
]
```

**带已上传文件（0.1.5 新增路径）**：

```jsonc
"content": [
  { "type": "text", "text": "看看这个文件" },
  { "type": "file", "receiptId": "<fileUploads/upload 或 /api/session/uploadFileBinary 返回的 receiptId>" }
]
```

**要点与陷阱**：
1. **`requestId` 必须由客户端生成且每次唯一**。Host 用它做幂等：同一 `requestId` 重复提交返回 `{accepted:true}` 而不重复入队。它同时被持久化进 `user/message.data.source.rpcId`，是乐观消息与落盘消息对账的唯一键。
2. **内容不能为空**：必须至少一个非空白 `text` 片段**或**一个附件，否则 `gateway/bad-request`（`prompt content must include non-whitespace text or an attachment`）。
3. **`mode: 'steer'` vs `'queue'`**：`'queue'` 排到当前轮之后的下一轮；`'steer'` 插进**当前轮最近的一步**。
4. **图片有服务端上限**：具体数值由 Host 的 `attachments.imageLimits` 决定，客户端应**从 `session/control` 的 `projections.imageLimits` 或 `session/list` 的 `projections.values.imageLimits` 读取**，不要硬编码。
5. **模型必须支持图片**：否则 `session/attachment-invalid` + `details.reason = 'MODEL_DOES_NOT_SUPPORT_IMAGES'`。客户端应先用 `session/modelCatalog` 判断，或直接处理该错误码。
6. **`{accepted:true}` 不是「模型已回复」**，只是「已进收件箱」。要看到消息必须消费 `session/follow`。
7. **不要用 `session/cancel` 来「清空重发」**；它对收件箱无效。

### 10.3 附件上传的两条路（回到 §6.2）

```
路 A（RPC）:   fileUploads/upload          { agentId, request:{ data(base64), name? } }  → { receiptId, file }
路 B（HTTP）:  POST /api/session/uploadFileBinary?sessionId=&name=   (application/octet-stream, 裸字节流)
                                            → 200 { ok:true, value:{ receiptId, file } }
                                 ↓ 任一
              session/prompt.request.content[].type='file'  { receiptId }
              或 commands/execute.submittedAttachments[].type='file' { receiptId }
```

**上传是否分块/带进度**：路 B 在**请求体层面**是流式的（Host 逐块读 `request.body`），**但协议不上报 Host 侧进度**——响应只在全部字节接收完后一次性返回。客户端进度来自**发送侧**逐块统计（见 §6.2）。路 A 一次性提交完整 base64，无分块可言。

#### 11.4.2 `compat-drift.mjs` 比的是内部名，因此**看不见线上改名**（高严重度）
