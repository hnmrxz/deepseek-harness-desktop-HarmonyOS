# 当前状态与缺口

更新时间：2026-09-16

## 已完成/已形成事实

- 本地 dsh Host + 原生 ArkUI Client 的产品定位已确定。
- `phone` / `tablet` / `2in1` 已写入模块设备类型；多窗口基础架构已存在。
- `EntryAbility` 负责窗口生命周期与系统能力装配，不直接持有会话状态；共享状态位于 appstate。
- `Tokens / HarmonyTheme / NativePrimitives` 形成 UI 令牌到原生组件链；布局由 Breakpoints / LayoutController / NavigationController 收敛。
- 最近 P7 已覆盖目标操作、模型重试、审批两选、队列竞态、失败恢复、`@`/`/` token 替换、斜杠命令等。
- SDK 口径为 `6.1.1(24)`；build profile 同时包含 `arm64-v8a` 与 `x86_64` ABI。

## 主要缺口

### A. 真机证据仍是发布前关键项

远程环境无法代替真实设备验证。尤其需要真机确认：通知/后台、软键盘、窗口恢复、折叠态切换、触控手势、功耗、长时运行、原生图片/文件能力。

### B. API 24 兼容债务

现有技术记录已经发现部分 API 26 能力与 API 24 兼容目标之间的风险；P8 必须把每个风险转为代码级守卫/回退/升级决策，不允许“编译有警告但认为没关系”。

### C. 运行时与资源闭包

Node Runtime、原生库、核心包、Host 资源之间需要持续做新克隆可构建检查，避免被忽略规则或本地产物污染事实。

### D. 四形态的一致性验收

目前最大的产品风险不是缺少一个按钮，而是手机/折叠/平板/2in1 在相同会话状态下的导航、输入、浮层、通知、窗口模型是否真正一致。

### E. 文档治理

原文档存在旧目标与新目标并存、重复结论、历史记录与当前规范混杂等问题。本轮以 `docs/01~07` 作为新的权威入口；旧编号文档保留为事实附录，后续只记录来源与迁移说明。

## 下一步决策顺序

1. 先收口 P8 技术债与 API 24。
2. 再完成 P9 四形态 UI 设备验收。
3. 再做 P10 运行时治理与升级回滚。
4. 最后做 P11 性能与 P12 发布。

不建议在此之前继续增加新的低频产品功能。
